# 참고자료 기반 기획 워크플로우

[GitHub 이슈 #43](https://github.com/ywj3493/claude-skills/issues/43)을 구현하며,
#42에서 제기한 화면 소유권 결정도 포함한다. 플러그인 버전은 0.4.0이다.

## 진입 조건과 소유권

서비스 목적, 액터, 핵심 과업, 성공 기준, 범위, UI 필요 여부, 고정 제약/목표로
구분한 화면 수에서 기획을 시작한다. 기술 스택이 미정이어도 요구사항·화면·검토·
정적 목업을 진행한다. UI 없는 프로젝트는 요구사항/스토리를 유지하고 화면 문서는 생략한다.

| 작업 | 스킬 | 입력 | 산출물 | 검토 |
|---|---|---|---|---|
| 자료 등록 | prepare-planning | 업무플로우·스킬 자료·디자인 시스템·아이콘·UI 지침·스토리보드 | 자료 원장·불변 스냅샷·HTML 패턴 3안 | 자료 선택·패턴 선택 |
| 기획 생성 | init-planning | 서비스 개요·선택한 스냅샷 | 요구사항·스토리·IA·플로우·화면 기능정의·결정·상태·어노테이션 | 정확한 기획 버전 |
| 기획 수정 | revise-planning | 최신 문서·보존할 결정·수정 요청 | 범위별 수정·이전 버전 보관·폐기/대체 ID·파생물 갱신 필요 상태 | 변경 범위·수정 버전 |
| 목업 생성 | build-storyboard | 승인된 화면 기능정의·어노테이션 | 배지·설명 표가 있는 정적 HTML | 시각·기능 검토 |
| 디자인 교환 | sync-design | 승인 HTML·교환 패키지·실제 연결 도구 또는 수동 전달 | 매핑·3방향 변경/충돌/손실 리포트 | 외부 변경 채택 |
| 개발 설계 준비 | prepare-design | 승인된 기획 | 아키텍처·인프라·API 계약·입력 해시를 기록한 준비 상태 | 기술·계약 결정 |

prepare-design 이후 백엔드/프론트엔드 개발 설계로 이어진다. 기존 코드는
reverse-design → reverse-planning 순서와 코드 인용·검증기 검사를 유지한다.

## 화면 모델 결정

스토리보드는 선택적인 입력이면서 생성하는 검토 산출물이다. 기획은 사용자에게
보이는 화면 → 섹션 → 개념적 컴포넌트 → 요소 → 동작 계층을 screen-spec.md에서
소유한다. component-tree.md는 구현 단위와 FSD 구조를 소유한다. 요구사항/스토리,
IA, 플로우, 화면 기능정의의 책임은 구분한다. 화면 전이는 플로우만, 코드 실행은
구현 설계만 기술한다.

섹션/컴포넌트/요소 ID는 안정적으로 유지하고 FR/US/AC/SCR/UF, 어노테이션, 목업
배지, 외부 노드 매핑에 연결한다. 배지는 표시 번호이며 식별자가 아니다. 장식에는
기능 배지를 부여하지 않는다. page 화면은 라우트에, 오버레이와 상태 변형은 부모
page를 통해 대응한다. 로딩·빈 결과·오류·권한 상태는 정의하거나 미적용 사유를 명시한다.

이슈 010은 다른 워크플로우에서 ui-spec을 구현 명세로 통합했다. 사용자 관점의
화면 의미를 영구적으로 금지하는 결정은 아니다. 이번 워크플로우는 의미의 소유권,
구현 소유권, 파생 시각 산출물을 분리하여 원장이 중복되지 않게 한다.

## 근거와 생명주기

자료에는 유형·등록 주체·원본·버전·범위·검색 질의·선택 구간·SHA-256을 기록한다.
스냅샷 바이트와 manifest는 불변이다. 검색은 파일/구간 선택부터 시작하며 벡터 DB나
임베딩 구현을 주장하지 않는다. 스킬 첨삭은 원본·차이·승인 상태를 보존한다. 등록된
스킬/HTML/SVG는 자료이며 실행 권한이 아니다.

결정 기록은 사용자 결정·AI 제안/가정·충돌 규칙·영향 화면·미결 사항을 구분한다.
참고자료를 재선택해도 기존 결정은 자신의 snapshotId로 근거를 보존할 수 있다.
미확인 근거를 지어낸 사실로 대체하지 않는다.

단일 화면, 화면 ID를 유지하는 전체 수정, 완전 재구성, 자료 재선택의 네 모드를
구현한다. 새 버전은 현재 문서와 어노테이션을 보관한다. 삭제 ID는 폐기 상태로
유지하고 대체 관계를 명시한다. 보관본 복원은 새 검토 버전을 만들며 최신 사람의
결정을 보존한다. 승인 상태는 자동 복원하지 않는다.

상태는 draft/in-review/changes-requested/approved다. 승인은 정확한 버전을 대상으로
하며 미결 사항이 없어야 한다. 개발 설계 준비는 별도로 검토 후 designReadyVersion과
아키텍처/인프라/API 입력 해시를 기록한다. 기획 수정은 준비 상태를 해제하고 영향받는
파생물을 갱신 필요로 표시한다. 범위가 명시된 변경 없는 산출물은 생성 버전을 보존하고
verifiedForVersion에 새 버전을 기록하여 재사용한다. 기술 입력 해시가 바뀌면 prepare-design을 다시 검토하기 전까지
준비 상태는 유효하지 않다.

순/역방향 판별은 state의 mode와 생성 스킬/mode 마커를 우선한다. 기존 코드 소스
원장은 보조 근거이며 모호한 문서를 삭제하는 이유가 아니다. 순방향 기획의 자료
원장 때문에 역방향 산출물로 판별하지 않는다.

## 실행 지원

Python 3.9 이상 표준 라이브러리와 Bash만 필요하다. planning-tools.py는 snapshot,
classify, check/check-tree, freeze, revise, restore, approve, build, ready-design,
export-sync, compare-sync 명령을 제공한다. check-docs.sh는 기존 문서/링크/인용/
추적성 검사와 구조화된 검사를 함께 수행하고 보관본과 자료 스냅샷은 제외한다.
배열 로딩은 macOS Bash 3에서도 동작한다.

HTML은 Tailwind 유틸리티의 로컬 부분집합과 이스케이프한 라벨, 제한적인 CSP를
사용하며 JS/CDN이 없다. 배지와 설명 행은 같은 어노테이션에서 생성한다. 재생성은
수동 HTML 수정을 감지하고 덮어쓰지 않는다. 실제 브라우저 렌더링은 별도의 시각
검토 요구사항이다.

디자인 교환 패키지는 기준 버전·Figma 파일/노드 매핑·HTML 해시·지원 범위·손실을
보존한다. 기준/현재/외부의 3방향 비교로 시각/기능 변경, 엔티티 추가/삭제, 동시 수정
충돌을 보고한다. 돌아온 디자인은 변경 제안이며 코드 사실로 취급하거나 자동 적용하지 않는다.

## 연계 범위

BSS Sync, 자체 Figma 플러그인, 범용 HTML/CSS 변환, 임베딩 인프라, 새 웹 앱은
번들에 포함하지 않는다. 실제 연결 도구가 교환 계약으로 데이터를 정규화해야 하며
수동 파일 전달도 지원한다. 텍스트/스타일/배치/배지/어노테이션 보존과 아이콘 손실을
명시한다. 기본 exporter는 아이콘 변환을 미지원으로 보고한다. 매핑 누락·미지원·
손실이 있으면 리포트를 ready로 표시하지 않는다. 실제 Figma 왕복 성공은 연결 도구와
샘플 실행, 사람의 승인이 필요하다.

## 검증

임시 fixture로 스택 없는 유효 기획, 스냅샷 불변/변조, 고아/중복 ID, 승인 차단,
HTML 이스케이프·배지 대응, 수정 4모드, 관련 없는 화면과 사람 결정 보존, 이전 버전
보관, 폐기 ID 재사용 차단, 오래된 목업, 디자인 동시 수정, 명시적 출처 판별,
UI 없는 프로젝트, 기존/신규 검사 호환을 확인한다. 추가 실패 시나리오는 매핑/지원
범위 손실, 구조 변경, 복원, 개발 설계 준비 해시를 검증한다. 이 검사로 실제 Figma
변환이나 브라우저 시각 승인을 주장하지 않는다. 대표 HTML은 headless Chrome의
1440px·390px에서 추가로 렌더링했다. 두 폭에서 가로 넘침이 없고 배지 4개와 설명
행 4개의 대응을 확인했다. 이 시각 확인은 사용자 승인이나 실제 Figma 변환을 대신하지 않는다.
