# 이슈 공통 규약

`orca-with-gh-issue`의 세 스킬이 시작 전에 읽는다. 스킬은 이 규칙을 반복하지
않고 `규약 §N`으로 부른다. 명령은 `commands.md`의 이름(예: `PR 목록`)으로
부른다.

---

## §1. 용어와 상태

| 용어 | 뜻 |
|---|---|
| epic | `epic` 라벨 이슈. 하위 이슈를 거느리고 기획·설계·추적을 맡는다 |
| leaf | `leaf` 라벨 이슈. 하위 이슈가 없고 구현을 맡는다 |
| 종류 미정 | 두 라벨이 둘 다 없거나 둘 다 있는 이슈. 추측하지 않고 묻는다 |
| 부모 / 하위 이슈 | GitHub sub-issue 관계의 위 / 아래. 부모는 최대 하나다 |
| 최상위 이슈 | 부모가 없는 이슈 (`부모 조회`가 404) |
| 이슈 브랜치 | §3의 정규식에 맞는 브랜치 |
| 이슈 PR | head가 이슈 브랜치인 PR. 열린 PR → 없으면 가장 최근 머지된 PR. 머지 없이 닫힌 PR은 세지 않는다. 열린 PR이 둘 이상이면 묻는다 |
| 선행 이슈 | 이 이슈보다 먼저 끝나야 하는 이슈. GitHub 이슈 의존성(blocked by)으로 건다 |
| Blocked | 열린 선행 이슈가 하나 이상 있는 상태 |
| 이상 | 규칙이 예상하지 않은 관계. 상태가 아니라 보고의 `이상` 목록에 따로 적는다. 사용자가 정리하기 전까지 그 이슈는 끝나지 않은 것으로 본다 |

상태는 위에서부터 처음 맞는 하나다. epic PR 체크리스트도 이 값을 쓴다.

| 상태 | 조건 |
|---|---|
| `취소` | 닫힘, `state_reason`이 `not_planned` 또는 `duplicate` |
| `완료` | 닫힘, 그 밖의 사유(`completed`, `null` 등) |
| `머지됨` | 열림, 이슈 PR이 머지됨 (`Closes`가 빠졌던 경우) |
| `진행 중` | 이슈 PR이 열려 있음 (Draft 포함) |
| `미시작` | 위 어느 것도 아님 |

"끝났다"는 `완료` 또는 `취소`다.

## §2. 계층

1. epic은 epic과 leaf를 거느린다. leaf는 아무것도 거느리지 않는다.
2. **epic은 하위 이슈를 1개 이상 등록한 상태로만 만든다.** 근거: 나눌 계획을
   본문에만 적은 epic은 진행률도 체크리스트도 잡히지 않고, epic이 구현을
   떠안는다.
3. 부모가 될 수 있는 이슈는 열린 epic뿐이다.
4. epic은 구현 코드를 쓰지 않는다. epic PR에는 시작 커밋과 정리 작업만
   들어간다.
5. leaf가 읽어야 하는 설계 문서·API 계약은 epic PR에 두지 않는다. 설계·계약
   leaf로 만들어 먼저 머지하고, 구현 leaf는 그것을 선행 이슈로 둔다. 근거:
   epic PR은 마무리 때까지 머지되지 않아 main에서 갈라진 leaf가 볼 수 없다.
6. 부모 없는 leaf도 허용한다.
7. `이상`: 하위 이슈 0개인 epic, 하위 이슈를 거느린 leaf, 하위 이슈를 거느린
   종류 미정. 동기화와 시작 동작이 보고만 하고 고치지 않는다.

## §3. 브랜치와 PR

- **base는 언제나 기본 브랜치다.** epic·leaf, 부모 유무와 상관없다. 계층은
  sub-issue와 Orca 워크스페이스로만 나타낸다. 근거: main이 늘 최신이고
  `Closes`가 동작한다. 대가로 epic 단위 일괄 반영은 없으니, 미완성 기능을
  숨겨야 하면 leaf에서 기능 플래그를 쓴다.
- 브랜치 이름: `<type>/issue<N>-<slug>`
  - `<type>`: 제목이 `fix`·`docs`로 시작하면 그 값 → `bug` 라벨이면 `fix` →
    `documentation` 라벨이면 `docs` → 그 밖에는 `feat`
  - `<slug>`: 제목을 영어 소문자 kebab-case 2~5단어로. 미리보기에서 보여 준다
- Orca는 `--name`을 브랜치로 바꿀 때 사용자 접두사를 붙이고 `/`·한글·기호를
  `-`로 바꾸거나 지운다(`feat/issue61-login` → `<사용자>/feat-issue61-login`).
  그래서 이슈 브랜치는 정규식 `(^|[/-])issue<N>-`로 찾는다.
- 시작 = Draft PR. 빈 커밋 `chore: start #<N>`으로 연다(base와 차이가 없으면
  PR을 열 수 없다). 작업 계획은 PR 본문에 쓴다.
- PR 본문 첫 줄은 `Closes #<N>`이다.

## §4. 선행과 Blocked

1. 선행 이슈는 부모와 상관없이, 실제로 막으면 건다(§7의 4). 부모가 다른 선행도
   묻지 않는다. 근거: 한 기능을 하위 epic으로 나누면 epic 사이에 실제로 막는
   선행이 생기고, Blocked 판정은 이슈마다 `선행 목록`으로 하므로(이 절의 3)
   부모가 달라도 그대로 동작한다.
   - **다른 부모의 선행**(선행 이슈의 부모가 이 이슈의 부모와 다르거나, 한쪽만
     최상위인 경우)은 보고에서 따로 적는다. 그 선행이 닫혀도 이 이슈의
     `blocked` 해제는 이 이슈 쪽 epic의 동기화나 시작에서만 일어나므로(이 절의 4),
     어느 epic의 동기화를 돌려야 풀리는지 보이게 한다.
2. 선행을 걸 때 선행 이슈가 열려 있으면 `blocked` 라벨도 단다.
3. 판정은 항상 `선행 목록`으로 한다. 라벨은 표시일 뿐이다.
4. 열린 선행이 없는데 `blocked` 라벨이 남아 있으면 뗀다. 해제는 epic
   동기화와 시작 동작에서만 일어난다(이벤트 트리거가 없다).
5. Blocked인 이슈는 시작하지 않는다.

## §5. epic 추적과 마무리

### 체크리스트

epic PR 본문의 표식 사이만 다시 쓴다.

```markdown
<!-- SUBISSUES:START -->
| | 이슈 | 종류 | 상태 | 담당 | 선행 |
|---|---|---|---|---|---|
| [x] | #60 상태 전이 계약 | leaf | 완료 | @bob | — |
| [ ] | #61 주문 취소 API | leaf | 진행 중 | @alice | #60 |
| [ ] | #62 주문 취소 화면 | leaf | 미시작 | — | #61 (Blocked) |
<!-- SUBISSUES:END -->
```

`[x]`는 끝난 이슈. `선행` 열은 열린 선행이면 `#번호 (Blocked)`, 닫힌 선행이면
번호만, 없으면 `—`.

epic 이슈 본문의 `SUBISSUE-PLAN` 표식 사이는 하위 이슈 계획(순서·이슈·내용·
선행)이다. epic 생성·하위 이슈 추가·leaf 생성이 행을 붙인다. 상태는 적지
않는다.

### 동기화 순서

1. 하위 이슈마다 상태를 매긴다.
2. `머지됨`이고 PR base가 기본 브랜치면 닫는다(`completed`). base가 다르면
   닫지 않고 `이상`.
3. 2가 끝난 뒤 Blocked를 다시 판정해 라벨을 붙이거나 뗀다. 근거: 2에서 닫힌
   이슈가 다른 이슈를 풀 수 있다.
4. 체크리스트를 다시 쓴다.
5. §2의 7 `이상`을 확인해 보고한다.

### 마무리

1. 동기화를 먼저 한다.
2. 끝나지 않은 하위 이슈(`이상` 포함)가 있으면 멈춘다.
3. epic 수용 기준마다 `충족`(근거: 하위 이슈 번호와 그 PR이 바꾼 파일) /
   `미충족` / `판단 불가`를 매기고 묻는다: 정리 작업 후 머지 / 정리 작업 없이
   끝내기 / 새 leaf로 분리 / 중단.
4. 정리 작업은 승인한 `미충족` 항목만 한다. 새 기능이 필요하면 새 leaf로 뺀다.
5. 정리 작업 없이 끝내기: epic 브랜치에 시작 커밋 말고 변경이 없으면 epic PR을
   닫고 epic 이슈를 `completed`로 닫는다(`not_planned`면 부모 동기화가
   `취소`로 본다). 변경이 있으면 닫으면 사라지므로 머지할지 묻는다.

## §6. 규모

`## 수용 기준`(또는 기존 이슈의 `## Acceptance Criteria`) 아래 체크박스
개수로 정한다.

| 개수 | 라벨 |
|---|---|
| 1 | `size/XS` |
| 2 | `size/S` |
| 3–4 | `size/M` |
| 5–6 | `size/L` |
| 7 이상 | leaf 불가 — epic으로 나눈다 |

- 0개면 크기를 정할 수 없다. 수용 기준을 지어내지 않고 받는다.
- epic 크기 라벨은 사용자가 지정할 때만 `size/XL`·`size/XXL`을 단다.
- 수치는 기본값이다(이슈 #53, 2026-10-16). 고칠 때는 이 표만 고친다.

## §7. 나누기 기준

epic의 하위 이슈 계획을 세우거나 제안할 때 쓴다. 사용자가 다르게 정하면 그
결정을 epic 본문 `## 나눈 기준`에 적는다.

1. 유스케이스·저장소(테이블)·승인 항목이 다르면 나눈다.
2. 공유하는 설계·계약이 있으면 그것을 첫 leaf로 두고 구현 leaf가 선행으로 건다.
3. 백엔드와 프론트엔드는 다른 leaf로 둔다.
4. 선행은 실제로 막는 것만 건다. 근거: 넘치면 Blocked가 늘어 병렬 진행이 막힌다.
5. leaf 하나가 §6 상한을 넘으면 하위 epic으로 만든다.
6. 이 기준으로 정할 수 없으면 지어내지 않고 묻는다.

## §8. 제목

| 종류 | 형식 | 예 |
|---|---|---|
| epic | `epic: <끝나면 되는 상태>` | `epic: 주문 취소와 부분 환불을 지원한다` |
| leaf | `<type>(<scope>): <할 일>` + 필요하면 ` — <BE/FE>` | `feat(order): 주문 취소 API를 구현한다 — BE` |

`<scope>`는 근거가 없으면 생략한다. 이미 있는 이슈 제목은 고치지 않는다.

## §10. 진입 조건 · 확인 · 실패

### 진입 조건 (모든 스킬의 Step 0)

1. **GitHub 원격이 있는 git 저장소인가** — `저장소 조회`. 아니면 멈춘다.
2. **쓰기 권한이 있는가** — `쓰기 권한`. GitHub에 쓰는 스킬(`issue-epic`,
   `issue-leaf`)만 확인한다. `false`면 아무것도 쓰지 않고 멈춘다.

   > "활성 gh 계정 `<계정>`에 쓰기 권한이 없습니다. `! gh auth switch -u <계정>`으로 바꾼 뒤 다시 실행하세요. 로그인된 계정: <목록>"

   스킬이 계정을 바꾸지 않는다.
3. 원격 정보는 매번 다시 조회한다. 대화에 남은 이전 결과를 쓰지 않는다.

라벨 점검은 쓸 라벨이 정해진 뒤, 첫 쓰기 확인 앞에서 한다. 없으면 §9의 색으로
만들지 묻는다.

### 확인

묻는 곳은 스킬 본문에 `> "…"` 인용으로 적혀 있다. 그곳에서는 반드시 멈추고
답을 기다린다. 선택지가 있으면 권장안에 `(권장)`과 한 줄 근거를 붙인다.

- **묻는다**: 이슈 생성(미리보기), Draft PR 열기(미리보기), 라벨 생성,
  동기화 변경 묶음(한 번에), 머지·머지 방식, 마무리 판정, 워크스페이스 생성,
  규칙에 없는 경우의 기본값
- **묻지 않는다**: 조회, 승인받은 내용을 그대로 쓰는 것(그 뒤의 연결·의존성·
  담당 지정 포함), Blocked 해제에 따른 `blocked` 라벨 떼기

### 실패

1. 명령이 실패하면 같은 명령을 한 번만 다시 실행한다. 또 실패하면 명령과
   오류를 보고하고 멈춘다.
2. 여러 쓰기 중간에 멈추면 이미 한 쓰기(만든 이슈, 라벨, 의존성)를 모두
   보고한다. 되돌리지 않는다.
3. 우회하지 않는다:
   - sub-issue·의존성 API가 실패했다고 본문에 "부모: #N"만 적고 넘어가기 —
     동기화가 API로 판정하므로 관계가 사라진다
   - `--admin` 머지, force push, `--no-verify`
   - Blocked인 이슈에서 라벨만 떼고 시작하기
