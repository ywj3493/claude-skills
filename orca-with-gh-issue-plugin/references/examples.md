# 이슈 예시

`issue-epic`과 `issue-leaf`가 이슈 본문을 쓰기 전에 읽는다. 형식과 분량의
기준이다. 내용은 지어낸 예(가상의 쇼핑몰 저장소)이므로 실제 이슈에 그대로
옮기지 않는다. 실제 이슈의 내용은 항상 사용자가 준 정보와 저장소에서 확인한
사실로 쓴다.

여러 실제 저장소의 이슈를 살펴보고 잘 굴러간 epic의 공통점을 뽑았다.

- 하위 이슈를 sub-issue로 등록했다. 그래서 진행률이 저절로 잡혔다.
- 하위 이슈 표에 선행 관계를 적었다.
- 나눈 기준을 남겼다.
- 범위 밖을 적었다.

잘 굴러가지 않은 epic에서는 다음 문제가 반복됐다.

- 나눌 계획을 체크박스로만 적고 하위 이슈를 등록하지 않았다.
- 구현 이슈가 커져서 epic 라벨 없이 하위 이슈를 거느렸다.

---

## 예 1 — epic (하위 이슈 4개, 계약 먼저)

제목: `epic: 주문 취소와 부분 환불을 지원한다`
라벨: `epic`

```markdown
## 요약

주문 상세에서 주문 전체 취소와 상품별 부분 환불을 할 수 있게 한다. 결제
게이트웨이 환불 호출, 재고 복원, 관리자·고객 화면이 함께 바뀌어 한 PR로
끝나지 않으므로 epic으로 나눈다.

## 배경

- 지금은 고객센터가 결제사 콘솔에서 직접 환불하고, 재고는 수동으로 맞춘다
- 주문 상태는 `docs/order/state-machine.md`의 5개 상태뿐이며 `CANCELLED`·
  `PARTIALLY_REFUNDED`가 없다
- 결제사 환불 API는 부분 금액을 지원한다(`docs/payments/gateway.md` §4)

## 수용 기준

- [ ] 고객이 배송 전 주문을 취소하면 결제 취소와 재고 복원이 한 번에 끝난다
- [ ] 관리자가 상품별 부분 환불을 하면 주문 상태와 정산 금액이 맞게 바뀐다
- [ ] 하위 이슈가 모두 닫힘

## 하위 이슈

<!-- SUBISSUE-PLAN:START -->
| 순서 | 이슈 | 내용 | 선행 |
|---|---|---|---|
| 1 | #121 | 취소·환불 상태 전이 설계와 API 계약 | — |
| 2 | #122 | 취소·부분 환불 BE (결제 환불, 재고 복원) | #121 |
| 3 | #123 | 고객 주문 상세 취소 FE | #121 |
| 4 | #124 | 관리자 부분 환불 FE | #121 |
<!-- SUBISSUE-PLAN:END -->

## 나눈 기준

- 설계·계약을 먼저 머지하고 BE·FE는 그 계약에 맞춰 함께 진행한다(규약 §7의 2)
- 고객 취소와 관리자 부분 환불은 화면과 권한이 달라 FE를 둘로 나눴다(§7의 1)
- FE 두 개는 서로 막지 않으므로 선행을 걸지 않았다(§7의 4)

## 범위 밖

- 배송 후 반품 회수 — #130 epic에서 다룬다
- 정산 리포트 화면 변경 — 없음(기존 리포트가 상태를 그대로 읽는다)

## 관련

- 연계: #98 (결제사 SDK 업그레이드)
```

## 예 2 — 설계·계약 leaf (다른 leaf의 선행)

제목: `docs(order): 주문 취소·부분 환불의 상태 전이와 API 계약을 정한다`
라벨: `leaf`, `size/M`

```markdown
## 요약

epic #120의 설계·계약 단계다. 취소·부분 환불의 상태 전이와 API 계약을
머지해, BE·FE leaf가 서로 기다리지 않고 진행할 수 있게 한다.

## 배경

- 현재 상태 머신: `docs/order/state-machine.md`
- 결제사 환불 API: `docs/payments/gateway.md` §4 (부분 금액 지원)

## 수용 기준

- [ ] `CANCELLED`·`PARTIALLY_REFUNDED` 전이와 금지 전이가 상태 머신 문서에 있다
- [ ] `POST /orders/{id}/cancel`, `POST /orders/{id}/refunds` 요청·응답·오류 계약이 OpenAPI에 있다
- [ ] 재고 복원 시점(취소 즉시 / 환불 확정 후)이 결정으로 기록돼 있다
- [ ] DoD: API 스냅샷 테스트 통과

## 작업

1. 상태 전이 표 갱신
2. OpenAPI 계약 추가 (본문은 501)
3. 재고 복원 시점 결정 — 착수 때 선택지를 제시하고 사용자 결정을 받는다

## 범위 밖

- 구현 — #122(BE), #123·#124(FE)

## 관련

- 상위: #120
- 후속: #122 · #123 · #124
```

## 예 3 — 구현 leaf (선행 있음, Blocked로 시작)

제목: `feat(order): 주문 취소와 부분 환불을 구현한다 — BE`
라벨: `leaf`, `size/M`, `blocked` (#121이 열려 있는 동안)

```markdown
## 요약

epic #120의 BE 단계다. #121에서 머지한 계약의 본문을 채운다.

## 배경

- 계약: #121이 정한 `POST /orders/{id}/cancel`·`/refunds`
- 결제사 환불 클라이언트는 `payments/gateway_client.py`에 있고 부분 금액 인자가 없다

## 수용 기준

- [ ] 배송 전 주문 취소 시 결제 취소와 재고 복원이 한 트랜잭션 경계 안에서 끝난다
- [ ] 부분 환불 합계가 결제 금액을 넘으면 409를 돌려준다
- [ ] 결제사 호출 실패 시 주문 상태가 바뀌지 않는다
- [ ] DoD: 단위·통합 테스트 통과, API 스냅샷 변경 없음

## 작업

1. 상태 전이 도메인 로직
2. 결제사 클라이언트 부분 환불 인자 추가
3. 재고 복원
4. 통합 테스트

## 범위 밖

- 화면 — #123 · #124

## 관련

- 상위: #120
- 선행: #121
- 연계: #123 · #124 (같은 기능의 FE)
```

## 하지 말 것 (실제로 본 문제)

| 문제 | 왜 문제인가 | 이 플러그인의 처리 |
|---|---|---|
| epic 본문에 "계약 → BE → FE로 나눈다"를 체크박스로만 적고 하위 이슈를 만들지 않음 | 진행률·체크리스트가 잡히지 않고 epic이 구현을 떠안는다 | epic 생성이 하위 이슈 등록까지 한 묶음이다(규약 §2의 2) |
| 구현 이슈가 커져 epic 라벨 없이 하위 이슈를 거느림 | 그 이슈가 구현인지 추적인지 알 수 없다 | 동기화가 `이상`으로 보고하고 epic 전환을 권한다(규약 §2의 7) |
| "먼저 하면 좋은" 순서까지 선행 이슈로 걸음 | Blocked가 늘어 병렬 진행이 막힌다 | 실제로 막는 것만 건다(규약 §7의 4) |
