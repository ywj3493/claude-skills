## 개요

epic은 큰 기능의 기획·설계와 추적을 맡는다. 구현은 하위 leaf가 하고, 각 leaf는
main에 바로 머지된다. epic PR에는 시작 커밋과 마무리 때의 정리 작업만 들어간다.

시작 전에 읽는다:

- `${CLAUDE_PLUGIN_ROOT}/references/issue-rules.md` (이하 `규약`)
- `${CLAUDE_PLUGIN_ROOT}/references/commands.md` — 아래 `이슈 생성` 같은 이름이 여기 있다
- 본문을 쓸 때만: `${CLAUDE_PLUGIN_ROOT}/references/examples.md`,
  `${CLAUDE_PLUGIN_ROOT}/templates/epic-issue.md` · `leaf-issue.md` · `epic-pr.md`

---

## 절대 금지

- **하위 이슈 없이 epic을 만들지 않는다.** 하위 이슈를 등록하지 못하면 생성이
  끝나지 않은 것이다(규약 §2의 2)
- epic PR에 구현 코드를 넣지 않는다
- 끝나지 않은 하위 이슈가 있으면 epic PR을 머지하거나 닫지 않는다
- 확인 없이 머지하지 않는다. `--admin`, force push, `--no-verify`를 쓰지 않는다
- 수용 기준과 하위 이슈 계획을 지어내지 않는다. 제안은 "제안"으로 표시해 승인받는다

---

## Step 0: 진입 조건과 동작 고르기

1. 규약 §10의 진입 조건을 확인한다
2. 요청을 아래 다섯 동작 중 하나로 정한다. 둘 이상이면 표 순서대로 잇는다.
   모르겠으면 다섯 가지를 보여 주고 묻는다

| 동작 | 요청 예 |
|---|---|
| 생성 | "epic 만들어줘", "#40 아래에 epic" |
| 하위 이슈 추가 | "#60에 하위 이슈 추가", "이 이슈들을 #60 아래로" |
| 시작 | "epic #60 시작" |
| 동기화 | "진행 상황 갱신", "체크리스트 업데이트" |
| 마무리 | "epic 마무리" |

epic 번호가 없으면 `현재 워크스페이스`의 `linkedIssue`를 후보로 묻는다.

## 생성

### Step 1: 입력과 하위 이슈 계획

받는다: 제목(규약 §8), 요약, 배경, 수용 기준, **하위 이슈 계획**. 선택: 상위
epic, 선행 이슈, 크기(`size/XL`·`size/XXL`).

계획의 행은 둘 중 하나다.

- **새 leaf** — 제목(규약 §8), 요약 한 줄, 수용 기준 1개 이상, 선행(계획 안의
  행 또는 기존 이슈). 크기는 규약 §6
- **기존 이슈** — 번호. 열려 있고 다른 부모가 없어야 한다(`이슈 조회`,
  `부모 조회`). 다른 부모가 있으면 옮길지 묻는다

계획을 받지 못했으면 규약 §7로 만들어 "제안"으로 표시한다. 행이 0개면 epic을
만들지 않는다. 한 행이 규약 §6 상한을 넘으면 묻는다.

> "<행 제목>은 수용 기준이 <n>개라 leaf 상한을 넘습니다. 1. 행을 나눈다 (권장) 2. 이 epic을 만든 뒤 하위 epic으로 따로 만든다"

### Step 2: 관계 확인

- 상위 epic: `이슈 조회`로 열린 epic인지 본다. 아니면 멈춘다
- 선행: 규약 §4의 1. 계획 안의 행끼리는 같은 부모(이 epic)이고, 계획 밖 이슈(다른
  epic의 하위 이슈 등)도 실제로 막으면 선행으로 건다. 그런 행은 미리보기에
  다른 부모의 선행으로 표시한다

### Step 3: 본문 작성

`examples.md`로 형식과 분량을 맞추고 내용은 옮기지 않는다.

- epic 본문(`epic-issue.md`) — 하위 이슈 표의 번호는 아직 없으므로 `(생성 후)`
- 새 leaf 본문(`leaf-issue.md`) — 요약의 epic 번호는 `#<EPIC>`으로 둔다

라벨 점검을 여기서 한다(규약 §10).

### Step 4: 미리보기

epic의 제목·본문·라벨·상위·선행과, 계획 표(새 leaf/기존 이슈, 제목, 크기,
수용 기준, 선행, Blocked 여부)를 한 번에 보여 준다.

> "epic 1개를 만들고 하위 이슈 <n>개(새 leaf <a>, 기존 <b>)를 등록할까요?"

### Step 5: 쓰기

순서를 지킨다 — 뒤 단계가 앞 단계의 번호와 id를 쓴다.

1. `이슈 생성` (라벨 `epic` + 지정한 크기) → epic 번호
2. 상위 epic에 `하위 이슈 연결`, epic의 `선행 지정`
3. 새 leaf마다 `#<EPIC>`을 바꿔 `이슈 생성` (라벨 `leaf` + `size/*`)
4. 모든 행을 epic에 `하위 이슈 연결`
5. 행의 `선행 지정`. 선행이 열려 있으면 `blocked`
6. epic 본문의 `SUBISSUE-PLAN` 표를 실제 번호로 `이슈 본문 갱신`

중간에 멈추면 규약 §10대로 한 쓰기를 모두 보고한다. 하위 이슈가 하나도 연결되지
않았으면 "epic #<E>는 하위 이슈가 없는 `이상` 상태입니다. `하위 이슈 추가`로
이어서 하세요"를 덧붙인다.

다음 단계 안내: `issue-orca-worktree` → 이 스킬의 `시작`. 선행 없는 leaf(대개
설계·계약)부터 시작한다.

## 하위 이슈 추가

생성 Step 1(계획 행만)·Step 2·Step 3, Step 5의 3~6과 같다. 다른 점:

- epic은 `이슈 조회`로 열린 epic인지 먼저 본다
- 선행에 이 epic의 기존 하위 이슈를 쓸 수 있다
- `SUBISSUE-PLAN` 표는 기존 행 뒤에 붙인다. 표식이 없으면(플러그인 밖에서 만든
  epic) 본문을 고치지 않고 보고에 적는다

> "epic #<E>에 하위 이슈 <n>개(새 leaf <a>, 기존 <b>)를 등록할까요?"

epic PR이 열려 있으면 `동기화`를 안내한다.

---

## 시작

1. **이슈 확인** — `이슈 조회`. 열린 epic이 아니면 멈춘다. `하위 이슈 목록`이
   0개면 묻는다

   > "epic #<N>에 하위 이슈가 없습니다. 1. `하위 이슈 추가`부터 한다 (권장 — 진행이 추적되지 않는다) 2. 그대로 시작한다"

2. **Blocked 확인** — `선행 목록`. 열린 선행이 있으면 목록을 보고하고 멈춘다.
   없는데 `blocked`가 있으면 뗀다
3. **이미 시작했는가** — `PR 목록`. 열린 이슈 PR이 있으면 보고하고 멈춘다.
   머지된 이슈 PR만 있으면 묻는다

   > "#<N>의 이슈 PR #<P>가 이미 머지됐습니다. 1. 중단 (권장) 2. 새 Draft PR을 연다"

4. **브랜치 확인** — 현재 브랜치가 이슈 브랜치가 아니면 묻는다

   > "현재 브랜치 `<브랜치>`는 #<N>의 이슈 브랜치가 아닙니다. 1. `issue-orca-worktree`로 워크스페이스를 만들고 거기서 다시 시작 (권장 — 이슈마다 워크스페이스 하나) 2. 여기서 `<type>/issue<N>-<slug>`를 새로 만든다"

5. **PR 본문** — `epic-pr.md`. 계획은 이슈의 수용 기준과 하위 이슈 계획을
   바탕으로 쓰고 범위를 더하지 않는다. 체크리스트는 동기화 1과 같이 채운다
6. **미리보기**

   > "빈 커밋 `chore: start #<N>`을 push하고 위 본문으로 Draft PR(base `<기본 브랜치>`)을 열까요?"

7. `Draft PR 열기` → `담당 지정`

---

## 동기화

이 epic의 직계 하위 이슈만 본다.

1. **상태 판정** — `하위 이슈 목록`, `PR 목록`(한 번), 이슈마다 `선행 목록`.
   규약 §1의 상태를 매기고 규약 §2의 7 `이상`을 모은다. 선행 중 다른 부모의
   선행(규약 §4의 1)을 모은다. epic PR이 없으면
   체크리스트는 빼고 나머지만 한다
2. **변경 묶음** — 닫을 이슈(`머지됨` 중 `이상`이 아닌 것), 붙이거나 뗄
   `blocked`(닫을 이슈가 닫힌 것으로 보고 계산), 바뀐 체크리스트
3. 변경이 없으면 "변경 없음"과 상태 표를 보고하고 끝낸다
4. **확인**

   > "이슈 닫기 <n>건, 라벨 <n>건, 체크리스트 갱신을 적용할까요?"

5. **적용** — `이슈 닫기` → `blocked` 변경 → `PR 본문 읽기 / 쓰기`(표식 사이만).
   라벨을 바꾸기 직전 `선행 목록`을 다시 보고, 승인 뒤 상황이 바뀐 항목은
   적용하지 않고 보고한다

---

## 마무리

1. `동기화`를 끝까지 한다. 거절되면 마무리도 멈춘다
2. 끝나지 않은 하위 이슈가 있으면 목록을 보고하고 멈춘다
3. **점검** — epic 수용 기준마다 `충족` / `미충족` / `판단 불가`. 근거는 끝난
   하위 이슈와 그 이슈 PR의 `PR 파일`. 근거를 대지 못하면 `판단 불가`.
   `미충족`이 없으면 2를, 있으면 크기에 따라 1 또는 3을 권장한다

   > "어떻게 마무리할까요? 1. 정리 작업 후 머지 2. 정리 작업 없이 끝내기 3. `미충족`을 새 leaf로 분리 4. 중단"

4. **정리 작업 후 머지**
   - 현재 브랜치가 epic PR의 head가 아니면 epic 워크스페이스 경로를 알려 주고 멈춘다
   - 승인한 `미충족` 항목만 고친다
   - 저장소의 테스트·린트를 돌린다. 실패하면 고쳐서 다시 돌리되 **2번까지**.
     그래도 실패하면 보고하고 멈춘다. 테스트 삭제, 단언 약화, 훅 건너뛰기로
     통과시키지 않는다
   - 저장소 커밋 규칙으로 커밋·push하고, PR 본문 `## 마무리 기록`에 점검표와
     한 일을 적는다 → 6
5. **정리 작업 없이 끝내기** — `## 마무리 기록`에 점검표를 적고 `epic 변경 범위`를 본다
   - 시작 커밋뿐이면:

     > "epic PR #<P>를 닫고 epic #<N>을 `completed`로 닫을까요? leaf의 변경은 이미 main에 있습니다."

     승인하면 `PR 닫기` → `이슈 닫기` → 7
   - 다른 커밋이 있으면 목록을 보여 주고 6으로 간다
6. **머지** — `PR 상태`가 `CONFLICTING`이면 멈춘다. `머지 방식`에서 허용된 것이
   하나면 그것만 적는다

   > "epic PR #<P>를 `<기본 브랜치>`에 머지할까요? 1. `--squash` (권장 — 시작 커밋과 정리 작업이 커밋 하나로 남는다) 2. `--merge` 3. `--rebase` 4. 중단"

   `PR 머지`. `Closes`가 epic을 닫는다
7. 부모 epic이 있으면 그 epic의 `동기화`를 안내한다

## 보고

실제로 실행해 확인한 것만 적는다.

```markdown
## issue-epic <동작> 결과

- epic: #<N> <제목> (<URL>)
- 한 일: <만든 이슈, 연결, 라벨, PR, 닫은 이슈, 머지>
- 하지 않은 일: <멈춘 곳과 이유. 없으면 생략>
- 하위 이슈: <동기화·마무리면 체크리스트 표>
- 이상: <목록과 정리 방법. 없으면 생략>
- 다른 부모의 선행: <하위 이슈 ← #번호 (부모 #P) 목록. 없으면 생략>
- 다음 단계: <한 줄>
```
