# 프론트엔드 공통 규약

`init-design-frontend`와 `reverse-design-frontend`가 로드한다.
`${CLAUDE_PLUGIN_ROOT}/references/common-rules.md`와 함께 쓴다.

---

## 1. 프레임워크 중립

**React를 가정하지 않는다.** 문서와 사고에 쓰는 어휘는 일반 명칭이다:
"UI 단위", "라우트", "렌더링 모드", "상태 저장소", "데이터 조회 단위",
"로딩·오류 경계". React·Vue·Svelte·Angular 어느 것이든 이 어휘로 기술된다.

구체 프레임워크·라이브러리 이름은 `architecture.md`의 스택 표에서 읽어
쓰되, **설계 판단에 그 프레임워크의 관례를 끌어들이지 않는다.**

---

## 2. FSD 기준선

레이어는 여섯 개다.

```text
app → pages → widgets → features → entities → shared
```

| 레이어 | 담는 것 |
|---|---|
| `app` | 진입점, 전역 프로바이더, 라우터 설정 |
| `pages` | 라우트 단위 화면 조립 |
| `widgets` | 재사용 가능한 화면 블록 |
| `features` | 사용자 행동 단위 |
| `entities` | 도메인 개체와 그 표현 |
| `shared` | 도메인 무관 공용 코드 |

레이어 안은 **슬라이스**(도메인 단위)로, 슬라이스 안은 **세그먼트**(`ui`,
`model`, `api`, `lib`, `config`)로 나뉜다.

**의존 규칙**: 상위 레이어만 하위 레이어를 참조한다. 같은 레이어의 다른
슬라이스는 참조하지 않는다. 공유가 필요하면 하위 레이어로 내린다.

### 순방향과 역방향에서의 지위

| 방향 | FSD의 역할 |
|---|---|
| 순방향 (`init-design-frontend`) | **기본값**. 사용자가 다른 구조를 고르지 않는 한 이대로 설계한다 |
| 역방향 (`reverse-design-frontend`) | **대조 기준**. 기존 코드를 기술하는 것이지 FSD로 리팩터링하자고 제안하는 것이 아니다. 따르지 않으면 실제 구조를 기록하고 대비표만 붙인다 |

## 3. 문서 간 책임 경계

**이 경계를 어기면 두 문서가 같은 내용을 서로 참조하며 반복한다.**

| 무엇 | 어느 문서 |
|---|---|
| 무엇이 무엇을 담는가 (구조) | `component-tree.md` |
| 언제 그려지고 무엇을 조회하는가 | `render-flow.md` |
| **지역 상태와 재렌더 유발 요인** | `render-flow.md` |
| **공유·전역 상태, 서버 캐시** | `state-flow.md` |
| 어떤 주소가 어떤 화면으로 가는가 (라우트 정의와 접근 제어) | `routing.md` |
| 사용자가 화면 사이를 어떻게 지나가는가 (여정) | `../../planning/user-flows.md` — **기획 소유** |
| 어떤 화면이 있고 어떻게 묶이는가 | `../../planning/information-architecture.md` — **기획 소유** |

마지막 두 문서는 **읽기만 한다.** 설계 스킬은 유저 플로우와 정보 구조를
만들지도 고치지도 않는다. 두 계층의 접점은 `routing.md`의 `대응 화면` 열
하나다 — 기획의 `SCR-` 키에 실제 라우트를 대응시킨다.

지역/공유의 경계는 **"그 라우트를 벗어나도 살아 있는가"**다. 역방향에서는
`render-flow-tracer`가 반환한 `state` 항목의 `scope` 값이 이 배분을
결정한다: `local`은 `render-flow.md`, `shared`와 `server`는
`state-flow.md`. 에이전트가 판단을 `unresolved`로 남긴 상태는 임의로
배분하지 말고 미해결 항목에 둔다.

## 4. 프론트엔드 고유 규칙

1. **기획의 모든 화면이 라우트를 가져야 한다.** `routing.md`의 `대응 화면`
   열을 채우고, `information-architecture.md`에 있는데 라우트가 없는 `SCR-`은
   `traceability.md`의 미연결 항목으로 내린다. 유저 플로우 자체의 작성 규칙은
   `planning-rules.md` §5가 소유한다.
2. **앱 셸은 한 번만 기술한다.** 라우트마다 다시 추적하면 N개의 동일한
   추적이 생기고 곧 서로 어긋난다. 다른 도메인 문서에 이미 앱 셸이 있으면
   링크만 하고 반복하지 않는다.
3. **라우트 목록의 `관련 스토리` 열을 반드시 채운다.** 어느 스토리와도
   연결되지 않는 라우트는 `traceability.md`의 미연결 항목으로 내린다.
4. **접근 제어 표에서 공개 라우트도 "인증 불필요"로 명시한다.** 빈 칸은
   미확인과 구분되지 않는다. 권한 이름은 `api-interface.md`의 인가 표와
   일치해야 한다.
5. **서버 상태의 `무효화 계기`를 반드시 채운다.** 이것이 없으면 "왜 화면이
   갱신되지 않는가"를 설명할 수 없다. `캐시 키`는 `render-flow.md`의 데이터
   조회 표와 일치해야 한다.
6. **FSD 레이어 표에서 이 도메인이 쓰지 않는 레이어의 행을 지우지 않는다.**
   경로를 `—`로 두고 비고에 사유를 적는다 — 왜 안 쓰는지가 정보다.
