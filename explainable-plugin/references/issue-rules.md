# 로컬 이슈 규약

`issue-local`이 관리 규칙으로 읽고, `issue-orca-worktree`는 §1·§2의 읽기 계약만
사용한다. `orca-with-gh-issue` #53의 epic/leaf 방식을 차용했지만 해당 플러그인,
GitHub, Orca 설치에 의존하지 않는다.

## §1. 원본 경로와 식별자

- 원본은 `docs/<source_language>/issue/`다. 언어는 `common-rules.md` §1.1로
  감지하되, `specifications/` 외에 기존 `issue/`도 후보로 본다. 경로가 없으면
  한국어 기본 경로 `docs/ko/issue/` 또는 사용자 경로를 물어 확정한 뒤 만든다.
- git 저장소에서는 먼저 `local-issues.py locate --repo <checkout>`을 실행한다.
  등록되어 있으면 반환된 절대 경로가 모든 워크트리의 원본이다. 등록 전에는
  현재 checkout의 위 경로를 후보로 보이고 `register --repo <checkout> --root
  <절대 이슈 경로>`로 선택을 기록한다. 기존 등록은 자동 교체하지 않는다.
  등록 파일은 git common directory의 `explainable-issue-store.json`이며 git에
  커밋하지 않는다. git이 없으면 사용자가 확정한 경로에 `--root`로 직접 접근한다.
- 등록된 경로가 사라졌으면 빈 저장소를 새로 만들지 않고 복구 또는 경로 재선택을
  요청한다. 재선택 승인 시에만 기존 등록 파일을 교체한다. 워크트리 삭제 전에는
  원본 문서와 등록 경로를 보존·이전해야 한다는 점을 안내한다.
- 작업 중인 checkout의 이슈 사본은 원본으로 덮어쓰거나 원본과 자동 병합하지
  않는다. 원본이 다른 checkout에 있으면 쓸 절대 경로를 작업 전에 알린다.
- ID는 양의 순번 `issue001` … `issue999`, `issue1000`이다. 파일은 같은 ID의
  `.md`다. 원문과 번역은 같은 ID이며 번역은 별도 이슈가 아니다.
- `next-id --root <경로>`는 원본의 모든 `issueNNN.md`(기존 형식 포함)를 세어
  후보를 반환한다. 예약이 아니다. 생성은 §5의 잠금과 배타적 파일 생성을 쓴다.
  충돌하면 새 번호 후보와 바뀔 참조를 보여 주고 기다린다. 덮어쓰지 않는다.

## §2. 파일 계약

새 문서는 `templates/issue/epic.md` 또는 `leaf.md`를 채운다. frontmatter는
YAML의 부분집합으로 **각 값은 JSON 표기**다. 별도 YAML 패키지 없이 읽기 위한
계약이며 임의 YAML 태그·주석·다중 행 값을 사용하지 않는다.

```yaml
---
id: "issue012"
type: "leaf"
status: "Open"
parent: "issue011"
blocked_by: []
size: "S"
---
```

| 필드 | 값 / 의미 |
|---|---|
| `id` | 파일명과 같은 ID |
| `type` | `epic` 또는 `leaf` |
| `status` | `Open`, `In Progress`, `Done`, `Cancelled` |
| `parent` | 부모 ID 또는 `null`. 관계의 원본 |
| `blocked_by` | 선행 ID 배열. 없으면 `[]`. 관계의 원본 |
| `size` | leaf는 `XS`/`S`/`M`/`L`, epic은 `null` 또는 사용자가 지정한 `XL`/`XXL` |

본문은 제목·요약과 `배경`, `수용 기준`, `작업`, `기록`을 가진다. 원문 언어가
영어면 `Background`, `Acceptance Criteria`, `Tasks`, `Notes`다. 수용 기준과
작업은 체크리스트로 쓴다. `기록`에는 결정, 상태 전이, 완료 근거를 적는다.
업무 정보가 없으면 사용자에게 받고, 범위·수용 기준을 제안했다면 제안임을
표시해 확정받는다. 빈 필수 절을 지어낸 내용으로 채우지 않는다.

앞머리가 없는 기존 문서는 `legacy`이며 번호만 예약한다. 종류·부모·상태를
추론하지 않는다. 기존 문서를 쓰거나 관계로 연결하려면 원문을 보존하면서
필수 필드를 사용자와 확정해 먼저 이 형식으로 전환한다. 앞머리가 있지만
형식이 잘못된 문서는 오류다. 누락된 필드를 기본값으로 채워 진행하지 않는다.

번역은 `docs/config.yml`의 `translation_languages`에 있는 언어만 만든다.
설정이 없으면 미러를 만들지 않는다. 등록 원본의 `docs/<source>/issue/`에
대응하는 `docs/<translation>/issue/`에 같은 파일명으로 쓰고, frontmatter·ID·
체크박스 상태·관계는 원문과 같게 유지한다. 커스텀 원본 경로에서 미러 경로를
결정할 수 없으면 경로를 묻는다. 이슈 미러는 `issue-local`이 관리한다.

## §3. 계층·규모·의존성

- epic은 기획·설계·추적을 맡으며 하위 epic/leaf를 거느린다. **하위 이슈
  1개 이상과 함께 생성**한다. leaf는 구현·조사·문서 등 한 작업 단위다.
- 부모는 완료·취소되지 않은 epic 하나다. 부모 없는 leaf도 허용한다.
  다른 부모로 옮기는 요청은 기존·새 부모를 미리 보여 주고 확인받는다.
- leaf의 `수용 기준` / `Acceptance Criteria` 절 체크박스 개수로 규모를 정한다.
  코드 펜스 안의 예시는 세지 않는다. 1개 XS, 2개 S, 3–4개 M, 5–6개 L이다.
  0개면 기준을 받고, 7개 이상이면 기준을 몰래 줄이거나 합치지 않고 epic/leaf
  분할안을 제시한다. Tasks의 체크박스는 크기에 포함하지 않는다.
- 분할은 유스케이스·저장소·승인 경계로 한다. 공유 설계·계약이 필요하면 먼저
  끝내는 leaf로 두고 구현이 의존하게 한다. BE/FE는 다른 leaf로 제안한다.
  분할 결정은 epic의 `나눈 기준` / `Split Rationale`에 기록한다.
- `blocked_by`는 실제 선행만 지정한다. 부모가 다른 이슈도 허용하고 보고에
  부모 차이를 표시한다. 누락된 ID, 자신에 대한 선행, 계층·완료 대기 순환은
  오류다. epic이 자식 완료를 기다리는 관계도 순환 검사에 포함한다.
- `Blocked`는 **상태 필드가 아닌 계산 값**이다. 종료되지 않은 선행이 하나라도
  있으면 작업 상태와 별도로 표시한다. 캐시·라벨을 원본으로 삼지 않는다.
  `Done`과 `Cancelled`는 종료다. 취소된 선행은 대기를 풀지만 수용 기준 충족의
  증거가 되지는 않는다. epic 마무리에서 그 공백을 확인한다.

## §4. 생명주기·동기화·완료

- 시작: Open 이슈의 선행을 읽어 Blocked가 아니면 `In Progress`와 작업 계획을
  기록한다. 이미 진행 중이면 중복 시작 없이 현재 상태를 보고한다.
- 완료: 수용 기준마다 충족 여부와 검증 결과/문서 경로/커밋 등 근거를 기록하고
  충족했을 때 `Done`으로 바꾼다. 사용자의 완료 지정도 근거로 기록할 수 있다.
  부족하거나 판단 불가인 항목이 있으면 보고하고 결정을 기다린다.
  PR·브랜치·머지는 필수가 아니다. 자동 머지 판정도 하지 않는다.
- 취소·재개: 명시적으로 요청한 경우 이유를 기록한다. 재개는 `Open`이다.
  하위 이슈가 활성인 epic의 취소, 종료된 부모 밑 자식의 재개는 연결된 이슈까지
  어떻게 처리할지 물어 확정한다. 관계를 지우거나 자식을 일괄 취소하지 않는다.
- 동기화: 원본 파일을 다시 읽어 `parent`로 직계 하위 이슈를 찾고, 종료 상태 →
  Blocked → epic 표 순서로 계산한다. 하위 상태를 추측해 고치지 않는다.
  epic의 `SUBISSUES` 표식 사이만 갱신한다. 표식 누락·중복이면 본문을 보존하고
  표식을 넣을지 묻는다. 미러는 §2대로 함께 갱신한다.
- epic 마무리: 동기화 후 모든 하위 이슈가 종료됐는지 확인한다. 손자 이하는
  각 자식 epic이 책임지지만 관계 오류가 있으면 완료를 막는다. epic 수용 기준을
  하위 이슈 근거와 대조한다. 미충족이면 새 leaf 분리 또는 범위 결정을 묻고,
  충족하면 마무리 기록과 Done을 쓴다. 취소 자식도 충족 근거를 대신하지 않는다.
- `이상`은 검사 오류의 보고 항목이며 상태가 아니다. 빈 epic, 자식이 있는 leaf,
  잘못된 관계 등을 보고하고 완료 판정에서 제외하지 않는다.

표 형식(제목은 원문 언어로 번역하되 표식은 고정):

```markdown
<!-- SUBISSUES:START -->
| 이슈 | 종류 | 상태 | Blocked | 선행 |
|---|---|---|---|---|
| [issue012](issue012.md) | leaf | Open | true | issue013 |
<!-- SUBISSUES:END -->
```

## §5. 쓰기·확인·실패

실행 파일: `${CLAUDE_PLUGIN_ROOT}/scripts/local-issues.py` (Python 3 표준 라이브러리).
`register --repo PATH --root PATH`, `locate --repo PATH`, `next-id --root PATH`,
`check --root PATH`는 JSON을 출력한다. `check`는 문제 없음 0, 문서/관계 문제 1,
사용법·경로·입력 실패 2다. `legacy` 목록은 자동 전환하지 않는다.

로컬 쓰기는 요청한 범위에서 진행한다. 생성할 내용·관계와 수정할 파일을 먼저
제시하고, 이미 확정된 요청은 중복 승인 없이 적용한다. 사용자 결정이 필요한
경계는 다음이다:

> **결정 필요**: <누락 정보/충돌/범위 변경>. 권장안과 이유, 선택지를 제시하고 답을 기다린다.

- 동시에 쓸 수 있는 공용 원본이므로, 모든 생성·갱신은 원본 디렉터리의
  `.issue-local.lock`을 배타적으로 생성(`open(..., "x")`)한 뒤 수행한다.
  잠금에는 수행 작업을 적고 자신이 획득한 잠금만 `finally`에서 해제한다.
  기존 잠금은 삭제하거나 재시도하지 않고 보고한다.
- 잠금 안에서 대상 원본·관계를 다시 읽고 미리보기와 달라졌으면 쓰지 않는다.
  새 파일은 `open(..., "x")`로 생성한다. epic과 새 하위 이슈는 전체 번호·관계를
  먼저 확정하고, 전체 문서를 준비한 다음 쓴다. 기존 파일은 읽은 내용이 같은지
  확인한 뒤 같은 디렉터리의 임시 파일을 `os.replace`로 치환한다.
- 쓰기 후 `check --root`와 이번 변경의 미러 구조 동등성을 확인한다. 검사 오류가
  있으면 수정·재검사는 최대 2회. 남으면 오류와 이미 쓴 파일을 보고하고 멈춘다.
  통과를 위해 기준·관계를 삭제하거나 검사 결과를 숨기지 않는다.
- 명령 실패는 자동 재시도하지 않는다. 부분 쓰기는 파일별로 보고하고 현재
  디스크 내용에서 재개한다. 자동 삭제·롤백·git 커밋·push·머지는 하지 않는다.
