## 1. ID 체계

한국어 문서 안에서도 **영문 그대로** 쓴다. 앵커·grep·플러그인 간 호환이
걸려 있다.

| 대상 | 형식 | 예 |
|---|---|---|
| 기능 요구사항 | `FR-<영역>-NN` | `FR-ORDER-01` |
| 비기능 요구사항 | `NFR-<분류>-NN` | `NFR-PERF-01` |
| 유저 스토리 | `US-NN` | `US-01` |
| 인수 기준 | `AC-USNN-NN` | `AC-US01-02` |
| 다중 액터 유스케이스 | `UC-<영역>-NN` | `UC-AUTH-01` |
| 화면 | `SCR-<영역>-NN` | `SCR-ORDER-01` |
| 유저 플로우 | `UF-<도메인>-NN` | `UF-order-01` |
| 흐름 (백엔드) | `FLOW-<도메인>-<오퍼레이션 ID>` | `FLOW-order-placeOrder` |
| 흐름 (프론트엔드) | `FLOW-<도메인>-<라우트 슬러그>` | `FLOW-order-detail` |
| 흐름 (도메인 횡단) | `FLOW-CROSS-<슬러그>` | `FLOW-CROSS-checkout` |
| 테스트 | `T-1NN` 백엔드 / `T-2NN` 프론트엔드 / `T-3NN` E2E | `T-101` |

`<영역>`과 `<분류>`는 대문자 약어, `NN`은 01부터 빈 번호 없이 순차.
`SCR-`의 `<영역>`은 `FR-`과 같은 약어를 쓰고, `UF-`의 `<도메인>`은
`FLOW-`와 같은 소문자 슬러그를 쓴다 — 화면은 요구사항 영역을 따라 묶이고
플로우는 도메인 단위로 묶이기 때문이다.

`UF-`를 `FLOW-`로 통합하지 않는 이유: `FLOW-`는 설계 단계에서 부여되는
구현 흐름 키이고 `UF-`는 기획 단계의 과업 흐름 키다. 같은 접두사를 쓰면
grep으로 어느 계층의 키인지 구분할 수 없다.

T-ID 대역이 나뉘어 있는 이유는 두 설계 스킬이 같은 번호 공간을 쓰면
충돌하기 때문이다.

## 2. 기술 중립성 스왑 테스트

`requirements.md`와 `user-stories.md`의 **모든 문장**에 문장 단위로
적용한다. Python을 Java로, REST를 GraphQL로, PostgreSQL을 MongoDB로 바꿔도
문장이 그대로 참이어야 한다. 프레임워크 이름, 경로, 타입 시그니처, 테이블
이름은 들어가지 않는다.

예외는 둘뿐이다:

- `api-interface.md` — 계약 문서이므로 구체 스키마를 담는다
- `[REF: ...]` 인용 — 기술 내용이 아니라 출처 표시다

---

## 3. 요구사항 작성 규칙

- 기능 요구사항은 한 문장으로 검증 가능해야 한다. "~를 잘 처리한다" 같은
  문장은 요구사항이 아니다.
- **측정 가능한 수치가 없으면 NFR이 아니다.** 측정 기준과 목표값을 채울 수
  없으면 넣지 않는다.
- `## 범위 밖`이 비어 있으면 범위가 정해지지 않은 것이다.
- 모든 FR이 최소 하나의 US로 커버되어야 한다. 커버되지 않으면 스토리를
  추가하거나 그 FR이 정말 필요한지 확인한다.

---

## 4. 유저 스토리와 인수 기준

- **유저 스토리는 (액터, 능력) 단위**이지 오퍼레이션 단위가 아니다.
- 인수 기준은 Given/When/Then으로 쓰고 **테스트로 옮길 수 있어야 한다.**
  "올바르게 동작한다", "적절히 처리한다" 같은 문장은 인수 기준이 아니다.
  정상 경로만 쓰지 말고 실패·경계 조건을 반드시 포함한다.
- **다중 액터 흐름은 조건부다.** 액터 2인 이상 또는 외부 시스템이 관여할
  때만 `UC-<영역>-NN`을 만든다. 조건에 맞지 않으면 섹션과 목차 항목을
  통째로 삭제한다.

## 5. 정보 구조와 유저 플로우

### 생성 조건

**사용자 인터페이스가 있는 프로젝트에서만 만든다.** 순방향에서는 스택 설정
단계에서 프론트엔드가 확정되었는지로, 역방향에서는 프론트엔드 설계 문서가
있는지로 판단한다. 조건에 맞지 않으면 두 문서를 **만들지 않고** 그 사실을
완료 리포트에 남긴다 (`common-rules.md` §6.1과 같은 방식).

**둘은 짝이다.** `user-flows.md`의 노드가 `information-architecture.md`의
`SCR-` 키를 참조하므로 유저 플로우만 만들지 않는다.

### 책임 경계

이 경계를 어기면 기획 문서가 화면 정의서로 자라나고, 구현이 바뀔 때마다
기획이 낡는다.

| 무엇 | 어느 문서 |
|---|---|
| 어떤 화면이 있고 어떻게 묶이는가 | `planning/information-architecture.md` |
| 화면 사이를 어떻게 지나가는가 | `planning/user-flows.md` |
| 화면 안에 무엇이 어떻게 배치되는가 | `design/frontend/component-tree.md` |
| 화면에 어떤 주소가 대응하는가 | `design/frontend/routing.md` |

**레이아웃·반응형 규칙·인터랙션 패턴은 기획이 아니다.** "상단에 크게",
"모바일에서는 접힌다" 같은 서술이 나오면 경계를 넘은 것이다.

**라우트 경로도 기획이 아니다.** 기획은 화면에 `SCR-` 키만 부여하고, 설계가
그 키에 주소를 대응시킨다.

### 작성 규칙

- **모든 화면은 최소 하나의 유저 스토리에 연결된다.** 연결되지 않는 화면은
  만들 이유가 없거나 스토리가 빠진 것이다.
- **모든 화면은 최소 하나의 유저 플로우에 등장한다.** 어느 플로우에도 나오지
  않는 화면은 도달 경로가 없다. `traceability.md`의
  `### 플로우에 등장하지 않는 화면`으로 내린다.
- **유저 플로우에 백엔드 호출을 그리지 않는다.** 서버 처리가 필요한 지점은
  노드 하나로 뭉뚱그리고 `FLOW-` 키를 링크만 한다. 이 규칙을 어기면 유저
  플로우와 백엔드 시퀀스 다이어그램이 같은 내용을 두 번 그리게 되고, 코드가
  바뀔 때 두 곳이 어긋난다.
- **`서버 흐름` 열은 설계 단계에서 채운다.** 기획 단계에서는 서버 호출이
  필요한 단계에 `설계 대기`, 필요 없는 단계에 `—`를 적는다.
- **화면 계층은 포함 관계이지 전이가 아니다.** 사용자 이동은 유저 플로우가
  그린다. 계층이 평면적이면 `## 화면 계층` 섹션을 통째로 삭제한다.
- 표시 정보의 개념 이름은 `glossary.md`의 영문 식별자를 따른다.

## 6. 인터페이스 계약

`api-interface.md`는 프론트엔드와 백엔드 **양쪽 설계 스킬의 공통 입력**이다.
설계 단계에서 만들면 두 스킬이 서로 다른 계약을 만들어 버리므로 기획 단계에
둔다.

### 계약 블록 형식 선택

`architecture.md`의 스택 표에서 확정된 API 스타일을 읽고, 템플릿의 계약
블록 중 **해당하는 형식만 남기고 나머지는 통째로 삭제한다.** 여러 스타일이
섞인 프로젝트만 블록을 여럿 남긴다.

| API 스타일 | 계약 블록 형식 |
|---|---|
| REST/HTTP | OpenAPI 3.1 YAML |
| GraphQL | SDL 스키마 |
| gRPC | `.proto` 정의 발췌 |
| 메시지/이벤트 기반 | AsyncAPI 또는 메시지 스키마 표 |
| 그 외 / 혼합 | 오퍼레이션 표 + 요청·응답 스키마 |

### 공통 규칙

- **오퍼레이션 카탈로그를 먼저 채운다.** `오퍼레이션 ID`는 프로토콜과 무관한
  안정적 식별자이며, 계약 블록과 시퀀스 다이어그램이 이 ID로 서로를 참조한다.
- **오류 모델을 한 번만 정의하고** 계약 블록이 그것을 참조하게 한다.
  오퍼레이션마다 오류 구조를 다르게 정의하지 않는다.
- **인가 표에서 공개 오퍼레이션도 "인증 불필요"로 명시한다.** 빈 칸은
  미확인과 구분되지 않는다.
- 스키마의 필드·타입 이름은 `glossary.md`의 영문 식별자를 따른다.

## 7. 추적성 매트릭스

`traceability.md`는 **조인 테이블**이다. 다른 문서의 내용을 옮겨 적지
않는다. ID와 링크만 있고 설명은 없어야 한다. 설명을 쓰고 싶어지면 그건
원본 문서에 있어야 할 내용이다.

`## 미연결 항목`을 정직하게 채운다. 연결이 끊긴 곳을 숨기지 않는다.
