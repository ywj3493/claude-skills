# 백엔드 구현 규약

`backend-implementation` 스킬이 시작 전에 로드한다. 설계 문서를 4-Layered
DDD 코드로 옮길 때 **어느 스택에서든 참인 규칙**만 담는다. 언어·프레임워크
관용구(폴더 이름, 불변 객체 문법, DI 방식, 테스트 도구)는
`${CLAUDE_PLUGIN_ROOT}/references/stacks/<프로파일>.md`가 소유한다.

스킬 본문은 여기 있는 내용을 반복하지 않고 절 번호로 참조한다
(예: `구현 규약 §3.1`).

---

## 1. 결정의 우선순위

같은 질문에 여러 출처가 다른 답을 주면 위에 있는 것이 이긴다.

1. **`architecture.md`의 `## 아키텍처 규약`** — 스택, 계층 ↔ 디렉터리 매핑,
   허용 의존성 방향. 사용자가 정한 값이다.
2. **도메인 설계 문서** — `layered-architecture.md`(파일 위치),
   `domain-model.md`(불변식·행위·상태 전이·식별자 생성·동시성 정책·이벤트
   전달 방식), `erd.md`(영속성 매핑), `sequence-diagram.md`(호출 흐름과 실패
   분기), `domain-map.md`(컨텍스트 간 패턴과 통합 방식), `glossary.md`(이름).
3. **기존 코드의 관례** — 같은 계층의 이웃 파일이 이미 쓰는 방식.
4. **스택 프로파일** — `references/stacks/<프로파일>.md`.
5. **이 문서의 일반 규칙.**

**이 순위는 관용구에 대한 것이다** — 이름, 파일 위치, 폴더 구성, 도구,
문법. §2 의존 방향과 §3~§7의 원칙은 위 출처가 다르게 말해도 자동으로
뒤집히지 않는다. 어겨야 한다면 `layered-architecture.md`의 `## 규약 예외`에
사유와 함께 기록한 뒤에만 어긴다 (§9).

기존 코드가 원칙을 어기고 있어도 **새로 쓰는 코드는 원칙을 따른다.** 구현
범위 밖의 기존 코드는 고치지 않고 완료 리포트에 "기존 코드의 규약 이탈"로
남긴다.

**설계 결정은 구현이 내리지 않는다.** 이 문서의 몇몇 규칙은 설계 문서의
값에 따라 갈라진다 — 식별자 생성 방식(§3.1.9), 동시성 정책(§4.8), 이벤트
전달 방식과 실패 시 처리(§4.9), 컨텍스트 간 패턴(§5.7). 그 값이 설계 문서에
`미정`으로 적혀 있거나 칸 자체가 없으면, 이 문서의 어느 선택지도 기본값으로
고르지 않는다. 스킬이 구현 계획 단계에서 사용자에게 묻는다.

`미정`은 "설계 시점에 정하지 못했다"는 한 가지 뜻으로만 쓴다. 섹션이 없는
것이 "없음"을 뜻하는 경우는 그 규칙에 따로 적는다 — 도메인 이벤트 섹션이
없으면 이벤트가 없고(§3.6), 읽기 모델 행이 없으면 읽기 전용 저장소를 두지
않는다(§4.6.4).

## 2. 의존 방향

```text
Presentation → Application → Domain ← Infrastructure
```

| 출발 | 도착 | 허용 | 비고 |
|---|---|---|---|
| Presentation | Application | O | 유스케이스와 DTO |
| Presentation | Domain | △ | **예외 타입에 한해** — 전역 오류 변환용 |
| Presentation | Infrastructure | X | 구현체는 컴포지션 루트만 안다 |
| Application | Domain | O | 애그리거트, 값 객체, 포트 |
| Application | Infrastructure | X | 포트(인터페이스)를 통해서만 |
| Application | Presentation | X | 요청 객체·HTTP 예외·쿠키를 받지 않는다 |
| Domain | 다른 모든 계층 | X | 웹·ORM·설정 프레임워크도 금지 |
| Infrastructure | Domain | O | 포트를 구현한다 |
| Infrastructure | Application | X | 응용 계층 예외도 import하지 않는다 |
| Infrastructure | Presentation | X | |

1. **도메인은 순수하다.** 표준 라이브러리와 부수 효과 없는 작은 유틸 외에는
   import하지 않는다. 시계와 ID 생성기도 인자나 포트로 받는다.
2. **컴포지션 루트는 예외다.** 구체 어댑터를 아는 유일한 곳이므로 위 표의
   적용 대상이 아니다. 대신 컴포지션 루트에는 조립 외의 로직을 두지 않는다.
3. **도구로 강제한다.** 스택의 import 규칙 도구(프로파일이 지정)로 위 표를
   계약으로 심고, 검증 단계마다 실행한다. 도구가 없는 스택이면 완료 리포트에
   "의존 방향 미강제"를 남긴다 — 조용히 넘어가지 않는다.
4. `architecture.md`의 허용 의존성 표에 위 표와 다른 행이 있으면
   `architecture.md`가 이긴다 (§1). 위 표에만 있는 행(예: Presentation →
   Domain 예외 타입)은 사용자 동의를 받아 `architecture.md` 비고에 기록한 뒤
   적용한다.

## 3. 도메인 계층

### 3.1 애그리거트와 엔티티

1. **상태는 애그리거트 루트의 의도를 드러내는 메서드로만 바꾼다.** 공개
   setter를 만들지 않는다. 메서드 이름은 `domain-model.md` 행위 표의
   `메서드` 열, 없으면 `glossary.md`의 영문 식별자를 쓴다
   (`setStatus` 대신 `cancel`, `changeShippingInfo`).
2. **불변식은 애그리거트가 스스로 지킨다.** `domain-model.md`의 불변식 표
   행마다, 그 불변식을 깰 수 있는 모든 생성 경로와 행위 메서드에서 검사한다.
   위반 시 동작은 표의 `위반 시 동작` 열을 따른다 — 보통 도메인 예외(§3.5).
3. **생성은 팩토리로 한다.** 새 애그리거트를 만드는 정적 팩토리(또는 다른
   애그리거트의 메서드 — "애그리거트를 팩토리로")가 식별자와 생성 시각을
   **인자로 받아** 불변식을 검사한다. 식별자를 어디서 얻는지는 §3.1.9가
   정한다. 유스케이스가 UUID나 타임스탬프를 직접 조립하지 않는다.
   다른 애그리거트의 상태가 생성 조건이면(상점이 영업 중일 때만 상품 등록)
   그 애그리거트의 메서드를 팩토리로 삼아 조건 검사를 캡슐화한다.
4. **재구성은 생성과 분리한다.** 저장소에서 읽어 되살리는 경로는 이벤트를
   발행하지 않고 생성 규칙(예: "초기 상태는 대기")을 다시 적용하지 않는다.
5. **상태 전이는 `## 상태 전이` 표를 그대로 코드로 옮긴다.** 허용 전이 외에는
   예외를 던진다. `금지 전이` 표의 행마다 테스트를 하나씩 둔다.
6. **다른 애그리거트는 ID로만 참조한다.** 객체 참조를 필드로 두지 않는다.
7. **루트 외의 엔티티를 의심한다.** 애그리거트에서 루트를 뺀 나머지는 대부분
   값 객체다. 별도 테이블에 저장된다고 엔티티인 것은 아니다. 독자적인
   생명주기가 있으면 다른 애그리거트일 가능성이 높다 — `domain-model.md`와
   다르게 판단되면 구현을 멈추고 설계 수정을 제안한다.
8. 엔티티의 동등성은 식별자로 판단한다.
9. **식별자 생성 위치는 `domain-model.md` 애그리거트 상세의 `식별자 생성`
   행을 따른다.** 세 방식과 그 위치:

   | 방식 | 예 | 생성 위치 |
   |---|---|---|
   | 사용자 입력 | 이메일, 로그인 ID | Command DTO로 들어오고, 식별자 값 객체가 형식을 검증한다. 중복 검사는 유스케이스가 리포지토리로 한다 |
   | 도메인 로직 | 주문번호, 문서번호 | 규칙이 있는 번호는 도메인 서비스(또는 식별자 값 객체의 팩토리)가 만든다. 규칙 없는 고유값이면 리포지토리 포트의 `nextId()` |
   | 저장소 일련번호 | DB 자동 증가 | 리포지토리 포트의 `nextId()`가 저장 전에 발급한다(시퀀스 선조회) |

   저장소가 삽입 시점에만 번호를 정하는 방식(저장 전에 식별자가 없는
   애그리거트)은 §3.1.3을 깨므로 §9 타협으로 기록한다.
10. **로딩 전략은 애그리거트마다 정한다.** "완전한 애그리거트"(§3.4.2)는
    행위 메서드가 실행될 때 필요한 구성 요소가 전부 보인다는 뜻이지, 루트를
    읽는 순간 모든 구성 요소를 한 번에 읽는다는 뜻이 아니다. 지연 로딩이
    트랜잭션 안에서 보장되는 스택이면 쓸 수 있다. 전역 기본값으로 즉시 로딩이나
    지연 로딩 하나를 강제하지 않는다. 판단 근거(구성 요소 크기, 행위 빈도
    대비 조회 빈도)는 스택 프로파일을 따른다.

### 3.2 값 객체

1. **불변이다.** 생성 후 필드를 바꿀 수 없고, 연산은 새 인스턴스를 돌려준다.
2. **생성 시점에 스스로 검증한다.** 잘못된 값 객체는 존재할 수 없다.
3. 동등성은 모든 값의 동등성이다.
4. `domain-model.md`가 식별자를 값 객체로 정했으면 원시 타입 대신 그 타입을
   쓴다. 타입 안정성과 식별자 고유 기능(형식 검증, 세대 구분 등)이 그 이유다.
5. 여러 필드가 개념적으로 하나면(금액+통화, 시작+종료) 값 객체로 묶는다.

### 3.3 도메인 서비스

1. **상태 없이 로직만 가진다.** 필요한 상태는 인자로 받는다.
2. 쓰는 때: 한 애그리거트에 넣기 어려운 계산(여러 애그리거트가 필요),
   또는 외부 시스템이 필요한 도메인 판단.
3. **외부 연동이 필요한 도메인 서비스는 도메인 관점의 인터페이스로
   정의한다** — `PermissionChecker.canCreateSurvey(userId)`이지
   `HttpClient.get(...)`이 아니다. 구현은 Infrastructure에 둔다.
4. 판단 기준: 그 로직이 애그리거트의 상태를 바꾸거나 상태 값을 계산하면
   도메인 로직이다. 응용 서비스에 두지 않는다.

### 3.4 리포지토리와 그 밖의 포트

1. **애그리거트 루트 하나에 리포지토리 하나.** 루트가 아닌 구성 요소용
   리포지토리를 만들지 않는다.
2. 기본 연산은 **식별자로 조회**와 **저장** 둘이다. 삭제는 필요할 때만.
   조회 결과는 **완전한 애그리거트**다.
3. 화면용 목록·검색 쿼리를 리포지토리에 넣지 않는다 — §4.6 조회 전용 경로.
4. **포트는 도메인 타입을 주고받는다.** 익명 튜플이나 딕셔너리를 반환하지
   않는다. 필요하면 값 객체를 새로 만든다(예: 토큰 묶음 → `TokenSet`).
5. **이름**: 포트는 기술 접두어 없이 도메인 용어로(`SessionRepository`),
   어댑터는 기술 접두어를 붙인다(`RedisSessionRepository`).
6. 위치는 `layered-architecture.md`의 Domain 표를 따른다. 표에 없는 포트가
   필요하면 기본 위치는 Domain이다.

### 3.5 도메인 예외

1. 불변식 위반과 금지 전이마다 **의미 있는 이름의 예외**를 둔다
   (`OrderAlreadyShipped`, `SessionExpired`).
2. 도메인 예외는 공통 기반 타입 하나를 상속한다. 표현 계층이 그 기반 타입과
   하위 타입으로 HTTP 상태를 정한다 (§6.3).
3. **도메인 예외는 전송 계층 정보를 갖지 않는다.** HTTP 상태 코드를 필드로
   넣지 않는다.

### 3.6 도메인 이벤트

`domain-model.md`의 `## 도메인 이벤트` 표에 행이 있을 때만 구현한다.
섹션이 없으면 이벤트를 만들지 않는다 — 다른 애그리거트를 바꿔야 할 것
같아도 이벤트를 지어내지 않고 §4.4.2에 따라 멈추고 묻는다.

1. **이름은 과거형이다** — 이미 일어난 일이다 (`OrderCanceled`,
   `PasswordChanged`). 이름은 표의 `이벤트` 열을 그대로 쓴다.
2. **페이로드는 표의 `페이로드` 열 그대로다.** 구독자가 처리에 필요한
   데이터를 담되, 이벤트와 무관한 애그리거트 전체를 싣지 않는다. 발생
   시각과 이벤트 고유 ID는 열에 없어도 넣는다 — 재처리·멱등성 판단(§4.9)에
   필요하다.
3. 이벤트는 불변 값 객체다 (§3.2).
4. **애그리거트는 이벤트를 기록만 한다.** 상태를 바꾼 행위 메서드가 자기
   안에 쌓아 두고, 응용 계층이 꺼내 간다. 애그리거트가 디스패처·메시지
   큐를 직접 부르지 않는다. 재구성 경로(§3.1.4)는 이벤트를 기록하지 않는다.
5. 이벤트를 쓰는 이유는 두 가지다 — **다른 컨텍스트의 후처리 트리거**(주문
   취소 → 환불)와 **시스템 간 데이터 동기화**. 같은 애그리거트 안의 다음
   단계를 이벤트로 쪼개지 않는다. 그건 행위 메서드 안의 로직이다.

발행 시점과 전달 방식은 §4.9가 정한다.

### 3.7 동시성 — 애그리거트 버전

`domain-model.md`의 `## 동시성 정책`에서 방식이 `낙관적`인 애그리거트에만
적용한다. 다른 방식은 §4.8.

1. **버전은 애그리거트 루트가 가진다.** 구성 요소마다 버전을 두지 않는다.
2. **루트가 아닌 구성 요소만 바뀌어도 루트 버전이 오른다.** 애그리거트는
   일관성의 단위이므로, 주문 항목 하나만 바뀐 것도 주문이 바뀐 것이다.
   ORM이 루트 테이블 행이 바뀌지 않았다는 이유로 버전을 올리지 않는 경우가
   있다 — 스택 프로파일이 정한 방법으로 강제 증가시킨다.
3. 버전 값은 읽기 전용 프로퍼티로 노출한다. 증가와 비교는 리포지토리
   어댑터가 저장 시점에 한다 (§5.6). 도메인 행위 메서드와 유스케이스는
   버전을 올리지 않는다.

## 4. 응용 계층

### 4.1 유스케이스 단위

1. **`FLOW-` 키 하나에 유스케이스 하나.** `sequence-diagram.md`의 흐름과
   `## 단순 통과 오퍼레이션` 표의 행이 구현 단위다.
2. 이름은 행위 기준 `<동사><명사>` + 스택 관례 접미사(`UseCase` 등). 영문
   단어는 `glossary.md`를 따른다.
3. 공개 진입 메서드는 하나다. 한 클래스에 여러 유스케이스를 묶지 않는다.

### 4.2 유스케이스의 모양

유스케이스 본문은 대체로 이것뿐이다.

```text
1. 포트로 애그리거트를 읽는다 (없으면 예외. 비관적 잠금이면 잠금 조회 — §4.8)
2. 애그리거트(또는 도메인 서비스)의 행위 메서드를 호출한다
3. 포트로 저장한다 (낙관적 잠금이면 기대 버전을 함께 — §4.8)
4. 커밋 후 애그리거트가 기록한 이벤트를 발행한다 (이벤트가 있을 때만 — §4.9)
5. 결과 DTO로 변환해 돌려준다
```

괄호 안의 변형은 이 모양의 일부다. 설계 문서가 정한 동시성·이벤트 동작
때문에 늘어난 줄은 아래의 "복잡하다"에 세지 않는다.

**이보다 복잡하면 도메인 로직이 새어 나온 것이다.** 조건 분기·계산·상태
판단을 애그리거트나 도메인 서비스로 옮긴다. 여러 유스케이스가 같은 로직을
복사하고 있다면 그것도 도메인 쪽(정책 값 객체, 도메인 서비스)으로 먼저
옮기고, 그래도 남는 **조율** 로직만 응용 서비스로 뺀다.

### 4.3 입력과 출력

1. 입력은 원시 값 2개 이하면 그대로, 그 이상이면 불변 Command(또는 Query)
   DTO로 받는다.
2. **표현 계층 타입을 받지 않는다** — 요청 객체, 세션, 쿠키, 헤더 맵.
3. 출력은 Result DTO다. **애그리거트를 표현 계층으로 넘기지 않는다.**
   DTO ↔ 도메인 변환은 한 곳(DTO의 변환 함수나 매퍼)에만 둔다.

### 4.4 트랜잭션

1. 트랜잭션 경계는 `layered-architecture.md` Application 표의
   `트랜잭션 경계` 열을 따른다.
2. **한 트랜잭션에서는 한 애그리거트만 바꾼다.** 둘 이상을 바꿔야 하면
   다음 중 하나다. 어느 쪽도 설계에 없으면 구현하지 않고 멈추고 묻는다.
   - `domain-model.md`의 `## 도메인 이벤트`에 그 연쇄가 있다 → 이벤트로
     나눈다 (§4.9).
   - 팀 표준·기술 제약(이벤트를 도입할 수 없음)이 이유다 →
     `layered-architecture.md`의 `## 도메인 고유 규칙` 또는 `## 규약 예외`에
     사유와 함께 기록된 행이 있다. 없으면 §9에 따라 기록을 제안한다.
3. 스택이 제공하는 트랜잭션 기능을 쓴다. 직접 커밋·롤백 코드를 흩뿌리지 않는다.
4. **트랜잭션은 짧게 유지한다.** 외부 시스템 호출, 사용자 입력 대기, 다른
   컨텍스트로의 동기 호출을 트랜잭션 안에 두지 않는다. 필요하면 커밋 후
   이벤트로 넘긴다 (§4.9).

### 4.5 설정과 권한

1. **응용 계층은 프레임워크 설정 객체에 의존하지 않는다.** 필요한 값(만료
   여유 시간, 한도 등)만 원시 값이나 정책 값 객체로 주입받는다. 설정 객체를
   읽어 값을 꺼내는 일은 컴포지션 루트가 한다.
2. 권한 검사 위치: **인증 여부**는 표현 계층, **기능 단위 인가**는 응용
   계층, **데이터 행 단위 권한**은 도메인 서비스.

### 4.6 조회 전용 경로 (CQRS)

명령 모델(애그리거트)은 한 애그리거트의 상태를 바꾸는 범위에 맞춰져 있고,
화면은 여러 애그리거트를 조합해 보여 준다. 두 범위가 다르므로 조회를 명령
모델로 구현하지 않는다.

1. 상태를 바꾸지 않는 화면용 조회는 애그리거트를 거치지 않아도 된다. 조회
   포트(DAO)가 읽기 모델 DTO를 직접 돌려준다. 트랜잭션이 필요 없다.
2. **조회에는 유스케이스를 두지 않아도 된다.** 표현 계층이 응용 계층의 조회
   포트를 직접 부를 수 있다 (§2의 Presentation → Application 행). 권한에
   따른 필터링, 여러 조회의 조합, 마스킹 같은 로직이 있을 때만 조회 서비스를
   둔다. 이 경우도 `FLOW-` 키 하나에 하나다 (§4.1).
3. 여러 애그리거트를 조인해야 하는 목록 화면은 리포지토리 여러 번 호출(N+1)
   대신 조회 전용 쿼리 하나로 만든다.
4. **읽기 전용 저장소는 설계가 정했을 때만 둔다.** 조회 전용 테이블·뷰·다른
   저장소를 이벤트로 동기화하는 방식은 실시간성이 덜 중요한 조회(통계,
   검색)에 쓰지만, 코드량과 운영할 기술이 늘어난다. `layered-architecture.md`
   Infrastructure 표에 구분이 `읽기 모델`인 행이 있을 때만 만든다. 동기화는
   §4.9의 이벤트 핸들러로 한다.
5. **검색 조건은 조합 가능한 조건 객체(스펙)로 표현한다.** 조건이 여러 개이고
   선택적이면 조회 포트가 조건 객체를 받는다. 비어 있는 조건은 "제한 없음"을
   뜻한다. 조건 객체를 SQL·쿼리 DSL로 바꾸는 일은 인프라가 한다 (§5.5).
   모든 데이터를 메모리로 읽어 걸러내지 않는다.
6. **페이지네이션은 조회 포트의 인자로 받는다** — 페이지 번호·크기·정렬을
   묶은 값 객체. 리포지토리(명령 모델)에 페이지네이션 메서드를 두지 않는다.
7. 1-N 연관을 페이지네이션할 때는 필터링을 먼저 하고 조인한다.

### 4.7 로깅

비밀값(토큰, 비밀번호, 세션 ID 원문, 개인정보)을 어느 로그 레벨에도 남기지
않는다. 식별이 필요하면 마스킹하거나 앞부분만 남긴다.

### 4.8 동시성 제어

`domain-model.md`의 `## 동시성 정책` 표가 애그리거트마다 방식을 정한다.
값이 `미정`이거나 표·행이 없는 애그리거트는 구현 계획 단계에서 사용자에게
묻는다 (§1). 세 방식은 모두 애플리케이션 수준의 패턴이며, 저장 기술에 맞는
구현은 §5.6과 스택 프로파일이 정한다.

| 방식 | 언제 | 응용 계층이 하는 일 |
|---|---|---|
| `낙관적` | 충돌이 드물고, 사용자가 본 화면 기준으로 수정해야 할 때 (운영자가 배송 처리하는 사이 고객이 배송지를 바꾸는 경우) | 요청의 기대 버전을 리포지토리에 넘기고 충돌 예외를 그대로 둔다 |
| `비관적` | 충돌이 잦고, 한 트랜잭션 안에서 끝나는 수정 | 잠금 조회 메서드로 읽는다. 대기 시간 상한은 표의 값 |
| `오프라인 비관적` | 수정이 여러 요청(트랜잭션)에 걸칠 때 (편집 화면 열기 → 저장) | 첫 요청에서 잠금을 얻고 마지막 요청에서 푼다 |
| `없음` | 표의 `충돌 시나리오`가 "없음"으로 확인된 경우 | 아무것도 하지 않는다 |

**낙관적**

1. `동시성 정책`의 `버전 전달`이 `요청`이면 Command DTO가 클라이언트가 본
   버전을 받는다. 표현 계층은 응답에 현재 버전을 담는다 —
   `api-interface.md`의 스키마에 버전 필드가 없으면 구현하지 않고 설계 수정을
   제안한다.
2. 유스케이스는 버전을 비교하거나 올리지 않는다. 기대 버전을 저장 호출에
   넘기기만 하고, 비교·증가는 어댑터가 한다 (§3.7.3, §5.6).
3. 충돌은 이름 있는 예외(예: `ConcurrentModification`)다. 표현 계층은
   `api-interface.md` `## 오류 모델`의 충돌 코드로 바꾼다. 오류 모델에 충돌
   코드가 없으면 설계 수정을 제안한다.
4. 충돌 시 자동 재시도를 하지 않는다. 사용자가 이전 데이터를 보고 내린 결정을
   새 데이터에 덮어쓰게 되기 때문이다. `충돌 시 동작`이 재시도 횟수와 함께
   재시도를 정했을 때만 그 횟수까지 재시도하고, 그래도 충돌하면 충돌 예외를
   그대로 낸다. 횟수 없이 "재시도"만 적혀 있으면 `미정`으로 본다.

**비관적**

1. 리포지토리 포트에 잠금 조회 메서드를 따로 둔다(`findByIdForUpdate`).
   기본 조회 메서드에 잠금을 섞지 않는다.
2. 대기 시간 상한을 반드시 둔다. 상한 초과는 이름 있는 예외다.
3. 한 트랜잭션에서 여러 행을 잠가야 하면 항상 같은 순서(식별자 오름차순)로
   잠가 교착을 피한다.

**오프라인 비관적**

1. 잠금은 `LockManager` 포트로 다룬다 — 잠금 획득(대상, 소유자, 만료 시간)
   → 잠금 ID, 잠금 확인, 해제, 만료 연장. 포트는 응용 계층에 둔다. 도메인
   규칙이 아니라 요청 간 조율이기 때문이다.
2. **만료 시간을 반드시 둔다.** 사용자가 편집 화면을 닫고 사라져도 잠금이
   풀려야 한다. 만료 시간은 `동시성 정책`의 값이다.
3. 잠금을 얻은 뒤의 수정 요청은 잠금 ID를 함께 보내고, 유스케이스는 저장 전에
   잠금이 아직 자기 것인지 확인한다.
4. 구현(잠금 테이블, 분산 락)은 인프라다 (§5.6).

### 4.9 이벤트 발행과 처리

`domain-model.md` `## 도메인 이벤트` 표의 `전달 방식`이 정한다. `미정`이거나
열이 없으면 구현 계획 단계에서 묻는다 (§1).

1. **핸들러는 트랜잭션이 커밋된 뒤에만 실행한다.** 저장이 롤백됐는데 후처리가
   실행되는 경우를 없애면 실패 조합이 절반으로 준다. 유스케이스는
   `읽기 → 행위 → 저장(커밋) → 기록된 이벤트 발행` 순서다. 이벤트 발행 때문에
   §4.2의 모양에서 벗어나는 것은 허용된다.
2. 전달 방식별 구현:

   | 전달 방식 | 하는 일 | 주의 |
   |---|---|---|
   | `커밋 후 동기` | 커밋 직후 같은 프로세스에서 핸들러를 차례로 호출한다 | 핸들러 실패가 이미 커밋된 원래 요청을 실패로 만들지 않게 한다. 핸들러가 외부 시스템을 부르면 응답이 그만큼 늦어진다 |
   | `로컬 비동기` | 커밋 후 같은 프로세스의 별도 작업으로 넘긴다 | 프로세스가 죽으면 잃는다. `실패 시 처리`가 손실을 허용할 때만 |
   | `메시지 큐` | 커밋 후 큐에 보낸다 | 저장과 큐 전송은 한 트랜잭션이 아니다. 손실을 허용하지 않으면 아웃박스(아래)를 거친다 |
   | `이벤트 저장소+포워더` | 애그리거트 저장과 **같은 트랜잭션**으로 이벤트를 저장소(아웃박스 테이블)에 쓰고, 별도 포워더가 읽어 핸들러나 큐로 보낸다 | 포워더는 마지막으로 보낸 위치(오프셋)를 기억한다 |
   | `이벤트 제공 API` | 이벤트 저장소를 조회하는 API를 열고 외부 소비자가 가져간다 | 소비자가 자기 처리 위치를 기억한다. API의 응답 계약은 `api-interface.md`에 있어야 한다 |

3. **이벤트 저장은 이벤트 발행이 아니다.** `이벤트 저장소+포워더`에서
   이벤트를 아웃박스에 쓰는 일은 커밋 전에, 같은 트랜잭션 안에서 한다.
   §4.9.1의 "커밋 후"는 핸들러 실행에 대한 규칙이다.
4. **핸들러는 멱등이다.** 비동기 전달은 같은 이벤트를 두 번 이상 보낼 수
   있다. 핸들러는 처리한 이벤트 ID를 기록하고 이미 처리한 ID는 무시한다
   (또는 결과가 같은 연산만 한다).
5. **순서가 필요하면 설계에 있어야 한다.** `실패 시 처리` 열이나
   `## 도메인 고유 규칙`이 발생 순서 보장을 요구하면 이벤트 저장소 기반
   방식을 쓴다 — 메시지 큐는 기술에 따라 순서가 바뀐다. 요구가 없으면 순서에
   기대는 코드를 쓰지 않는다.
6. **실패 처리는 `실패 시 처리` 열을 따른다** — 재시도 횟수·간격, 상한 후
   처리(보류 목록·수동 처리). 상한 없는 재시도를 쓰지 않는다. 열에 재시도
   상한이나 상한 후 처리가 빠져 있으면 `미정`으로 본다 (손실을 허용하는
   `로컬 비동기`처럼 재시도하지 않는 방식은 "재시도 없음"이면 충분하다). 한 이벤트가
   계속 실패해 뒤의 이벤트 전체를 막지 않도록, 상한에 닿은 이벤트는 보류
   목록으로 옮기고 다음으로 진행한다.
7. 핸들러는 구독하는 쪽 컨텍스트의 응용 계층에 둔다. 핸들러의 본문은
   유스케이스와 같은 모양이다 (§4.2). 다른 컨텍스트의 이벤트를 받으면
   §5.7에 따라 자기 모델로 바꾼 뒤 쓴다.

## 5. 인프라 계층

1. **어댑터는 포트를 구현한다.** 포트에 없는 공개 메서드를 추가해 상위
   계층이 쓰게 하지 않는다.
2. **영속성 모델과 도메인 모델의 변환은 인프라에 둔다.** 도메인 객체가
   자기 직렬화(`to_dict`, JSON 매핑)를 알지 않는다. 단, `erd.md`가 "도메인
   모델 = 영속성 모델"로 정했으면 ORM 매핑을 도메인에 둘 수 있다 — 그
   경우도 §9에 따라 기록한다.
3. **기술 예외를 밖으로 새지 않게 한다.** 드라이버·SDK 예외를 잡아 도메인
   예외나 포트가 선언한 예외로 바꾼다. 응용 계층 예외를 import하지 않는다.
4. **외부 SDK는 감싼다.** SDK 모델을 도메인 타입으로 한 곳에서 변환한다.
   같은 변환을 메서드마다 복사하지 않는다.
5. 복잡한 조회 쿼리(§4.6)의 구현도 여기 둔다. 조건 객체를 쿼리로 바꾸는
   변환도 여기다.
6. **동시성 구현은 어댑터가 한다** (§3.7, §4.8).
   - 낙관적: 저장 시 "저장소의 버전 = 기대 버전"을 조건으로 갱신하고 버전을
     1 올린다. 갱신된 행이 없으면 충돌 예외를 던진다. 비교와 갱신은 한 원자적
     연산이어야 한다(조건부 UPDATE, 저장소의 compare-and-set). 읽고 비교한 뒤
     따로 쓰지 않는다.
   - 비관적: 저장소의 행 잠금(`SELECT ... FOR UPDATE` 등)과 대기 시간 상한
     설정. 상한 초과를 이름 있는 예외로 바꾼다.
   - 오프라인 비관적: `LockManager` 구현 — 잠금 테이블이나 분산 락. 만료는
     저장소가 강제한다(TTL, 만료 시각 조건).
7. **다른 컨텍스트의 모델은 경계에서 번역한다** (번역기 · ACL). 다른
   컨텍스트의 API 응답이나 이벤트 메시지를 받는 어댑터가 그것을 **자기
   컨텍스트의 도메인 타입**으로 바꾼다. 상대 컨텍스트의 DTO·필드 이름이
   도메인·응용 계층에 나타나지 않는다. 번역은 어댑터 한 곳에 모은다(§5.4와
   같은 이유).
   - 번역 책임은 `domain-map.md` `### 컨텍스트 관계` 표의 `패턴` 열을
     따른다. 기본은 **downstream(받는 쪽) 어댑터가 번역**한다 — `ACL`,
     `OHS`, `PL`, `C/S`, `P`가 여기 해당한다(`OHS`·`PL`이면 upstream이
     공개한 형식이 번역의 입력이다). 예외는 둘이다: `CF`면 upstream 모델을
     그대로 따르기로 한 결정이므로 번역하지 않고, `SK`면 공유 커널의 모델을
     함께 쓴다 (§7.7).
   - 메시지 큐로 통합할 때도 같다. 보내는 쪽은 자기 이벤트를 공개 형식으로
     직렬화하고, 받는 쪽 어댑터(메시지 리스너)가 번역한다. 맵에 패턴이 없으면
     구현 계획 단계에서 묻는다.

## 6. 표현 계층

1. **요청 형식을 검사하고, 응용 계층이 원하는 형식으로 바꾸고, 유스케이스를
   부르고, 결과를 응답 형식으로 바꾼다.** 그 이상을 하지 않는다.
2. **요청·응답 스키마는 `api-interface.md`의 계약과 정확히 일치한다** —
   필드 이름, 필수 여부, 상태 코드. 계약에 없는 필드를 응답에 더하지 않는다.
3. **오류 변환은 한 곳에 모은다.** 전역 예외 처리기가 도메인·응용 예외
   타입을 `api-interface.md`의 `## 오류 모델`(오류 응답 구조, 오류 코드)에
   맞는 상태 코드와 본문으로 바꾼다.
   엔드포인트마다 try/except를 복사하지 않는다.
4. 인증 확인, 세션, 쿠키, 헤더 같은 전송 관심사는 여기서 끝낸다.

## 7. 컴포지션 루트와 컨텍스트 경계

1. 구체 어댑터를 생성하고 포트 타입으로 넘기는 **유일한 곳**이다.
2. 컨텍스트(도메인)마다 하나를 기본으로 하고, 앱 수준 자원(DB 연결, HTTP
   클라이언트)은 앱 수명 주기에서 한 번 만들고 닫는다.
3. 설정 객체를 읽어 필요한 값만 꺼내 하위 계층에 넘긴다 (§4.5).
4. 테스트가 같은 조립을 대역으로 바꿔 끼울 수 있게 만든다.
5. **배포 단위가 하나여도 컨텍스트마다 패키지를 나눈다.** 여러 하위 도메인을
   한 컨텍스트 안의 한 모델로 합치지 않는다. 같은 용어라도 컨텍스트마다 뜻이
   다르면 타입도 따로 둔다.
6. **다른 컨텍스트의 내부를 import하지 않는다.** 한 프로세스 안에 있어도
   다른 컨텍스트의 도메인·응용 계층을 직접 부르지 않고, 포트와 어댑터(§5.7)나
   이벤트(§4.9)로 통합한다.
7. **공유 커널은 설계가 정했을 때만 둔다.** `domain-map.md`에 `SK` 패턴
   엣지가 있는 두 컨텍스트만 공유 패키지(예: `shared/`)의 모델을 함께 쓴다.
   기술 공용 코드(예외 기반 타입, 시계 타입)는 공유 커널이 아니므로 이 규칙과
   무관하다. 공유 커널을 바꾸는 변경은 두 컨텍스트의 테스트를 모두 돌린다.

## 8. 테스트

### 8.1 계층별 전략

| 계층 | 무엇을 | 대역 |
|---|---|---|
| Domain | 불변식, 행위, 상태 전이(허용·금지), 값 객체 검증 | 없음 — 순수 단위 테스트 |
| Application | 유스케이스의 정상·실패 분기 | 포트의 **페이크**(동작하는 메모리 구현) |
| Infrastructure | 어댑터의 변환·예외 변환·저장 형식 | 테스트용 실물 저장소가 가능하면 실물, 아니면 클라이언트 목 |
| Presentation | 스키마 검증, 상태 코드, 오류 변환 | 유스케이스 또는 포트를 대역으로 바꾼 앱 |

1. **응용 계층 테스트는 목이 아니라 페이크로 한다.** 페이크는 포트를 실제로
   구현한 메모리 버전이다(딕셔너리 저장소, 미리 정한 응답의 외부 클라이언트).
   호출 기록만 확인하는 목은 부수 효과 자체가 검증 대상일 때만 쓴다.
2. 페이크는 한 디렉터리에 모아 계층 테스트들이 공유한다. 테스트 전용 보조
   메서드(시드 데이터 주입, 개수 확인)를 둘 수 있다.
3. 모킹 경계는 `test-spec.md`의 `## 모킹 경계` 표와 일치시킨다.
4. 설계가 정한 동시성·이벤트 동작은 테스트가 있어야 한다:
   - 낙관적: 오래된 버전으로 저장하면 충돌 예외(어댑터 테스트), 루트가 아닌
     구성 요소만 바꿔도 버전이 오름(어댑터 테스트), 충돌의 상태 코드(표현
     테스트)
   - 비관적·오프라인 비관적: 대기 상한 초과·만료된 잠금의 예외
   - 이벤트: 저장이 실패하면 핸들러가 실행되지 않음, 같은 이벤트를 두 번
     받아도 결과가 한 번과 같음(멱등), 상한에 닿은 이벤트가 보류 목록으로
     옮겨짐(설계가 상한을 정했을 때)
   - 페이크도 이 동작을 흉내 낸다 — 메모리 리포지토리 페이크가 버전을 비교한다.

### 8.2 테스트 명세와의 연결

1. **`test-spec.md` 백엔드 매트릭스의 `T-1NN` 행 하나에 테스트 하나 이상.**
   테스트 이름이나 설명에 `T-1NN`을 그대로 적어 grep으로 찾을 수 있게 한다.
2. `sequence-diagram.md`의 `alt` 실패 분기마다 테스트가 하나 이상 있어야
   한다. 매트릭스에 없는 분기를 발견하면 테스트를 쓰고 완료 리포트의
   "명세 외 테스트"에 남긴다.
3. 매트릭스에 없는 도메인 단위 테스트(불변식, 값 객체)는 자유롭게 추가한다.
   T-ID를 지어내지 않는다.

### 8.3 작성 순서와 형식

1. 계층마다 **테스트를 먼저 쓰고 실패를 확인한 뒤** 구현한다.
2. 본문은 Given / When / Then으로 나눈다.
3. 실패하거나 건너뛴(skip) 테스트가 있는 `T-1NN`은 `구현됨`으로 표시하지
   않는다.

## 9. 실용적 타협과 기록

완전한 DIP와 순수한 도메인을 고집하지 않아도 된다 — 저장 기술은 거의
바뀌지 않고, 구현 편의도 변경 유연성만큼 중요하다. **다만 타협은 반드시
보이게 한다.**

허용되는 타협의 예:

- ORM 엔티티를 도메인 모델로 겸용 (`erd.md`가 "도메인 모델 = 영속성 모델"로
  정한 경우)
- 응용 계층에서 프레임워크의 트랜잭션 데코레이터·애너테이션 사용
- 값 객체 컬렉션을 위해 개념상 값을 엔티티로 매핑
- 저장소가 삽입 시점에만 식별자를 정해 팩토리가 식별자를 받지 못함 (§3.1.9)
- 팀 표준이나 기술 제약으로 한 트랜잭션에서 두 애그리거트를 바꿈 (§4.4.2)

규칙:

1. 타협마다 `layered-architecture.md`의 `## 규약 예외` 표에 행을 더한다 —
   출발, 도착, **예외 사유**. 사유 없는 예외는 설계 결함이므로 타협하지
   않고 코드를 고친다.
2. 기록은 사용자 동의를 받은 뒤에 한다. 단계별 모드에서는 해당 단계의 리뷰
   게이트에서, 연속 모드에서는 완료 리포트에서 확인받는다.
3. 기록하지 않은 타협은 §10 자체 검토에서 위반으로 센다.
