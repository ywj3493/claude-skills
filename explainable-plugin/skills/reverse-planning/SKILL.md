# reverse-planning

설계 문서가 **어떻게**를 이미 기록했다면, 이 스킬은 그로부터 **무엇을**을
역산한다.

역방향 파이프라인의 마지막 단계다. 코드가 이미 있는 상태에서 요구사항을
먼저 쓰려고 하면 근거 없이 추측하게 된다. 설계 문서에서 코드가 실제로
강제하는 것을 확인한 뒤에야 요구사항을 말할 수 있다.

## 사용 시점

- `reverse-design-backend` 또는 `reverse-design-frontend`가 끝난 뒤
- "요구사항 역산해줘", "코드에서 유저 스토리 뽑아줘"
- 계획과 구현이 얼마나 벌어졌는지 확인해야 할 때

## 사용하지 않는 경우

- **설계 문서가 없는 경우** — 역산할 대상이 없다. 역방향 설계 스킬을 먼저
  실행한다.
- **코드가 없는 새 기능** — `init-planning`을 쓴다.
- **설계 문서가 필요한 경우** — 역방향 설계 스킬의 일이다.

## 이 스킬의 실패 모드

**설계 문서를 한국어로 바꿔 쓰기만 하는 것**이다. 아래 세 규칙이 그것을
막는다.

### 규칙 1: 인용은 코드를 가리킨다

`FR-01`이 `design/backend/sequence-diagram.md:88`을 인용하면 검증기가 문서를
문서로 검증하게 되어 근거 사슬이 끊긴다.

설계 문서는 `## 관련 문서`의 링크로만 등장한다. **모든 `[REF: ...]`는 소스
코드 파일을 가리켜야 한다.**

설계 문서는 어디를 읽어야 할지 알려주는 **지도**다. 근거 자체가 아니다.

### 규칙 2: 유저 스토리는 (액터, 능력) 단위다

오퍼레이션 단위가 아니다. `US 개수 ≈ 오퍼레이션 개수`가 되면 설계를
되풀이한 것이므로 통합한다.

액터에게 의미 없는 CRUD 스캐폴딩은 묶거나 버린다. "주문을 조회한다",
"주문을 수정한다", "주문을 삭제한다"가 각각 스토리가 아니라, "주문을
관리한다"가 하나의 스토리일 수 있다.

### 규칙 3: 기술 중립성 스왑 테스트

`requirements.md`와 `user-stories.md`의 모든 문장을 문장 단위로 검사한다.
Python을 Java로, REST를 GraphQL로, PostgreSQL을 MongoDB로 바꿔도 문장이
그대로 참이어야 한다.

`[REF: ...]` 인용은 예외다 — 기술 내용이 아니라 출처 표시다.

## 도출 계약

무엇을 근거로 무엇을 뽑는지의 대응이다. 이 표를 벗어나 추측하지 않는다.

| 근거 (코드) | 도출 대상 | 인용 |
|---|---|---|
| 검증 로직, 가드, 권한 체크, 비즈니스 규칙 분기 | FR | `[REF: 경로:줄번호]` |
| 타임아웃, 재시도 횟수, 레이트 리밋, 캐시 TTL, 인덱스, 커넥션 풀, SLO·알림 임계값 | NFR | `[REF: 경로:줄번호]` (설정 파일) |
| 진입점 + 인증 역할 (액터 단위로 묶음) | US | `[REF: 경로:줄번호]` |
| 시퀀스 다이어그램의 에러 분기와 응답 코드 | AC | `[REF: 경로:줄번호]` |
| 진입점 정의와 요청·응답 스키마 | 인터페이스 계약 | `[REF: 경로:줄번호]` |

**"진입점이 존재한다"는 요구사항이 아니다.** 그 진입점이 무엇을 거부하고
무엇을 허용하는지가 요구사항이다.

## 실행 규약

1. **템플릿은 필수다.** 없으면 없는 경로를 보고하고 멈춘다.

2. **설계 문서를 디스크에서 읽되, 인용은 코드에서 다시 확인한다.** 설계
   문서의 `[REF: ...]`를 그대로 복사하지 말고, 그 위치를 직접 열어 기획
   관점에서 무엇을 말하는지 확인한 뒤 인용한다.

3. **순방향 기획 문서를 덮어쓰지 않는다.** 판별 방법과 처리는 단계 1에
   있다.

4. **ID는 부여하는 것이지 추측하는 것이 아니다.** `FR-<영역>-NN`,
   `NFR-<분류>-NN`, `US-NN`, `AC-USNN-NN`, `UC-<영역>-NN` 형식을 그대로 쓴다.

5. **`UC-`는 조건부다.** 액터 2인 이상 또는 외부 시스템이 관여할 때만
   만든다. 역방향에서 US와 UC를 둘 다 뽑으면 거의 같은 문서가 두 벌 나온다.

6. **`## 읽은 소스` 원장을 모든 문서에 넣는다.** 코드를 인용하므로 필요하다.

7. **없는 테스트를 지어내지 않는다.** 커버되지 않은 인수 기준은 `미구현`으로
   표시한다. 그것이 정확한 정보다.

8. **미해결 항목이 남아 있으면 완료를 보고하지 않는다.**

## 산출물

docs/<원본 언어>/specifications/
├── domain-map.md                       # 도메인 간 통합 계약, 도메인 횡단 흐름
└── <도메인>/

    │   ├── user-stories.md
    │   ├── api-interface.md

    │   └── reverse-diff.md             # 순방향 문서가 있을 때만

## 단계별 지침

### 단계 0: 환경 감지와 선행 문서 확인

1. **문서 환경 감지.** `docs/config.yml`을 읽어 `source_language`를 정한다.
   절차는 다른 역방향 스킬과 동일하다.

2. **분석 기준 커밋을 확정한다.** `git rev-parse HEAD`. 설계 문서의
   `분석 기준 커밋`과 다르면 경고한다:

   > 설계 문서의 기준 커밋(`<sha1>`)과 현재 HEAD(`<sha2>`)가 다릅니다.
   > 설계 문서가 낡았을 수 있습니다. 역방향 설계 스킬을 다시 실행한 뒤
   > 진행하는 것을 권합니다. 그래도 계속할까요?

3. **선행 설계 문서를 확인한다.** 없으면 멈춘다:

   > `<도메인>/design/`에 설계 문서가 없습니다. 이 스킬은 설계 문서를
   > 입력으로 받습니다.
   >
   > - 백엔드: `/explainable:reverse-design-backend`
   > - 프론트엔드: `/explainable:reverse-design-frontend`
   >
   > 를 먼저 실행해 주세요.

4. **리뷰 모드를 확인한다** (`단계별` 기본 / `연속`).

### 단계 1: 순방향 문서 판별

기존 `requirements.md` / `user-stories.md`가 있으면 **순방향 산출물인지
역방향 산출물인지 판별한다.**

**판별 기준**: `## 읽은 소스` 원장의 유무. 순방향 스킬은 이 섹션을
생성하지 않는다.

| 판별 | 처리 |
|---|---|
| 역방향 산출물 | 단계 0의 재실행 정책에 따라 폐기 후 재생성 |
| **순방향 산출물** | **덮어쓰지 않는다.** 차이 리포트를 만든다 |
| 없음 | 새로 생성 |

**순방향 산출물이면:**

> `<도메인>/planning/`의 문서가 순방향으로 작성된 것으로 보입니다
> (`## 읽은 소스` 원장이 없음). 사람이 결정한 기획을 코드에서 역산한
> 내용으로 덮어쓰지 않겠습니다.
>
> 대신 `<도메인>/planning/reverse-diff.md`에 계획과 구현의 차이를
> 기록하겠습니다. 진행할까요?

`reverse-diff.md`에 담을 것:

- **계획에는 있으나 코드에 근거가 없는 FR** — 미구현이거나, 구현되었으나
  찾지 못했거나, 요구사항이 폐기된 것
- **코드에는 있으나 계획에 없는 동작** — 계획 없이 추가된 기능. 사람이
  판단해야 할 사안이므로 눈에 띄게 기록한다
- **계획과 다르게 구현된 부분** — 계획의 문장과 코드의 실제 동작을 나란히
  놓고 인용을 붙인다

이것이 계획과 구현의 표류를 잡아내는 유일한 지점이다.

### 단계 2: 요구사항 역산

**산출**: `<도메인>/planning/requirements.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/planning/requirements.md`

1. **설계 문서를 지도로 삼아 코드를 읽는다.** `sequence-diagram.md`의
   `Note`와 `domain-model.md`의 불변식이 어느 파일을 봐야 하는지 알려준다.

2. **기능 요구사항은 검증·가드·분기에서 뽑는다.**
   - 입력 검증이 거부하는 조건 → 그 조건을 만족해야 한다는 요구사항
   - 권한 체크 → 누가 무엇을 할 수 있는지의 요구사항
   - 비즈니스 규칙 분기 → 상황별로 달라지는 동작의 요구사항
   - 도메인 모델의 불변식 → 항상 참이어야 하는 조건

   각각을 **직접 코드에서 확인하고 인용한다.** 설계 문서를 인용하지 않는다.

3. **비기능 요구사항은 설정값에서 뽑는다.** `infrastructure.md`의
   `tunables`에 모아둔 값들이 출발점이다. **수치를 그대로 옮긴다.**
   측정 기준과 목표값을 채울 수 없으면 그것은 NFR이 아니므로 넣지 않는다.

4. **이해관계자를 식별한다.** 인증 역할, 진입점 접근 제어, 외부 호출자에서
   액터를 도출한다. 사람이 아닌 주체(스케줄러, 외부 시스템)도 액터다.

5. **스왑 테스트를 문장 단위로 적용한다.** 통과하지 못하는 문장을 고친다.
   `[REF: ...]`는 예외다.

6. **의도를 추론한 섹션에 배너를 넣는다:**
   "이 섹션은 코드에서 추론한 내용입니다 — 이해관계자와 확인이 필요합니다."

7. **`## 범위 밖`을 채운다.** 코드에 없는데 있을 법한 기능을
   `[ASSUMED: ...]`로 기록한다. 비어 있으면 범위를 확인하지 않은 것이다.

> **단계 2 완료**: 요구사항을 역산했습니다. 검토 후 유저 스토리로
> 진행할까요?

### 단계 3: 유저 스토리 역산

**산출**: `<도메인>/planning/user-stories.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/planning/user-stories.md`

1. **(액터, 능력) 쌍을 먼저 만든다.** 진입점 목록을 액터별로 묶고, 같은
   액터가 같은 목적으로 쓰는 진입점들을 하나의 능력으로 통합한다.

2. **`US 개수 ≈ 오퍼레이션 개수`인지 확인한다.** 그렇다면 통합이 부족한
   것이므로 다시 묶는다.

3. **"~하기 위해" 목적절은 기본이 `[ASSUMED: ...]`다.** 코드에서 의도를
   읽을 수 없기 때문이다. 주석, 문서, 커밋 메시지에 의도가 실제로 적혀
   있고 그것을 읽었을 때만 `[REF: ...]`를 쓴다.

4. **인수 기준은 에러 분기와 응답 코드에서 뽑는다.**
   `sequence-diagram.md`의 `alt` 블록과 `api-interface.md`의 오류 코드가
   출발점이지만, **각각을 코드에서 다시 확인하고 인용한다.**

   Given/When/Then으로 쓰고 테스트로 옮길 수 있어야 한다. 정상 경로만 쓰지
   말고 실패·경계 조건을 반드시 포함한다.

5. **다중 액터 흐름은 조건부다.** 액터 2인 이상 또는 외부 시스템이 관여할
   때만 `UC-<영역>-NN`을 만든다. 조건에 맞지 않으면 섹션과 목차 항목을
   통째로 삭제한다.

6. **`흐름 키` 항목에 설계 문서의 `FLOW-` 키를 채운다.**

> **단계 3 완료**: 유저 스토리를 역산했습니다. 검토 후 인터페이스 계약으로
> 진행할까요?

### 단계 4: 인터페이스 계약

**산출**: `<도메인>/planning/api-interface.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/planning/api-interface.md`

1. `architecture.md`의 스택 표에서 **감지된 API 스타일**을 읽는다.
2. 템플릿의 계약 블록 중 **해당하는 형식만 남기고 나머지는 통째로
   삭제한다.** 여러 스타일이 섞여 있으면 블록을 여럿 남긴다.
3. **실제 진입점 정의에서 계약을 뽑는다.** 경로·메서드·스키마·상태 코드를
   코드에서 읽고 각각 인용한다.
4. **스키마 정의 파일이 이미 저장소에 있으면 그것을 인용해 재사용한다.**
   손으로 옮겨 적으면 곧 어긋난다.
5. 오류 모델을 한 번만 정의하고 계약 블록이 참조하게 한다.
6. 인가 표에서 공개 오퍼레이션도 "인증 불필요"로 명시한다.
7. 스키마 필드 이름은 코드의 실제 이름을 쓴다. `glossary.md`와 다르면
   그 사실을 용어집 비고에 기록한다.

### 단계 5: 도메인 간 통합 계약과 횡단 흐름

**산출**: `specifications/domain-map.md`의 `## 도메인 간 통합 계약`과
`## 도메인 횡단 흐름`

도메인이 하나뿐이면 건너뛴다.

1. **설계 단계에서 만든 `## 백엔드 컨텍스트 맵`의 엣지를 사용자 관점의
   통합 계약으로 승격한다.** 컨텍스트 맵은 "어떤 코드가 어떤 코드를
   부르는가"이고, 통합 계약은 "어떤 도메인이 다른 도메인에 무엇을
   보장하는가"다.

2. **`계약 위치`는 실제 파일이나 문서 앵커를 가리킨다.** "API를 통해"
   같은 말은 계약이 아니다.

3. **`실패 시 동작`은 코드에 근거가 있을 때만 적는다.** 보상 트랜잭션,
   사가, 재시도 정책이 코드에 있으면 인용과 함께 기록한다.

4. **도메인 횡단 흐름을 만든다.** 두 도메인 이상을 지나는 흐름에
   `FLOW-CROSS-<슬러그>` 키를 부여한다. 도메인을 참여자로 삼아 한 단계
   위에서 그리고, **각 구간은 해당 도메인의 `FLOW-` 키를 참조만 한다.**
   다이어그램을 복제하지 않는다.

5. **다른 스킬이 쓴 섹션(컨텍스트 맵, 슬라이스 의존 맵)은 바이트 단위로
   보존한다.**

### 단계 6: 추적성 매트릭스

**산출**: `<도메인>/planning/traceability.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/planning/traceability.md`

1. 세 조인 표를 채운다: 요구사항 → 스토리, 스토리 → 흐름,
   인수 기준 → 테스트.
2. **설계 문서의 `FLOW-` 키로 조인한다.** 설계 문서를 다시 열어 키를
   고치지 않는다 — 이미 `citation-verifier` 검증을 통과한 문서다.
3. **`## 미연결 항목`을 정직하게 채운다.** 특히
   `### 요구사항에 없는 코드 동작`이 중요하다 — 계획에 없던 기능이
   구현되어 있다는 뜻이며 사람이 판단해야 할 사안이다.
4. 이 문서는 **조인 테이블**이다. 다른 문서의 내용을 옮겨 적지 않는다.
   설명을 쓰고 싶어지면 그건 원본 문서에 있어야 할 내용이다.

### 단계 7: 테스트 명세

**산출**: `<도메인>/verification/test-spec.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/verification/test-spec.md`

1. **기존 테스트 코드를 찾아 인수 기준에 대응시킨다.** 찾은 테스트는
   `상태: 구현됨`과 `[REF: 경로:줄번호]`를, 못 찾은 것은 `상태: 미구현`과
   빈 근거를 쓴다.
2. **T-ID 대역**: 백엔드 `T-1NN`, 프론트엔드 `T-2NN`, E2E `T-3NN`.
3. **없는 테스트를 지어내지 않는다.** 이것이 이 단계의 핵심이다.
4. **`## 커버리지 공백`을 정직하게 채운다.** 특히
   `### 인수 기준에 대응하지 않는 테스트` — 테스트는 있으나 어느 인수
   기준과도 연결되지 않는 것을 기록한다.
5. 모킹 경계 표는 실제 테스트 코드에서 무엇을 대역으로 쓰는지 확인해
   채운다.

### 단계 8: 검증과 수정 루프

1. **생성한 문서마다 `citation-verifier`를 한 번씩 호출한다.**

2. **`reverse-planning` 특유의 검사를 추가로 확인한다:**
   - **모든 `[REF: ...]`가 소스 코드를 가리키는가.** 설계 문서(`.md`)를
     가리키는 인용이 하나라도 있으면 규칙 1 위반이므로 고친다.
   - `US` 개수가 오퍼레이션 개수와 비슷하지 않은가 (규칙 2)
   - 스왑 테스트를 통과하는가 (규칙 3)

3. **수정 루프:** `MISMATCHED`와 `UNSUPPORTED`만 고치고, `MATCHED`와
   `EXCLUDED`는 건드리지 않는다. 깨끗해질 때까지 다시 호출한다.

4. **결정적 검사도 실행한다:**

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-docs.sh" docs/<원본 언어>/specifications
   ```

5. **미해결 항목이 남아 있으면 완료를 보고하지 않는다.**

### 단계 9: 문서 인덱스와 완료 리포트

1. `specifications/README.md`에서 **이 도메인의 행만** 갱신한다.
   `생성 방식` 열을 `역방향`으로 표시한다. 다른 도메인의 행은 보존한다.

2. 완료 리포트:
   - 생성한 파일 경로 (디스크에서 확인한 것만)
   - 문서별 `citation-verifier` 최종 집계
   - `check-docs.sh` 결과
   - **미해결 항목 개수**
   - **`reverse-diff.md`를 만들었다면 그 요약** — 계획에 없던 코드 동작
     개수와 코드에 근거 없는 계획 항목 개수
   - **커버리지 공백 요약** — 테스트가 없는 인수 기준 개수
   - 다음 단계 안내:

     > 역방향 문서화가 끝났습니다.
     >
     > - 아직 문서화하지 않은 도메인이 있으면 역방향 설계 스킬을 다시
     >   실행하세요.
     > - 번역 미러가 필요하면 `/explainable:translate-docs`

## 문서 규칙

- 모든 문서는 한국어로 쓴다. 코드 블록, 파일 경로, 식별자는 영어 그대로 둔다.
- **`requirements.md`와 `user-stories.md`는 기술 중립이다.** 프레임워크
  이름, 경로, 타입 시그니처, 테이블 이름이 들어가지 않는다.
  `api-interface.md`만 예외다.
- 기계용 토큰은 영문 고정이다: `[REF: ...]`, `[ASSUMED: ...; basis: ...]`,
  `MATCHED`/`MISMATCHED`/`UNSUPPORTED`/`EXCLUDED`, 모든 ID 접두사.
- `## 문서 정보` 표는 하단에 두고 **`분석 기준 커밋`을 반드시 채운다.**
- 날짜는 `date +%F`로 얻는다.
- 내비게이션 링크는 `${CLAUDE_PLUGIN_ROOT}/references/document-order.md`를
  따른다.
- 병합 전용 문서에서 자기 소유가 아닌 섹션은 바이트 단위로 보존한다.
- 증거가 없거나 해당하지 않는 섹션은 비워 두지 말고 제목까지 삭제한다.
