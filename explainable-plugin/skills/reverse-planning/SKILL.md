# reverse-planning

설계 문서가 **어떻게**를 이미 기록했다면, 이 스킬은 그로부터 **무엇을**을
역산한다. 역방향 파이프라인의 마지막 단계다.

**시작 전에 로드한다**:
`${CLAUDE_PLUGIN_ROOT}/references/common-rules.md` ·
`${CLAUDE_PLUGIN_ROOT}/references/reverse-rules.md` ·
`${CLAUDE_PLUGIN_ROOT}/references/planning-rules.md`

## 사용 시점

- `reverse-design-backend` 또는 `reverse-design-frontend`가 끝난 뒤
- "요구사항 역산해줘", "코드에서 유저 스토리 뽑아줘"
- 계획과 구현이 얼마나 벌어졌는지 확인해야 할 때

## 사용하지 않는 경우

- **설계 문서가 없는 경우** — 역방향 설계 스킬을 먼저 실행한다.
- **코드가 없는 새 기능** — `init-planning`
- **설계 문서가 필요한 경우** — 역방향 설계 스킬

## 이 스킬의 실패 모드

**설계 문서를 한국어로 바꿔 쓰기만 하는 것**이다. 아래 세 규칙이 그것을
막는다.

### 규칙 1: 인용은 코드를 가리킨다

`FR-01`이 `design/backend/sequence-diagram.md:88`을 인용하면 검증기가 문서를
문서로 검증하게 되어 근거 사슬이 끊긴다. 설계 문서는 `## 관련 문서`의
링크로만 등장한다. **모든 `[REF: ...]`는 소스 코드 파일을 가리켜야 한다.**

설계 문서는 어디를 읽어야 할지 알려주는 **지도**다. 근거 자체가 아니다.

### 규칙 2: 유저 스토리는 (액터, 능력) 단위다

오퍼레이션 단위가 아니다. `US 개수 ≈ 오퍼레이션 개수`가 되면 설계를
되풀이한 것이므로 통합한다. 액터에게 의미 없는 CRUD 스캐폴딩은 묶거나
버린다 — "주문을 조회한다", "주문을 수정한다", "주문을 삭제한다"가 각각
스토리가 아니라 "주문을 관리한다"가 하나의 스토리일 수 있다.

### 규칙 3: 기술 중립성 스왑 테스트

`planning-rules.md` §2를 문장 단위로 적용한다.

## 도출 계약

무엇을 근거로 무엇을 뽑는지의 대응이다. 이 표를 벗어나 추측하지 않는다.

| 근거 (코드) | 도출 대상 | 인용 |
|---|---|---|
| 검증 로직, 가드, 권한 체크, 비즈니스 규칙 분기 | FR | `[REF: 경로:줄번호]` |
| 타임아웃, 재시도 횟수, 레이트 리밋, 캐시 TTL, 인덱스, 커넥션 풀, SLO·알림 임계값 | NFR | `[REF: 경로:줄번호]` (설정 파일) |
| 진입점 + 인증 역할 (액터 단위로 묶음) | US | `[REF: 경로:줄번호]` |
| 시퀀스 다이어그램의 에러 분기와 응답 코드 | AC | `[REF: 경로:줄번호]` |
| 진입점 정의와 요청·응답 스키마 | 인터페이스 계약 | `[REF: 경로:줄번호]` |

**"진입점이 존재한다"는 요구사항이 아니다.** 그 진입점이 무엇을 거부하고
무엇을 허용하는지가 요구사항이다.

## 실행 규약

`common-rules.md` 실행 규약 1~9, `reverse-rules.md`, `planning-rules.md`를
전부 따른다. 이 스킬 고유 항목:

1. **설계 문서를 디스크에서 읽되, 인용은 코드에서 다시 확인한다.** 설계
   문서의 `[REF: ...]`를 그대로 복사하지 말고, 그 위치를 직접 열어 기획
   관점에서 무엇을 말하는지 확인한 뒤 인용한다 (규칙 1).
2. **순방향 기획 문서를 덮어쓰지 않는다** — 판별과 처리는 단계 1.
3. **없는 테스트를 지어내지 않는다.** 커버되지 않은 인수 기준은 `미구현`으로
   표시한다. 그것이 정확한 정보다.

## 단계별 지침

### 단계 0: 환경 감지와 선행 문서 확인

1. `common-rules.md` §1 — 문서 환경 감지, 분석 기준 커밋 확정, 리뷰 모드.
2. 설계 문서의 `분석 기준 커밋`과 현재 HEAD가 다르면 경고한다:

   > 설계 문서의 기준 커밋(`<sha1>`)과 현재 HEAD(`<sha2>`)가 다릅니다.
   > 설계 문서가 낡았을 수 있습니다. 역방향 설계 스킬을 다시 실행한 뒤
   > 진행하는 것을 권합니다. 그래도 계속할까요?

3. **선행 설계 문서를 확인한다.** 없으면 멈춘다:

   > `<도메인>/design/`에 설계 문서가 없습니다. 이 스킬은 설계 문서를
   > 입력으로 받습니다.
   >
   > - 백엔드: `/explainable:reverse-design-backend`
   > - 프론트엔드: `/explainable:reverse-design-frontend`
   >
   > 를 먼저 실행해 주세요.

### 단계 1: 순방향 문서 판별

기존 `requirements.md` / `user-stories.md`가 있으면 **순방향 산출물인지
역방향 산출물인지 판별한다.**

**판별 기준**: `## 읽은 소스` 원장의 유무. 순방향 스킬은 이 섹션을
생성하지 않는다.

| 판별 | 처리 |
|---|---|
| 역방향 산출물 | `reverse-rules.md` §3의 재실행 정책에 따라 폐기 후 재생성. **폐기 범위는 이 도메인의 역방향 `planning/**`** |
| **순방향 산출물** | **덮어쓰지 않는다.** 차이 리포트를 만든다 |
| 없음 | 새로 생성 |

**순방향 산출물이면:**

> `<도메인>/planning/`의 문서가 순방향으로 작성된 것으로 보입니다
> (`## 읽은 소스` 원장이 없음). 사람이 결정한 기획을 코드에서 역산한
> 내용으로 덮어쓰지 않겠습니다.
>
> 대신 `<도메인>/planning/reverse-diff.md`에 계획과 구현의 차이를
> 기록하겠습니다. 진행할까요?

`reverse-diff.md`에 담을 것:

- **계획에는 있으나 코드에 근거가 없는 FR** — 미구현이거나, 구현되었으나
  찾지 못했거나, 요구사항이 폐기된 것
- **코드에는 있으나 계획에 없는 동작** — 계획 없이 추가된 기능. 사람이
  판단해야 할 사안이므로 눈에 띄게 기록한다
- **계획과 다르게 구현된 부분** — 계획의 문장과 코드의 실제 동작을 나란히
  놓고 인용을 붙인다

이것이 계획과 구현의 표류를 잡아내는 유일한 지점이다.

### 단계 2: 요구사항 역산

**산출** `<도메인>/planning/requirements.md` ·
**템플릿** `templates/planning/requirements.md`

1. **설계 문서를 지도로 삼아 코드를 읽는다.** `sequence-diagram.md`의
   `Note`와 `domain-model.md`의 불변식이 어느 파일을 봐야 하는지 알려준다.
2. **기능 요구사항은 검증·가드·분기에서 뽑는다** — 입력 검증이 거부하는
   조건, 권한 체크, 비즈니스 규칙 분기, 도메인 모델의 불변식. 각각을 **직접
   코드에서 확인하고 인용한다** (규칙 1).
3. **비기능 요구사항은 설정값에서 뽑는다.** `infrastructure.md`의 `tunables`가
   출발점이다. **수치를 그대로 옮긴다.** 측정 기준과 목표값을 채울 수 없으면
   NFR이 아니므로 넣지 않는다.
4. **이해관계자를 식별한다.** 인증 역할, 진입점 접근 제어, 외부 호출자에서
   액터를 도출한다.
5. 스왑 테스트를 통과하지 못하는 문장을 고친다 (규칙 3).
6. **의도를 추론한 섹션에 배너를 넣는다** (`reverse-rules.md` §1.4).
7. **`## 범위 밖`을 채운다.** 코드에 없는데 있을 법한 기능을
   `[ASSUMED: ...]`로 기록한다. 비어 있으면 범위를 확인하지 않은 것이다.

> **단계 2 완료**: 요구사항을 역산했습니다. 검토 후 유저 스토리로
> 진행할까요?

### 단계 3: 유저 스토리 역산

**산출** `<도메인>/planning/user-stories.md` ·
**템플릿** `templates/planning/user-stories.md`

1. **(액터, 능력) 쌍을 먼저 만든다** (규칙 2). 진입점 목록을 액터별로 묶고,
   같은 액터가 같은 목적으로 쓰는 진입점들을 하나의 능력으로 통합한다.
2. **`US 개수 ≈ 오퍼레이션 개수`인지 확인한다.** 그렇다면 통합이 부족한
   것이므로 다시 묶는다.
3. **"~하기 위해" 목적절은 기본이 `[ASSUMED: ...]`다.** 코드에서 의도를 읽을
   수 없기 때문이다. 주석·문서·커밋 메시지에 의도가 실제로 적혀 있고 그것을
   읽었을 때만 `[REF: ...]`를 쓴다.
4. **인수 기준은 에러 분기와 응답 코드에서 뽑는다.** `sequence-diagram.md`의
   `alt` 블록과 `api-interface.md`의 오류 코드가 출발점이지만, **각각을
   코드에서 다시 확인하고 인용한다** (규칙 1). 형식은 `planning-rules.md` §4.
5. **`흐름 키` 항목에 설계 문서의 `FLOW-` 키를 채운다.**

> **단계 3 완료**: 유저 스토리를 역산했습니다. 검토 후 인터페이스 계약으로
> 진행할까요?

### 단계 4: 인터페이스 계약

**산출** `<도메인>/planning/api-interface.md` ·
**템플릿** `templates/planning/api-interface.md`

`planning-rules.md` §5를 따르되, 역방향이므로:

1. **실제 진입점 정의에서 계약을 뽑는다.** 경로·메서드·스키마·상태 코드를
   코드에서 읽고 각각 인용한다.
2. **스키마 정의 파일이 이미 저장소에 있으면 그것을 인용해 재사용한다.**
   손으로 옮겨 적으면 곧 어긋난다.
3. 스키마 필드 이름은 코드의 실제 이름을 쓴다. `glossary.md`와 다르면 그
   사실을 용어집 비고에 기록한다.

### 단계 5: 도메인 간 통합 계약과 횡단 흐름

**산출** `specifications/domain-map.md`의 `## 도메인 간 통합 계약`,
`## 도메인 횡단 흐름`

도메인이 하나뿐이면 건너뛴다 (`common-rules.md` §6.6).

1. **설계 단계에서 만든 `## 백엔드 컨텍스트 맵`의 엣지를 사용자 관점의 통합
   계약으로 승격한다.** 컨텍스트 맵은 "어떤 코드가 어떤 코드를 부르는가"이고,
   통합 계약은 "어떤 도메인이 다른 도메인에 무엇을 보장하는가"다.
2. **`계약 위치`는 실제 파일이나 문서 앵커를 가리킨다.** "API를 통해" 같은
   말은 계약이 아니다.
3. **`실패 시 동작`은 코드에 근거가 있을 때만 적는다.** 보상 트랜잭션·사가·
   재시도 정책이 코드에 있으면 인용과 함께 기록한다.
4. **도메인 횡단 흐름**에 `FLOW-CROSS-<슬러그>` 키를 부여한다. 도메인을
   참여자로 삼아 한 단계 위에서 그리고, **각 구간은 해당 도메인의 `FLOW-`
   키를 참조만 한다.** 다이어그램을 복제하지 않는다.
5. 다른 스킬이 쓴 섹션은 바이트 단위로 보존한다 (계약 6).

### 단계 6: 추적성 매트릭스

**산출** `<도메인>/planning/traceability.md` ·
**템플릿** `templates/planning/traceability.md`

`planning-rules.md` §6을 따른다.

1. 세 조인 표를 채운다: 요구사항 → 스토리, 스토리 → 흐름, 인수 기준 → 테스트.
2. **설계 문서의 `FLOW-` 키로 조인한다.** 설계 문서를 다시 열어 키를 고치지
   않는다 — 이미 `citation-verifier` 검증을 통과한 문서다.
3. **`## 미연결 항목`을 정직하게 채운다.** 특히
   `### 요구사항에 없는 코드 동작`이 중요하다 — 계획에 없던 기능이 구현되어
   있다는 뜻이며 사람이 판단해야 할 사안이다.

### 단계 7: 테스트 명세

**산출** `<도메인>/verification/test-spec.md` ·
**템플릿** `templates/verification/test-spec.md`

1. **기존 테스트 코드를 찾아 인수 기준에 대응시킨다.** 찾은 테스트는
   `상태: 구현됨`과 `[REF: 경로:줄번호]`를, 못 찾은 것은 `상태: 미구현`과
   빈 근거를 쓴다.
2. T-ID 대역은 `planning-rules.md` §1을 따른다.
3. **없는 테스트를 지어내지 않는다.** 이것이 이 단계의 핵심이다.
4. **`## 커버리지 공백`을 정직하게 채운다.** 특히
   `### 인수 기준에 대응하지 않는 테스트` — 테스트는 있으나 어느 인수 기준
   과도 연결되지 않는 것을 기록한다.
5. 모킹 경계 표는 실제 테스트 코드에서 무엇을 대역으로 쓰는지 확인해 채운다.

### 단계 8: 검증과 수정 루프

`common-rules.md` §3의 인용 검증과 결정적 검사를 실행한다. 이 스킬 특유의
추가 확인:

- **모든 `[REF: ...]`가 소스 코드를 가리키는가.** 설계 문서(`.md`)를 가리키는
  인용이 하나라도 있으면 규칙 1 위반이므로 고친다.
- `US` 개수가 오퍼레이션 개수와 비슷하지 않은가 (규칙 2)
- 스왑 테스트를 통과하는가 (규칙 3)

### 단계 9: 문서 인덱스와 완료 리포트

1. `specifications/README.md`에서 **이 도메인의 행만** 갱신하고 `생성 방식`
   열을 `역방향`으로 표시한다.
2. `common-rules.md` §4에 다음을 더한다: **`reverse-diff.md`를 만들었다면
   그 요약** (계획에 없던 코드 동작 개수, 코드에 근거 없는 계획 항목 개수),
   **커버리지 공백 요약** (테스트가 없는 인수 기준 개수).

   > 역방향 문서화가 끝났습니다.

   >   실행하세요.
