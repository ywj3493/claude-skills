# init-planning

코드가 없는 상태에서 **무엇을 만들 것인지** 정하는 스킬이다. 인프라와
프로젝트 설정을 먼저 확정하고, 그 위에 기획 문서를 쌓는다.

설계는 이 스킬이 하지 않는다. 기획이 끝나면 `init-design-backend`와
`init-design-frontend`가 이어받는다.

## 사용 시점

- 빈 저장소나 새 기능에서 시작할 때
- "기획 문서 만들어줘", "요구사항 정리해줘", "유저 스토리 뽑아줘"
- 프론트엔드와 백엔드가 합의할 인터페이스 계약이 필요할 때

## 사용하지 않는 경우

- **이미 코드가 있는 경우** — 코드에서 문서를 뽑아야 한다.
  `reverse-design-backend` / `reverse-design-frontend`로 설계를 먼저 뽑고
  `reverse-planning`으로 기획을 역산한다.
- **설계 문서가 필요한 경우** — 도메인 모델, ERD, 시퀀스 다이어그램,
  컴포넌트 구조는 `init-design-backend` / `init-design-frontend`의 일이다.
- **문서 구조 전체를 초기화해야 하는 경우** — 이 플러그인은 출력 경로만
  최소로 만든다. `docs/` 전체 스캐폴딩이 필요하면 `/dev-docs:init-docs`를
  안내한다.

## 실행 규약

이 규칙들은 스킬 계약의 일부다. 어느 모델이 실행하든 결과가 같도록 작업
방식을 명시한다.

1. **템플릿은 필수다.** 각 단계는 생성 전에
   `${CLAUDE_PLUGIN_ROOT}/templates/` 아래의 템플릿 파일을 읽는다. 템플릿이
   없으면 없는 경로를 보고하고 멈춘다. 기억으로 구조를 지어내지 않는다.

2. **이전 단계 산출물은 디스크에서 다시 읽는다.** 대화에 내용이 남아 있어도
   파일을 다시 읽는다. 사용자가 단계 사이에 문서를 고쳤을 수 있다.

3. **ID는 부여하는 것이지 추측하는 것이 아니다.** `FR-<영역>-NN`,
   `NFR-<분류>-NN`, `US-NN`, `AC-USNN-NN`, `UC-<영역>-NN` 형식을 그대로 쓰고,
   한 문서 안에서 빈 번호나 중복 없이 순차로 매긴다. 다른 문서의 ID를
   참조할 때는 그 문서에 실제로 있는지 확인한 뒤 쓴다.

4. **기획 문서는 기술 중립이다.** `requirements.md`와 `user-stories.md`의
   모든 문장은 스왑 테스트를 통과해야 한다 — Python을 Java로, REST를
   GraphQL로, PostgreSQL을 MongoDB로 바꿔도 문장이 그대로 참이어야 한다.
   프레임워크 이름, 경로, 타입 시그니처, 테이블 이름은 들어가지 않는다.
   `api-interface.md`만 예외다.

5. **프레임워크는 사용자가 정한다.** 기본값(백엔드 4-Layered DDD, 프론트엔드
   FSD)은 제안하되, 사용자 결정이 항상 우선한다. 정해지지 않은 값을 임의로
   채우지 않는다.

6. **`## 읽은 소스` 섹션은 생성하지 않는다.** 코드가 없으므로 인용할 대상이
   없다. 템플릿에서 그 섹션을 제목까지 삭제한다. 이 섹션을 넣고 싶어진다면
   기존 코드를 문서화하고 있다는 뜻이므로 역방향 스킬을 써야 한다.

7. **리뷰 게이트를 문자 그대로 지킨다.** 단계별 모드(기본)에서는 각 단계
   후 멈추고 사용자 승인을 기다린다. 여러 단계를 한 턴에 몰아 처리하지
   않는다.

8. **확인한 경로만 보고한다.** 완료 리포트에는 디스크에 실제로 존재하는
   파일만 나열한다.

## 산출물

```text
docs/<원본 언어>/specifications/
├── architecture.md          # 아키텍처 규약 (스택·레이어 매핑·의존성)
├── infrastructure.md        # 런타임, 배포, 환경, CI/CD
├── glossary.md              # 한국어 용어 ↔ 영문 식별자
├── domain-map.md            # 도메인 2개 이상일 때만
├── README.md                # 도메인 인덱스
└── <도메인>/
    ├── planning/
    │   ├── requirements.md
    │   ├── user-stories.md
    │   ├── api-interface.md
    │   └── traceability.md
    └── verification/        # 이 스킬은 만들지 않는다 (설계 스킬의 일)
```

## 단계별 지침

### 단계 0: 문서 환경 감지와 범위 확인

1. **`docs/config.yml`을 읽는다.**
   - 있으면 `source_language`를 쓴다. 질문하지 않는다.
   - 없지만 `docs/<언어>/specifications/`가 있으면 추론한다
     (`reference` 제외, 애매하면 사용자에게 묻는다). 진행하고 추론 사실을
     완료 리포트에 남긴 뒤 `docs/config.yml`에 기록할지 제안한다.
   - `docs/` 자체가 없으면 한 번만 묻는다:

     > 문서 구조가 아직 없습니다. 어떻게 할까요?
     >
     > 1. `docs/ko/specifications/`에 바로 생성 (기본)
     > 2. `/dev-docs:init-docs`로 전체 문서 구조를 먼저 초기화
     > 3. 다른 경로 지정

     선택에 따라 출력 디렉터리만 만들고 진행한다.

   - **동의 없이 `docs/config.yml`, 루트 `CLAUDE.md`, `.claude/rules/`를
     쓰지 않는다.**

2. **기존 문서를 확인한다.** 대상 도메인에 이미 기획 문서가 있으면
   **덮어쓰지 않는다.** 사람이 결정한 기획을 스킬이 지울 수는 없다.
   차이를 보고하고 어떻게 할지 묻는다:

   > `<도메인>/planning/`에 이미 문서가 있습니다:
   > `<파일 목록>`
   >
   > 1. 기존 문서에 이어서 추가 (기본)
   > 2. 특정 문서만 다시 작성
   > 3. 중단

3. **도메인을 정한다.** 사용자에게 기능 영역을 묻고 도메인 구획을 제안한
   뒤 확인받는다. 최소 하나는 있어야 한다.

4. **리뷰 모드를 확인한다.**

   > 진행 방식을 선택해 주세요.
   >
   > - `단계별` (기본): 각 단계 후 검토를 받고 진행
   > - `연속`: 전체를 한 번에 생성하고 마지막에 검토

### 단계 1: 프로젝트·인프라 설정

**산출**: `specifications/infrastructure.md`, `specifications/architecture.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/overview/infrastructure.md`,
`${CLAUDE_PLUGIN_ROOT}/templates/overview/architecture.md`

기획보다 이것이 먼저다. 어떤 스택 위에서 만드는지 정해지지 않으면
인터페이스 계약의 형식조차 정할 수 없다.

1. **사용자에게 묻는다.** 정해지지 않은 항목을 추측해서 채우지 않는다.
   - 백엔드: 언어·런타임, 프레임워크, **API 스타일**, 영속성
   - 프론트엔드: 언어·런타임, 프레임워크, 라우터, 상태 관리, 렌더링 모드
   - 인프라: 배포 대상, 환경 구분, CI/CD 계획
   - 한쪽만 있는 프로젝트면 그쪽만 묻는다.

2. **아키텍처 기준선을 제안한다.**

   > 아키텍처 기준선으로 백엔드는 4-Layered DDD(Presentation / Application /
   > Domain / Infrastructure), 프론트엔드는 FSD(app / pages / widgets /
   > features / entities / shared)를 제안합니다. 이대로 갈까요, 아니면 다른
   > 구조를 쓸까요?

   사용자 결정이 우선한다.

3. **`architecture.md`의 아키텍처 규약 표 세 개를 채운다.** 이 표들이 향후
   구현 단계에서 파일 위치와 import 방향을 결정하는 근거이므로 반드시
   표 형태로 채운다. 산문으로 대체하지 않는다.
   - 스택 (근거 열은 전부 "사용자 결정")
   - 레이어·슬라이스 ↔ 디렉터리 매핑 (아직 없는 경로의 계획값)
   - 허용 의존성 방향

4. **`infrastructure.md`를 채운다.** 증거가 없어 정할 수 없는 섹션은 비워
   두지 말고 통째로 삭제한다.

5. `<!-- GENERATED-BY: init-planning; commit: <sha>; root: <경로>;
   date: <오늘> -->` 마커를 두 파일 상단에 넣는다. `분석 기준 커밋` 필드는
   "해당 없음"으로 둔다 — 순방향이므로 분석 대상 코드가 없다.

> **단계 1 완료**: 인프라와 아키텍처 규약을 작성했습니다. 검토 후 요구사항
> 단계로 진행할까요?

### 단계 2: 용어집 초기화

**산출**: `specifications/glossary.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/overview/glossary.md`

이후 모든 문서가 이 표를 참조한다. 여기서 정한 영문 식별자가 코드 심볼
이름의 단일 출처가 된다.

1. 사용자와 대화하며 핵심 도메인 개념을 추린다.
2. 각 개념에 한국어 용어와 영문 식별자를 하나씩 배정한다. 한 개념에 영문
   식별자는 하나만 둔다.
3. 정의는 한 문장으로 쓴다. 두 문장이 필요하면 개념이 둘로 쪼개져야 한다는
   신호다.
4. `근거` 열은 전부 "기획 결정", `상태` 열은 "사용 중"이다.

### 단계 3: 요구사항

**산출**: `<도메인>/planning/requirements.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/planning/requirements.md`

1. 이해관계자(액터)를 먼저 확정한다. 사람이 아닌 주체도 액터가 될 수 있다.
2. 기능 요구사항을 `FR-<영역>-NN`으로 부여한다. 한 요구사항은 한 문장으로
   검증 가능해야 한다.
3. 비기능 요구사항을 `NFR-<분류>-NN`으로 부여한다. **측정 가능한 수치가
   없으면 NFR이 아니다.** 수치를 정할 수 없으면 사용자에게 묻는다.
4. 제약 사항과 범위 밖을 채운다. 범위 밖이 비어 있으면 범위가 정해지지
   않은 것이므로 사용자에게 확인한다.
5. **스왑 테스트를 문장 단위로 적용한다.** 통과하지 못하는 문장은 고친다.
6. `## 읽은 소스` 섹션을 제목까지 삭제한다.

> **단계 3 완료**: 요구사항을 작성했습니다. 검토 후 유저 스토리로 진행할까요?

### 단계 4: 유저 스토리와 인수 기준

**산출**: `<도메인>/planning/user-stories.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/planning/user-stories.md`

1. `requirements.md`를 디스크에서 다시 읽는다.
2. 스토리를 `US-NN`으로, 인수 기준을 `AC-USNN-NN`으로 부여한다.
3. **인수 기준은 Given/When/Then으로 쓰고 테스트로 옮길 수 있어야 한다.**
   "올바르게 동작한다" 같은 문장은 인수 기준이 아니다. 정상 경로만 쓰지 말고
   실패·경계 조건을 반드시 포함한다.
4. **다중 액터 흐름은 조건부다.** 액터 2인 이상 또는 외부 시스템이 관여할
   때만 `UC-<영역>-NN`을 만든다. 조건에 맞지 않으면 섹션과 목차 항목을
   통째로 삭제한다.
5. **모든 FR이 최소 하나의 US로 커버되는지 확인한다.** 커버되지 않는 FR이
   있으면 스토리를 추가하거나, 그 FR이 정말 필요한지 사용자에게 묻는다.
6. `흐름 키` 항목은 설계 전이므로 비워 둔다.

> **단계 4 완료**: 유저 스토리를 작성했습니다. 검토 후 인터페이스 계약으로
> 진행할까요?

### 단계 5: 인터페이스 계약

**산출**: `<도메인>/planning/api-interface.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/planning/api-interface.md`

프론트엔드와 백엔드가 합의하는 계약이므로 설계보다 먼저 만든다. 설계
단계에서 만들면 두 설계 스킬이 서로 다른 계약을 만들어 버린다.

1. `architecture.md`의 스택 표에서 **확정된 API 스타일**을 읽는다.
2. 템플릿의 계약 블록 중 **해당하는 형식만 남기고 나머지는 통째로
   삭제한다.** 여러 스타일이 섞인 프로젝트만 블록을 여럿 남긴다.
   - REST/HTTP → OpenAPI 3.1 YAML
   - GraphQL → SDL
   - gRPC → `.proto` 발췌
   - 메시지·이벤트 → AsyncAPI 또는 메시지 스키마 표
3. 오퍼레이션 카탈로그를 먼저 채운다. `오퍼레이션 ID`는 프로토콜과 무관한
   안정적 식별자이며, 계약 블록과 시퀀스 다이어그램이 이 ID로 서로를
   참조한다.
4. 오류 모델을 한 번만 정의하고 계약 블록이 그것을 참조하게 한다.
   오퍼레이션마다 오류 구조를 다르게 정의하지 않는다.
5. 인가 표에서 공개 오퍼레이션도 "인증 불필요"로 명시한다. 빈 칸은
   미확인과 구분되지 않는다.
6. 스키마의 필드·타입 이름은 `glossary.md`의 영문 식별자를 따른다.

> **단계 5 완료**: 인터페이스 계약을 작성했습니다. 검토 후 다음으로
> 진행할까요?

### 단계 6: 도메인 간 통합

**산출**: `specifications/domain-map.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/overview/domain-map.md`

**도메인이 2개 이상일 때만 수행한다.** 하나뿐이면 이 단계를 건너뛰고 그
사실을 완료 리포트에 남긴다.

1. `## 도메인 목록` 섹션을 채운다.
2. `## 도메인 간 통합 계약` — 도메인 사이의 통합 지점을 표로 정리한다.
   `계약 위치`는 실제 문서 앵커를 가리켜야 한다. "API를 통해" 같은 말은
   계약이 아니다.
3. `## 도메인 횡단 흐름` — 두 도메인 이상을 지나는 흐름이 있으면
   `FLOW-CROSS-<슬러그>` 키로 만든다. 도메인을 참여자로 삼아 한 단계 위에서
   그리고, 각 구간의 상세는 설계 단계에서 부여될 `FLOW-` 키를 참조만 한다.
4. `## 백엔드 컨텍스트 맵`과 `## 프론트엔드 슬라이스 의존 맵`은 **설계
   스킬이 소유**하므로 여기서 채우지 않는다. 자리표시자 주석만 남긴다.
5. `## 패턴 범례`는 고정 표다. 그대로 두고 편집하거나 줄이지 않는다.

### 단계 7: 추적성과 자체 점검

**산출**: `<도메인>/planning/traceability.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/planning/traceability.md`

## 문서 규칙

- 모든 문서는 한국어로 쓴다. 코드 블록, 파일 경로, 식별자, 스키마는 영어
  그대로 둔다.
- 기계용 토큰은 영문 고정이다: `[REF: ...]`, `[ASSUMED: ...]`,
  `FR-`/`NFR-`/`US-`/`AC-`/`UC-`/`T-`/`FLOW-` 접두사.
- `## 문서 정보` 표는 문서 **하단**에 둔다. 상단에 메타데이터 블록을 만들지
  않는다.
- 날짜는 `date +%F`로 얻는다. 기억으로 쓰지 않는다.
- 내비게이션 링크는 `${CLAUDE_PLUGIN_ROOT}/references/document-order.md`의
  규칙을 따른다. 생성하지 않은 문서는 링크하지 않는다.
- 횡단 문서(`architecture.md`, `infrastructure.md`, `glossary.md`,
  `domain-map.md`, `README.md`)에는 이전/다음 내비게이션과 `전체 문서`
  인덱스를 붙이지 않는다.
- 병합 전용 문서에서 자기 소유가 아닌 섹션은 **바이트 단위로 보존한다**.
- 증거가 없거나 해당하지 않는 섹션은 비워 두지 말고 제목까지 삭제한다.
  빈 표는 "확인했으나 없음"과 "확인하지 않음"을 구분하지 못한다.
