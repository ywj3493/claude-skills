# reverse-design-backend

이미 동작하는 백엔드 코드에서 **실제로 무엇이 어떻게 되어 있는지**를 근거와
함께 문서로 만든다.

**순서가 이 스킬의 핵심이다.** 인프라 → 코드베이스 구조 → 도메인 →
오퍼레이션. 위에서 아래로 내려가야 각 단계가 다음 단계의 판단 근거를
제공한다. 코드부터 읽기 시작하면 어느 계층에 속한 파일인지도 모르는 채로
다이어그램을 그리게 된다.

기획 문서는 이 스킬이 만들지 않는다 — 설계가 끝난 뒤 `reverse-planning`이
그 결과로부터 요구사항과 유저 스토리를 역산한다.

**시작 전에 로드한다**:
`${CLAUDE_PLUGIN_ROOT}/references/common-rules.md` ·
`${CLAUDE_PLUGIN_ROOT}/references/reverse-rules.md`

## 사용 시점

- 인수인계받은 코드베이스를 파악해야 할 때
- "이 코드베이스 문서화해줘", "백엔드 분석해줘"
- 문서가 코드보다 오래되어 다시 만들어야 할 때

## 사용하지 않는 경우

- **코드가 아직 없는 경우** — `init-design-backend`
- **백엔드가 없는 프로젝트** — `common-rules.md` §6.1
- **프론트엔드 분석** — `reverse-design-frontend`
- **요구사항·유저 스토리가 필요한 경우** — 이 스킬을 먼저 돌리고
  `reverse-planning`을 실행한다.

## 실행 규약

`common-rules.md` 실행 규약 1~9와 `reverse-rules.md` 전체를 따른다.
인용 계약, Source-Linked 규약, 재실행 정책, 에이전트 호출 규약은
`reverse-rules.md`가 소유한다. 이 스킬 고유 항목:

1. **계층 라벨은 단계 2에서 확정한 매핑에서만 온다.** 오퍼레이션마다 라벨이
   달라지면 병합이 어긋난다.
2. **프레임워크를 추측하지 않는다.** 단계 1~2에서 감지한 API 스타일과
   진입점 파일 패턴을 에이전트 입력으로 넘긴다.
3. **리뷰 게이트 ②(오퍼레이션 선별)는 비용이 가장 큰 지점**이므로 반드시
   확인받는다.

## 단계별 지침

### 단계 0: 환경 감지와 재실행 판단

1. `common-rules.md` §1 — 문서 환경 감지, 분석 기준 커밋 확정, 리뷰 모드.
2. `reverse-rules.md` §3 — 재실행 판단. **폐기 범위는
   `<도메인>/design/backend/**`**이며, 횡단 문서와 `glossary.md`는 폐기하지
   않는다.

### 단계 1: 인프라 탐색

**산출** `specifications/infrastructure.md` ·
**템플릿** `templates/overview/infrastructure.md`

인프라가 먼저인 이유: 런타임, 배포 단위, 외부 서비스, 환경 변수를 알아야
코드에서 무엇이 경계인지 판단할 수 있다.

1. **`infra-explorer` 에이전트를 호출한다.** 저장소 루트를 넘긴다.
2. 반환된 `INFRA` 블록을 템플릿에 옮긴다. 근거를 그대로 유지한다.
3. **`tunables` 항목을 정확히 옮긴다.** 타임아웃·재시도·레이트 리밋·캐시
   TTL·임계값은 `reverse-planning`이 비기능 요구사항의 근거로 쓴다.
   반올림하거나 요약하지 않는다.
4. **환경 변수의 값을 절대 적지 않는다.** 이름·용도·필수 여부만 쓴다.
5. `not_found` 항목은 해당 섹션에 "없음 — 확인한 경로: ..."로 남긴다.
6. `<!-- GENERATED-BY: reverse-design-backend; commit: <sha>; root: <경로>;
   date: <오늘> -->` 마커를 넣는다.

> **단계 1 완료**: 인프라를 문서화했습니다. 검토 후 코드베이스 구조 분석으로
> 진행할까요?

### 단계 2: 코드베이스 구조 분석

**산출** `specifications/architecture.md`의 `## 백엔드 구조`와
`## 아키텍처 규약` 표

이 단계의 산출물이 **이후 모든 에이전트 호출의 입력**이 된다. 여기서 틀리면
모든 다이어그램의 라벨이 흔들린다.

1. **백엔드가 있는지 확인한다.** 없으면 멈춘다:

   > 이 저장소에서 백엔드 코드를 찾지 못했습니다. 확인한 경로: `<경로들>`
   > 프론트엔드 분석은 `/explainable:reverse-design-frontend`를 사용하세요.

2. **스택 표를 채운다.** 언어·런타임·프레임워크·영속성을 각각 인용한다.
3. **API 스타일과 진입점 파일 패턴을 확정한다.** 라우트 정의, 리졸버, 서비스
   정의, 메시지 컨슈머 중 무엇이 있는지 실제로 확인한다. 여러 스타일이 섞여
   있으면 전부 기록한다. 이 값이 `operation-tracer`의 입력이 된다.
4. **실측 레이어 패턴을 먼저 기술한다** (`reverse-rules.md` §5).
5. **레이어 ↔ 디렉터리 매핑 표를 채운다.** `실제 경로` 열은 반드시 실존해야
   한다. 이 표가 에이전트 호출의 핵심 입력이다.
6. **허용 의존성 표를 채우고, 실제 위반을 `## 백엔드 구조`의 위반 목록에
   기록한다** (`reverse-rules.md` §5).
7. **4-Layered DDD 대비표**를 일치 / 부분 / 없음으로 판정한다.
8. **모듈 경계를 식별한다.** 각 경계를 정하는 근거 파일을 인용한다.
9. 모노레포면 `common-rules.md` §6.2에 따라 앱·패키지 경계도 확인한다.

### 단계 3: 도메인 식별 — 리뷰 게이트 ①

1. 모듈 경계, 디렉터리 구조, 애그리거트 후보, 라우트 그룹을 근거로 도메인
   후보를 만든다.
2. **사용자에게 제시하고 확인받는다:**

   > 다음 도메인 구획을 발견했습니다:
   >
   > | 도메인 | 근거 | 오퍼레이션 수 |
   > |---|---|---|
   >
   > 이대로 진행할까요, 아니면 구획을 조정할까요?

3. 도메인이 나뉘어 있지 않으면 단일 도메인으로 진행한다. 억지로 쪼개지 않는다.

### 단계 4: 오퍼레이션 목록화와 선별 — 리뷰 게이트 ②

비용이 가장 큰 지점이다. 여기서 걸러야 60개 오퍼레이션짜리 서비스에서
60개의 똑같이 생긴 CRUD 다이어그램이 나오는 것을 막을 수 있다.

1. **도메인별로 오퍼레이션을 전부 나열한다.** 진입점 파일 패턴으로 `Grep`하고,
   각 오퍼레이션의 진입점 `경로:줄번호`와 심볼을 기록한다.

2. **선별한다.**

   | 분류 | 기준 | 처리 |
   |---|---|---|
   | 추적 대상 | 참여자 3개 이상 **또는** 분기가 있음 | `operation-tracer` 호출 |
   | 단순 통과 | 진입점 → 저장소, 분기 없음, 참여자 3개 미만 | 표 한 줄 |

3. **사용자에게 제시하고 확인받는다:**

   > `<도메인>`에서 오퍼레이션 `<N>`개를 찾았습니다.
   >
   > - 추적 대상 `<M>`개 — 시퀀스 다이어그램 생성
   > - 단순 통과 `<N-M>`개 — 표로만 기록
   >
   > `<추적 대상 목록>`
   >
   > 이대로 진행할까요? 목록을 조정할 수도 있습니다.

4. 20개 상한은 `common-rules.md` §6.3을 따른다.

### 단계 5: 오퍼레이션 추적

**산출** `<도메인>/design/backend/sequence-diagram.md` ·
**템플릿** `templates/design/backend/sequence-diagram.md`

호출 방식·`PARTIAL` 처리·별칭 재배정은 `reverse-rules.md` §4가 소유한다.

1. **에이전트에 넘기는 입력** (하나라도 빠뜨리면 결과가 어긋난다):

   | 입력 | 출처 |
   |---|---|
   | 저장소 루트 | 단계 0 |
   | 오퍼레이션 식별자 | 단계 4 |
   | 진입점 `경로:줄번호`와 심볼 | 단계 4 |
   | API 스타일, 진입점 파일 패턴 | 단계 2 |
   | 계층 ↔ 디렉터리 매핑 | 단계 2 |
   | 용어집 항목 | 현재까지 확정된 것 |
   | 도메인 이름 | 단계 3 |
   | 종료 규칙 | 외부 시스템 / 저장소 어댑터 / 호출자 반환 / 다른 도메인 진입점 |

2. **렌더링.** 각 TRACE의 `edges` 목록 하나에서 세 가지를 함께 만든다.
   간선의 어느 필드가 어디로 가는지가 정해져 있다:

   | 간선 필드 | 렌더링 결과 |
   |---|---|
   | `출발 별칭`, `도착 별칭`, 화살표 종류 | `sequenceDiagram`의 메시지 방향 |
   | `호출 표현` | 메시지 라벨 |
   | `[REF: 경로:줄번호]` | 메시지 바로 다음 줄의 `Note` |
   | `from: 경로:줄번호` + `호출 표현` + `[REF:]` | `CALLGRAPH` 한 줄 (`<from> -> <호출 표현> \| <REF 위치>`) |
   | `branches` | `alt` / `else` 블록 |

   **코드를 다시 읽어 다이어그램을 새로 그리지 않는다.**

3. **참여자 `link` 줄**을 `participants`의 `path`와 단계 0의 저장소
   URL·브랜치로 만든다.
4. **흐름 제목은 행위로 짓는다** — `### FLOW-<도메인>-<오퍼레이션 ID>:
   <행위 이름>`. 진입점이 아니라 행위이며, 재실행 시 이 제목이 앵커가 된다.
5. **단순 통과 오퍼레이션**은 `## 단순 통과 오퍼레이션` 표에 한 줄씩 적는다.
6. **`## 읽은 소스` 원장**에 모든 TRACE의 `sources_read`를 합쳐 적는다.

### 단계 6: 도메인 모델과 ERD 역추출

**산출** `<도메인>/design/backend/{domain-model,erd}.md` ·
**템플릿** `templates/design/backend/{domain-model,erd}.md`

1. **애그리거트를 식별한다.** 근거는 리포지토리 인터페이스가 다루는 타입,
   트랜잭션 경계, 함께 저장되는 객체 묶음이다. 각각 인용한다.
2. **불변식은 검증 코드에서 뽑는다** — 예외를 던지는 지점, 사전 조건 검사,
   상태 전이 가드. **불변식이 하나도 없는 타입은 애그리거트가 아니라 데이터
   덩어리다** — 그렇게 기록한다.
3. **상태 전이는 열거형과 전이 코드에서 뽑는다.** 금지 전이도 찾아 적는다.
4. **`erd.md`는 조건부다.** 마이그레이션·DDL·별도 퍼시스턴스 엔티티가 있을
   때만 만든다. 없으면 만들지 않고 내비게이션 체인에서도 뺀다.
5. **ORM 엔티티가 곧 도메인 모델이면** `erd.md`만 만들고 `domain-model.md`에
   "도메인 모델 = 영속성 모델" 주석을 남긴다. 같은 표를 두 번 찍지 않는다.
6. **`## 도메인 모델 매핑`의 `불일치` 열이 핵심이다** — 값 객체가 여러
   컬럼으로 펼쳐지거나, 애그리거트가 여러 테이블로 나뉘거나, 상속이 단일
   테이블로 접히는 지점을 기록한다.

### 단계 7: 레이어 매핑과 용어집

**산출** `<도메인>/design/backend/layered-architecture.md`,
`specifications/glossary.md`

1. 계층별 실제 파일과 클래스를 인용과 함께 기록한다. **일반적인 4계층 설명을
   쓰지 않는다** — `architecture.md`가 이미 소유한다.
2. 규약 예외(허용 의존성 위반)를 기록한다 (`reverse-rules.md` §5).
3. **`glossary.md`를 갱신한다.** 코드에서 발견한 도메인 개념의 영문 식별자와
   한국어 용어를 대응시킨다. **추가 전용**이며 기존 항목의 영문 식별자를
   바꾸지 않는다. 코드에 여러 표기가 섞여 있으면 대표 식별자 하나를 정하고
   나머지를 비고에 기록한다.

### 단계 8: 도메인 간 관계 역추출

**산출** `specifications/domain-map.md`의 `## 백엔드 컨텍스트 맵`

도메인이 하나뿐이면 건너뛴다 (`common-rules.md` §6.6).

1. **도메인 경계를 넘는 지점을 찾는다** — 다른 도메인 패키지의 import, 다른
   도메인 서비스 호출, 이벤트 발행·구독, 공유 테이블 접근.
2. **컨텍스트 맵을 그린다.** 서브그래프 = 도메인, 노드 = 애그리거트 루트.
   속성 수준 상세는 넣지 않는다.
3. **패턴을 코드 증거로 분류한다.** 번역 계층이 있으면 ACL, upstream 모델을
   그대로 쓰면 CF, 공개 프로토콜이면 OHS 등. **증거로 분류할 수 없으면
   `[ASSUMED: ...; basis: ...]`를 쓰고 단정하지 않는다.**
4. **화살표는 항상 upstream → downstream**이다.
5. 다른 스킬이 쓴 섹션은 바이트 단위로 보존한다 (계약 6).

### 단계 9: 검증과 수정 루프

`common-rules.md` §3의 인용 검증과 결정적 검사를 실행한다. 대상은
`infrastructure.md`, `architecture.md`, `sequence-diagram.md`,
`domain-model.md`, `erd.md`, `layered-architecture.md`, `domain-map.md`,
`glossary.md` 전부다.

### 단계 10: 완료 리포트 — 리뷰 게이트 ③

`common-rules.md` §4에 다음을 더한다: 추적하지 않은 오퍼레이션과 그 이유
(단순 통과 / 상한 초과 / 실패), 아직 문서화하지 않은 도메인.

> 백엔드 설계 문서화가 끝났습니다.
>
> - 요구사항과 유저 스토리를 역산하려면 `/explainable:reverse-planning`
> - 프론트엔드가 있다면 `/explainable:reverse-design-frontend`
> - 번역 미러가 필요하면 `/explainable:translate-docs`
>
> 영어 DDD 컨텍스트 맵이 별도로 필요하면 `dev-docs` 플러그인의
> `/dev-docs:domain-overview`가 있습니다.

## 문서 규칙

`common-rules.md` §5를 따른다. 이 스킬 고유 사항:

- **`분석 기준 커밋`을 반드시 채운다.** 없으면 문서가 무엇에 대해 참이었는지
  알 방법이 없다.
- 증거가 없는 카테고리의 문서를 만들지 않는다. **오퍼레이션이 없는 도메인에
  빈 시퀀스 다이어그램을 만드는 것이 이 스킬이 막아야 할 환각이다.**
