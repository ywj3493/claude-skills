# reverse-design-backend

이미 동작하는 백엔드 코드에서 **실제로 무엇이 어떻게 되어 있는지**를
근거와 함께 문서로 만든다.

**순서가 이 스킬의 핵심이다.** 인프라 → 코드베이스 구조 → 도메인 → 오퍼레이션.
위에서 아래로 내려가야 각 단계가 다음 단계의 판단 근거를 제공한다. 코드부터
읽기 시작하면 어느 계층에 속한 파일인지도 모르는 채로 다이어그램을 그리게
된다.

기획 문서는 이 스킬이 만들지 않는다. 설계가 끝난 뒤 `reverse-planning`이
그 결과로부터 요구사항과 유저 스토리를 역산한다.

## 사용 시점

- 인수인계받은 코드베이스를 파악해야 할 때
- "이 코드베이스 문서화해줘", "백엔드 분석해줘"
- 문서가 코드보다 오래되어 다시 만들어야 할 때

## 사용하지 않는 경우

- **코드가 아직 없는 경우** — 근거로 삼을 것이 없다.
  `init-design-backend`를 쓴다.
- **백엔드가 없는 프로젝트** — 감지 후 "해당 없음"을 보고하고 멈춘다.
- **프론트엔드 분석** — `reverse-design-frontend`의 일이다.
- **요구사항·유저 스토리가 필요한 경우** — 이 스킬을 먼저 돌리고
  `reverse-planning`을 실행한다.

## 근거와 인용 계약

이 계약이 이 스킬의 존재 이유다.

1. **코드에서 직접 확인한 사실만 쓴다.** 추측하는 표현, "보통 이런 경우에는",
   프레임워크 관례로 빈칸을 채우는 것 모두 금지다. 읽지 않았으면 사실로
   쓰지 않는다.

2. **모든 주장에 인용이 붙는다.** `[REF: 경로:줄번호]` 또는
   `[REF: 경로:시작-끝]` 형식이며, 저장소 기준 상대 경로와 정수를 쓴다.
   "관련 파일 참조" 같은 모호한 표현, 산문 속 괄호 인용, 이번 패스에서
   `Read`/`Grep`으로 실제로 열지 않은 파일의 인용은 전부 금지다. 도구로
   확인하지 못하는 인용은 인용이 없는 것보다 나쁘다 — 주장을 지우거나
   `[ASSUMED: ...]`로 바꾼다.

3. **완결성을 위해 필요하지만 코드로 확인할 수 없는 내용**은
   `[ASSUMED: <추론>; basis: <실제로 본 것>]`을 인용 자리에 쓴다.
   추측을 확인된 것처럼 보이게 하려고 `파일:줄`을 지어내지 않는다.

4. **의도를 추론해야 하는 섹션**에는 문서 상단에 배너를 넣는다:
   "이 섹션은 코드에서 추론한 내용입니다 — 이해관계자와 확인이 필요합니다."
   그리고 항목마다 인용이나 `[ASSUMED: ...]`를 붙인다.

5. **모든 문서는 `## 읽은 소스` 원장으로 끝난다.** 그 문서를 쓰면서 실제로
   연 파일(부분만 읽었으면 줄 범위 포함)을 전부 나열한다. 문서의 모든
   `[REF: ...]`는 이 목록에 있는 파일을 가리켜야 한다.

6. **시퀀스 다이어그램은 규칙이 더 붙는다.** 참여자마다
   `link <별칭>: Source @ <저장소 URL>/blob/<브랜치>/<경로>` 줄, 메시지마다
   실제 `경로:줄번호`를 담은 `Note`, 확인 불가한 흐름은 `[ASSUMED: ...]`,
   흐름 끝에 숨김 `<!-- CALLGRAPH: ... -->` 블록. `<저장소 URL>`은
   `git remote get-url origin`을 `https://`로 정규화하고, `<브랜치>`는
   체크아웃된 브랜치에서 얻는다.

   **다이어그램을 먼저 그리고 근거를 나중에 채우지 않는다.** 호출 그래프를
   먼저 추출하고, 그것으로 다이어그램·`Note`·`CALLGRAPH`를 함께 렌더링한다.

## 실행 규약

1. **템플릿은 필수다.** 없으면 없는 경로를 보고하고 멈춘다.

2. **에이전트 결과를 코드 재확인 없이 렌더링한다.** `operation-tracer`가
   반환한 TRACE 블록의 간선 목록에서 다이어그램·`Note`·`CALLGRAPH`를 **함께**
   렌더링한다. 그래야 셋이 구조적으로 일치한다. 에이전트 결과를 받고 나서
   코드를 다시 읽어 다이어그램을 새로 그리지 않는다.

3. **별칭은 스킬이 배정한다.** 에이전트가 준 별칭은 그 추적 안에서만
   유일하다. 여러 오퍼레이션을 한 문서에 병합할 때 별칭을 다시 배정해
   문서 전체에서 유일하고 일관되게 만든다.

4. **계층 라벨은 한 곳에서 온다.** 단계 2에서 확정한 레이어 ↔ 디렉터리
   매핑을 모든 에이전트 호출에 넘기고, 다이어그램의 `(계층)` 라벨도 그것만
   쓴다. 오퍼레이션마다 라벨이 달라지면 병합이 어긋난다.

5. **프레임워크를 추측하지 않는다.** 단계 1~2에서 감지한 API 스타일과
   진입점 파일 패턴을 에이전트에 입력으로 넘긴다. 에이전트가 스스로 REST를
   가정하지 않도록 하는 장치다.

6. **`PARTIAL` 추적을 조용히 받아들이지 않는다.** 처리 절차는 단계 5에
   명시되어 있다.

7. **리뷰 게이트를 문자 그대로 지킨다.** 특히 게이트 ②(오퍼레이션 선별)는
   비용이 가장 큰 지점이므로 반드시 확인받는다.

8. **미해결 항목이 남아 있으면 완료를 보고하지 않는다.** `citation-verifier`
   리포트에 `MISMATCHED`나 `UNSUPPORTED`가 남아 있는 문서, 패스, 전체 작업을
   완료로 보고하지 않는다.

## 단계별 지침

### 단계 0: 환경 감지와 재실행 판단

1. **문서 환경 감지.** `docs/config.yml`을 읽어 `source_language`를 정한다.
   없으면 디렉터리에서 추론하고, `docs/`가 아예 없으면 한 번만 묻는다
   (`init-planning` 단계 0과 동일한 절차). **동의 없이 `docs/config.yml`,
   루트 `CLAUDE.md`, `.claude/rules/`를 쓰지 않는다.**

2. **분석 기준 커밋을 확정한다.**

   ```bash
   git rev-parse HEAD
   git remote get-url origin
   git rev-parse --abbrev-ref HEAD
   git status --porcelain
   ```

   저장소 URL은 `https://`로 정규화한다. 이 세 값이 이후 모든 인용과 `link`
   줄의 기준이 된다.

3. **재실행 판단.** 대상 도메인에 이미 역방향 산출물이 있으면:

   a. 저장된 `분석 기준 커밋`과 현재 HEAD를 비교하고, 인용된 파일 중 몇 개가
      바뀌었는지 확인한다:

      ```bash
      git diff --name-only <저장된 sha>..HEAD -- <인용 경로들>
      ```

   b. **폐기 대상 목록을 전부 보여주고 확인받는다:**

      > `<도메인>`에 이미 역방향 설계 문서가 있습니다.
      > 저장된 기준 커밋 `<sha>` 이후 인용 파일 `<N>`개가 변경되었습니다.
      >
      > 역방향 문서는 특정 커밋의 코드를 기술한 스냅샷이므로, 부분 갱신하면
      > 낡은 인용과 새 인용이 한 문서에 섞입니다. 다음 파일을 폐기하고 현재
      > 코드 기준으로 다시 만들 것을 권합니다:
      >
      > `<삭제 대상 파일 목록>`
      >
      > 1. 폐기 후 재생성 (기본)
      > 2. 중단
      >
      > 다음은 폐기하지 않고 이 도메인 관련 부분만 갱신합니다:
      > `architecture.md`, `infrastructure.md`, `domain-map.md`,
      > `README.md`, `glossary.md`

   c. **작업 트리가 clean하지 않으면 경고한다.** 되돌리기를 git에 맡기므로
      커밋되지 않은 문서는 복구할 수 없다:

      > 커밋되지 않은 변경이 있습니다. 폐기한 문서는 git으로 복구할 수
      > 없습니다. 그래도 진행할까요?

   d. **확인 없이는 삭제하지 않는다.**

   e. **폐기 범위**: `<도메인>/design/**`와 그 도메인의 역방향
      `planning/**`. 횡단 문서와 `glossary.md`는 폐기하지 않는다.
      `glossary.md`에서 코드에 없어진 용어는 지우지 말고 `상태` 열을
      `폐기됨`으로 바꾼다 — 지우면 다른 문서의 링크가 끊긴다.

4. **리뷰 모드를 확인한다** (`단계별` 기본 / `연속`).

### 단계 1: 인프라 탐색

**산출**: `specifications/infrastructure.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/overview/infrastructure.md`

인프라가 먼저인 이유: 런타임, 배포 단위, 외부 서비스, 환경 변수를 알아야
코드에서 무엇이 경계인지 판단할 수 있다.

1. **`infra-explorer` 에이전트를 호출한다.** 저장소 루트를 넘긴다.
2. 반환된 `INFRA` 블록을 템플릿에 옮긴다. 근거를 그대로 유지한다.
3. **`tunables` 항목을 정확히 옮긴다.** 타임아웃, 재시도, 레이트 리밋,
   캐시 TTL, 임계값은 `reverse-planning`이 비기능 요구사항의 근거로 쓴다.
   반올림하거나 요약하지 않는다.
4. **환경 변수의 값을 절대 적지 않는다.** 이름·용도·필수 여부만 쓴다.
5. `not_found` 항목은 해당 섹션에 "없음 — 확인한 경로: ..."로 남긴다.
   섹션을 통째로 빼면 "확인했는데 없음"과 "확인하지 않음"이 구분되지 않는다.
6. `<!-- GENERATED-BY: reverse-design-backend; commit: <sha>; root: <경로>;
   date: <오늘> -->` 마커를 넣는다.

> **단계 1 완료**: 인프라를 문서화했습니다. 검토 후 코드베이스 구조 분석으로
> 진행할까요?

### 단계 2: 코드베이스 구조 분석

**산출**: `specifications/architecture.md`의 `## 백엔드 구조` 섹션과
`## 아키텍처 규약` 표

이 단계의 산출물이 **이후 모든 에이전트 호출의 입력**이 된다. 여기서 틀리면
모든 다이어그램의 라벨이 흔들린다.

1. **백엔드가 있는지 확인한다.** 없으면 멈춘다:

   > 이 저장소에서 백엔드 코드를 찾지 못했습니다. 확인한 경로: `<경로들>`
   > 프론트엔드 분석은 `/explainable:reverse-design-frontend`를 사용하세요.

2. **스택 표를 채운다.** 매니페스트와 설정에서 언어·런타임·프레임워크·
   영속성을 읽고 각각 인용한다.

3. **API 스타일과 진입점 파일 패턴을 확정한다.** 라우트 정의, 리졸버, 서비스
   정의, 메시지 컨슈머 중 무엇이 있는지 실제로 확인한다. 여러 스타일이 섞여
   있으면 전부 기록한다. 이 값이 `operation-tracer`의 입력이 된다.

4. **실측 레이어 패턴을 먼저 기술한다.** 코드가 실제로 어떤 계층 구조인지
   쓴다. **3계층이면 3계층이라고 쓴다** — 4계층으로 재분류하지 않는다.

5. **레이어 ↔ 디렉터리 매핑 표를 채운다.** `실제 경로` 열의 경로는 반드시
   실존해야 한다. 이 표가 에이전트 호출의 핵심 입력이다.

6. **허용 의존성 표를 채우고, 실제 위반을 `## 백엔드 구조`의 위반 목록에
   기록한다.** 규칙을 코드에 맞춰 느슨하게 고치지 않는다. 위반은 사실로만
   기록하고 리팩터링을 제안하지 않는다.

7. **4-Layered DDD 대비표를 채운다.** 일치 / 부분 / 없음으로 판정한다.

8. **모듈 경계를 식별한다.** 각 경계를 정하는 근거 파일을 인용한다.

9. **모노레포면 앱·패키지 경계도 확인한다.** `GENERATED-BY` 마커의 `root:`
   필드에 스캔 범위를 기록한다.

### 단계 3: 도메인 식별 — 리뷰 게이트 ①

1. 모듈 경계, 디렉터리 구조, 애그리거트 후보, 라우트 그룹을 근거로 도메인
   후보를 만든다.
2. **사용자에게 제시하고 확인받는다:**

   > 다음 도메인 구획을 발견했습니다:
   >
   > | 도메인 | 근거 | 오퍼레이션 수 |
   > |---|---|---|
   >
   > 이대로 진행할까요, 아니면 구획을 조정할까요?

3. 도메인이 나뉘어 있지 않으면 단일 도메인으로 진행한다. 억지로 쪼개지
   않는다.
4. **증거가 없는 도메인은 목록에서 뺀다.** 그 사실을 완료 리포트에 남긴다.

### 단계 4: 오퍼레이션 목록화와 선별 — 리뷰 게이트 ②

비용이 가장 큰 지점이다. 여기서 걸러야 60개 오퍼레이션짜리 서비스에서
60개의 똑같이 생긴 CRUD 다이어그램이 나오는 것을 막을 수 있다.

1. **도메인별로 오퍼레이션을 전부 나열한다.** 진입점 파일 패턴으로
   `Grep`하고, 각 오퍼레이션의 진입점 `경로:줄번호`와 심볼을 기록한다.

2. **선별한다.** 각 오퍼레이션을 훑어 다음으로 나눈다.

   | 분류 | 기준 | 처리 |
   |---|---|---|
   | 추적 대상 | 참여자 3개 이상 **또는** 분기가 있음 | `operation-tracer` 호출 |
   | 단순 통과 | 진입점 → 저장소, 분기 없음, 참여자 3개 미만 | 표 한 줄 |

3. **사용자에게 제시하고 확인받는다:**

   > `<도메인>`에서 오퍼레이션 `<N>`개를 찾았습니다.
   >
   > - 추적 대상 `<M>`개 — 시퀀스 다이어그램 생성
   > - 단순 통과 `<N-M>`개 — 표로만 기록
   >
   > `<추적 대상 목록>`
   >
   > 이대로 진행할까요? 목록을 조정할 수도 있습니다.

4. **추적 대상이 도메인당 20개를 넘으면 개수를 알리고 다시 확인받는다.**
   조용히 잘라내지 않는다. 제외한 항목은 완료 리포트에 남긴다.

### 단계 5: 오퍼레이션 추적

**산출**: `<도메인>/design/backend/sequence-diagram.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/backend/sequence-diagram.md`

1. **오퍼레이션 하나당 `operation-tracer`를 한 번 호출한다.** 5~8개씩 묶어
   병렬로 실행하고 묶음마다 결과를 병합한다.

2. **에이전트에 넘기는 입력** (하나라도 빠뜨리면 결과가 어긋난다):

   | 입력 | 출처 |
   |---|---|
   | 저장소 루트 | 단계 0 |
   | 오퍼레이션 식별자 | 단계 4 |
   | 진입점 `경로:줄번호`와 심볼 | 단계 4 |
   | API 스타일, 진입점 파일 패턴 | 단계 2 |
   | 계층 ↔ 디렉터리 매핑 | 단계 2 |
   | 용어집 항목 | 현재까지 확정된 것 |
   | 도메인 이름 | 단계 3 |
   | 종료 규칙 | 외부 시스템 / 저장소 어댑터 / 호출자 반환 / 다른 도메인 진입점 |

3. **`status: PARTIAL` 처리 절차:**
   - **1회 재시도** — 종료 규칙과 계층 매핑을 보강해 다시 호출한다.
   - 여전히 `PARTIAL`이면 해당 구간을 `[ASSUMED: ...]`로 표시하고
     `unresolved` 항목을 문서의 `## 미해결 항목`에 남긴다.
   - **완료 리포트에 미해결 개수를 명시한다.**
   - 에이전트가 아무것도 반환하지 않거나 스키마를 벗어나면 그 오퍼레이션을
     실패로 기록하고 다음으로 넘어간다. **묶음 하나가 실패해도 전체를
     멈추지 않는다.**

4. **렌더링.** 각 TRACE의 `edges` 목록 하나에서 세 가지를 함께 만든다.
   간선의 어느 필드가 어디로 가는지가 정해져 있다:

   | 간선 필드 | 렌더링 결과 |
   |---|---|
   | `출발 별칭`, `도착 별칭`, 화살표 종류 | `sequenceDiagram`의 메시지 방향 |
   | `호출 표현` | 메시지 라벨 |
   | `[REF: 경로:줄번호]` | 메시지 바로 다음 줄의 `Note` |
   | `from: 경로:줄번호` + `호출 표현` + `[REF:]` | `CALLGRAPH` 한 줄 (`<from> -> <호출 표현> \| <REF 위치>`) |
   | `branches` | `alt` / `else` 블록 |

   같은 목록에서 나오므로 셋이 구조적으로 일치하고,
   `citation-verifier`의 `Note` ↔ `CALLGRAPH` 양방향 검사가 통과한다.
   **코드를 다시 읽어 다이어그램을 새로 그리지 않는다.**

5. **참여자 `link` 줄**을 `participants`의 `path`와 단계 0의 저장소
   URL·브랜치로 만든다.

6. **별칭을 문서 전체에서 유일하게 재배정한다.** 여러 오퍼레이션이 같은
   파일을 참여자로 쓰면 같은 별칭을 공유하게 만든다.

7. **흐름 제목은 행위로 짓는다.**
   `### FLOW-<도메인>-<오퍼레이션 ID>: <행위 이름>` — 진입점이 아니라
   행위다. 재실행 시 이 제목이 앵커가 된다.

8. **단순 통과 오퍼레이션**은 `## 단순 통과 오퍼레이션` 표에 한 줄씩 적는다.

9. **`## 읽은 소스` 원장**에 모든 TRACE의 `sources_read`를 합쳐 적는다.

### 단계 6: 도메인 모델과 ERD 역추출

**산출**: `<도메인>/design/backend/domain-model.md`,
`<도메인>/design/backend/erd.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/backend/domain-model.md`,
`${CLAUDE_PLUGIN_ROOT}/templates/design/backend/erd.md`

1. **애그리거트를 식별한다.** 근거는 리포지토리 인터페이스가 다루는 타입,
   트랜잭션 경계, 함께 저장되는 객체 묶음이다. 각각 인용한다.

2. **불변식은 검증 코드에서 뽑는다.** 예외를 던지는 지점, 사전 조건 검사,
   상태 전이 가드가 근거다. **불변식이 하나도 없는 타입은 애그리거트가
   아니라 데이터 덩어리다** — 그렇게 기록한다.

3. **상태 전이는 열거형과 전이 코드에서 뽑는다.** 금지 전이도 찾아 적는다.

4. **`erd.md`는 조건부다.** 마이그레이션, DDL, 별도 퍼시스턴스 엔티티가
   있을 때만 만든다. 없으면 만들지 않고 내비게이션 체인에서도 빼며, 그
   사실을 완료 리포트에 남긴다.

5. **ORM 엔티티가 곧 도메인 모델이면** `erd.md`만 만들고 `domain-model.md`에
   "도메인 모델 = 영속성 모델" 주석을 남긴다. 같은 표를 두 번 찍지 않는다.

6. **`## 도메인 모델 매핑`의 `불일치` 열이 핵심이다.** 값 객체가 여러
   컬럼으로 펼쳐지거나, 애그리거트가 여러 테이블로 나뉘거나, 상속이 단일
   테이블로 접히는 지점을 기록한다.

### 단계 7: 레이어 매핑과 용어집

**산출**: `<도메인>/design/backend/layered-architecture.md`,
`specifications/glossary.md`

1. `layered-architecture.md`에 계층별 실제 파일과 클래스를 인용과 함께
   기록한다. **일반적인 4계층 설명을 쓰지 않는다** — `architecture.md`가
   이미 소유한다.
2. 규약 예외(허용 의존성 위반)를 기록한다. 사실만 쓰고 리팩터링을 제안하지
   않는다.
3. **`glossary.md`를 갱신한다.** 코드에서 발견한 도메인 개념의 영문
   식별자와 한국어 용어를 대응시킨다.
   - **추가 전용**이다. 기존 항목의 영문 식별자를 바꾸지 않는다.
   - 코드에 여러 표기가 섞여 있으면 대표 식별자 하나를 정하고 나머지를
     비고에 기록한다.
   - 코드에서 사라진 용어는 지우지 말고 `상태`를 `폐기됨`으로 바꾼다.

### 단계 8: 도메인 간 관계 역추출

**산출**: `specifications/domain-map.md`의 `## 백엔드 컨텍스트 맵`

도메인이 하나뿐이면 건너뛰고 그 사실을 완료 리포트에 남긴다.

1. **도메인 경계를 넘는 지점을 찾는다.** 다른 도메인 패키지의 import,
   다른 도메인 서비스 호출, 이벤트 발행·구독, 공유 테이블 접근.
2. **컨텍스트 맵을 그린다.** 서브그래프 = 도메인, 노드 = 애그리거트 루트.
   속성 수준 상세는 넣지 않는다.
3. **패턴을 코드 증거로 분류한다.** 번역 계층이 있으면 ACL, upstream 모델을
   그대로 쓰면 CF, 공개 프로토콜이면 OHS 등. **증거로 분류할 수 없으면
   `[ASSUMED: ...; basis: ...]`를 쓰고 단정하지 않는다.**
4. **화살표는 항상 upstream → downstream**이다.
5. **다른 스킬이 쓴 섹션(프론트엔드 슬라이스 의존 맵, 도메인 간 통합 계약,
   도메인 횡단 흐름)은 바이트 단위로 보존한다.**
6. `## 패턴 범례`는 고정 표다. 편집하거나 줄이지 않는다.

### 단계 9: 검증과 수정 루프

1. **생성한 문서마다 `citation-verifier`를 한 번씩 호출한다.**
   `infrastructure.md`, `architecture.md`, `sequence-diagram.md`,
   `domain-model.md`, `erd.md`, `layered-architecture.md`, `domain-map.md`,
   `glossary.md` 전부 대상이다.

2. **수정 루프:**
   - `MISMATCHED`와 `UNSUPPORTED` 항목만 고친다.
   - 인용된 위치를 다시 열어 주장을 고치거나, 인용을 고치거나,
     `[ASSUMED: ...]`로 바꾼다.
   - **`MATCHED`와 `EXCLUDED` 항목은 건드리지 않는다.**
   - 깨끗해질 때까지 다시 호출한다.

3. **결정적 검사도 실행한다:**

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-docs.sh" docs/<원본 언어>/specifications
   ```

4. **미해결 항목이 남아 있으면 완료를 보고하지 않는다.**

### 단계 10: 완료 리포트 — 리뷰 게이트 ③

- 생성한 파일 경로 (디스크에서 확인한 것만)
- 문서별 `citation-verifier` 최종 집계
- `check-docs.sh` 결과
- **미해결 항목 개수**와 그 목록
- 추적하지 않은 오퍼레이션과 그 이유 (단순 통과 / 상한 초과 / 실패)
- 생성하지 않은 문서와 그 이유
- 아직 문서화하지 않은 도메인
- 다음 단계 안내:

  > 백엔드 설계 문서화가 끝났습니다.
  >
  > - 요구사항과 유저 스토리를 역산하려면 `/explainable:reverse-planning`
  > - 프론트엔드가 있다면 `/explainable:reverse-design-frontend`
  > - 번역 미러가 필요하면 `/explainable:translate-docs`
  >
  > 영어 DDD 컨텍스트 맵이 별도로 필요하면 `dev-docs` 플러그인의
  > `/dev-docs:domain-overview`가 있습니다.

## 문서 규칙

- 모든 문서는 한국어로 쓴다. 코드 블록, 파일 경로, 식별자는 영어 그대로 둔다.
- 기계용 토큰은 영문 고정이다: `[REF: ...]`, `[ASSUMED: ...; basis: ...]`,
  `MATCHED`/`MISMATCHED`/`UNSUPPORTED`/`EXCLUDED`, `FLOW-` 접두사.
- `## 문서 정보` 표는 문서 하단에 두고, **`분석 기준 커밋` 필드에 단계 0의
  SHA를 반드시 채운다.** 이것이 없으면 문서가 무엇에 대해 참이었는지 알
  방법이 없다.
- 날짜는 `date +%F`로 얻는다.
- 내비게이션 링크는 `${CLAUDE_PLUGIN_ROOT}/references/document-order.md`를
  따른다. 생성하지 않은 문서는 체인에서 뺀다.
- 병합 전용 문서에서 자기 소유가 아닌 섹션은 바이트 단위로 보존한다.
- 증거가 없는 카테고리의 문서를 만들지 않는다. 오퍼레이션이 없는 도메인에
  빈 시퀀스 다이어그램을 만드는 것이 이 스킬이 막아야 할 환각이다.
