# init-design-backend

기획 문서가 정한 **무엇을**을 **어떻게**로 옮긴다. 백엔드만 다룬다 —
프론트엔드는 `init-design-frontend`가 담당한다.

**시작 전에 로드한다**: `${CLAUDE_PLUGIN_ROOT}/references/common-rules.md`

## 사용 시점

- `init-planning`이 끝난 뒤
- "백엔드 설계해줘", "도메인 모델 만들어줘", "ERD 그려줘"
- 기획은 이미 있고 서버 쪽 구조만 필요할 때

## 사용하지 않는 경우

- **기획 문서가 없는 경우** — `init-planning`을 먼저 실행한다.
- **이미 코드가 있는 경우** — `reverse-design-backend`
- **백엔드가 없는 프로젝트** — `common-rules.md` §6.1에 따라 "해당 없음"을
  보고하고 멈춘다.
- **프론트엔드 설계** — `init-design-frontend`

## 실행 규약

`common-rules.md`의 실행 규약 1~9를 따른다. 이 스킬 고유 항목:

1. **입력을 디스크에서 읽는다** (계약 2): `requirements.md`,
   `user-stories.md`, `api-interface.md`, `architecture.md`, `glossary.md`.
2. **프레임워크 관례를 설계 판단에 끌어들이지 않는다.** 4-Layered DDD의
   레이어 **역할**과 **의존성 방향**(Presentation → Application → Domain ←
   Infrastructure)만 다룬다. 구체 프레임워크는 `architecture.md`의 아키텍처
   규약 표에 이미 결정되어 있으므로 그 값을 읽어 쓴다.
3. **이름은 `glossary.md`의 영문 식별자를 따른다.** 새 개념이 필요하면 먼저
   용어집에 추가한 뒤 쓴다.
4. **참여자 라벨은 계층 기준이다** — `[파일명]<br/>(계층)`. 계층 이름은
   `architecture.md`의 매핑 표에서 가져온다. 프레임워크 타입명을 쓰지 않는다.
5. **`FLOW-<도메인>-<오퍼레이션 ID>` 키를 시퀀스 다이어그램 제목에 부여한다.**
   이 키가 추적성 매트릭스와 향후 구현 단위의 식별자가 된다.
6. **`## 읽은 소스`를 생성하지 않는다** (계약 7). `분석 기준 커밋`은
   "해당 없음".

## 산출물

```text
docs/<원본 언어>/specifications/<도메인>/
├── design/backend/
│   ├── layered-architecture.md
│   ├── domain-model.md
│   ├── erd.md                    # 조건부
│   └── sequence-diagram.md
└── verification/test-spec.md     # 백엔드 섹션만 (T-1NN)
```

갱신하는 병합 전용 문서: `architecture.md`의 백엔드 구조, `domain-map.md`의
백엔드 컨텍스트 맵, `planning/traceability.md`, `glossary.md`.

## 단계별 지침

### 단계 0: 입력 확인

1. `common-rules.md` §1의 문서 환경 감지와 리뷰 모드 확인을 수행한다.
2. **선행 기획 문서를 확인한다.** 없으면 멈춘다:

   > `<도메인>/planning/`에 기획 문서가 없습니다. 설계는 기획을 입력으로
   > 받습니다. `/explainable:init-planning`을 먼저 실행해 주세요.

3. **백엔드가 있는 프로젝트인지 확인한다.** `architecture.md`의 스택 표에
   백엔드 항목이 없고 사용자도 계획하지 않는다면:

   > 이 프로젝트에는 백엔드가 없습니다. 백엔드 설계 문서를 만들지 않고
   > 종료합니다. 프론트엔드 설계는 `/explainable:init-design-frontend`를
   > 사용하세요.

4. **기존 설계 문서를 확인한다.** 있으면 덮어쓰지 않고 어느 문서를 다시
   만들지 확인받는다.

### 단계 1: 레이어 매핑

**산출** `<도메인>/design/backend/layered-architecture.md` ·
**템플릿** `templates/design/backend/layered-architecture.md`

**일반적인 4계층 설명을 여기 쓰지 않는다.** 계층의 역할과 허용 의존성은
`architecture.md`가 한 번만 소유한다. 이 문서는 **이 도메인에서만 참인 것**만
담는다 — 분량을 채우려고 규약을 복사하지 않는다.

1. `architecture.md`의 레이어 ↔ 디렉터리 매핑 표를 읽는다.
2. 계층별 구성 요소와 계획 경로를 표로 채운다. 경로는 그 매핑과 일치해야 한다.
3. `역할` 열은 동어반복을 피한다 — "Order 컨트롤러"가 아니라 "주문 생성
   요청 수신과 입력 검증".
4. 도메인 고유 규칙이 없으면 섹션을 삭제한다. 규약 예외가 없으면 "예외 없음".

> **단계 1 완료**: 레이어 매핑을 작성했습니다. 검토 후 도메인 모델로
> 진행할까요?

### 단계 2: 도메인 모델

**산출** `<도메인>/design/backend/domain-model.md` ·
**템플릿** `templates/design/backend/domain-model.md`

1. `requirements.md`의 **명사**에서 애그리거트 후보를, **동사**에서 행위를
   만든다.
2. 애그리거트 경계 기준은 **함께 일관성을 지켜야 하는 범위**다. 한 트랜잭션
   에서 함께 바뀌어야 하는 것들이 한 애그리거트다.
3. `classDiagram`에 스테레오타입(`<<AggregateRoot>>`, `<<Entity>>`,
   `<<ValueObject>>`)을 반드시 붙인다.
4. **애그리거트 경계를 넘는 참조는 ID로만** 그린다.
5. **불변식을 채운다.** 값 범위 제약은 `erd.md`나 `api-interface.md`에
   속하므로, 여기는 **여러 필드에 걸친 규칙**을 쓴다. 불변식이 하나도 없는
   애그리거트는 애그리거트가 아니라 데이터 덩어리다 — 그렇다면 그렇게 표시한다.
6. 행위 표에서 getter/setter는 적지 않는다.
7. 상태를 가지는 애그리거트만 `## 상태 전이`를 만든다. **금지 전이도 적는다.**
8. 도메인 이벤트가 도메인 경계를 넘으면 `domain-map.md`의 통합 계약과
   일치해야 한다.
9. 새 개념을 `glossary.md`에 추가한다. 기존 항목은 고치지 않는다.

> **단계 2 완료**: 도메인 모델을 작성했습니다. 검토 후 ERD로 진행할까요?

### 단계 3: ERD (조건부)

**산출** `<도메인>/design/backend/erd.md` ·
**템플릿** `templates/design/backend/erd.md`

**영속성 스키마가 도메인 모델과 구분될 때만 만든다.**

1. 저장소가 없는 도메인(순수 계산, 외부 API 프록시)이면 만들지 않고
   내비게이션 체인에서도 뺀다.
2. `erDiagram`으로 테이블과 관계를 그린다. 카디널리티를 정확히 표기한다.
3. **컬럼 타입·제약·인덱스는 이 문서가 소유한다.**
4. ORM 엔티티가 곧 도메인 모델이면 매핑 표를 지우고 한 문장으로 대체한 뒤,
   `domain-model.md`에 "도메인 모델 = 영속성 모델" 주석을 남긴다. 같은 표를
   두 번 찍지 않는다.
5. `불일치` 열이 매핑 표의 존재 이유다 — 값 객체가 여러 컬럼으로 펼쳐지거나
   애그리거트가 여러 테이블로 나뉘는 지점을 기록한다.
6. 인덱스 근거가 되는 `NFR-PERF-NN`이 있으면 연결한다.

### 단계 4: 시퀀스 다이어그램

**산출** `<도메인>/design/backend/sequence-diagram.md` ·
**템플릿** `templates/design/backend/sequence-diagram.md`

1. **템플릿의 Source-Linked 모드 요소를 전부 생략한다** — 참여자 `link` 줄,
   메시지별 `Note`, 숨김 `CALLGRAPH`. 순방향에는 근거로 삼을 코드가 없다.
2. **유저 스토리 하나당 흐름 하나**를 기본으로 만들고, `api-interface.md`의
   오퍼레이션 카탈로그와 대조해 빠진 것을 확인한다.
3. **흐름 제목은 행위로 짓는다** — "만료된 세션 토큰 갱신"이지
   "POST /auth/refresh"가 아니다. 진입점이 바뀌어도 행위 이름은 유지된다.
4. 참여자는 4계층을 지나가게 그린다.
5. **인수 기준의 실패 조건을 `alt` 블록으로 그린다.** 정상 경로만 그린
   다이어그램은 설계가 아니라 그림이다.
6. 단순 통과 오퍼레이션(참여자 3개 미만, 분기 없음)은 `## 단순 통과
   오퍼레이션` 표에 한 줄로 적는다.
7. **추적성 확인** — 모든 `US-NN`에 흐름이 있는지, 모든 오퍼레이션이 흐름이나
   단순 통과 표에 있는지.

> **단계 4 완료**: 시퀀스 다이어그램을 작성했습니다. 검토 후 테스트 명세로
> 진행할까요?

### 단계 5: 테스트 명세 백엔드 섹션

**산출** `<도메인>/verification/test-spec.md` (백엔드 섹션) ·
**템플릿** `templates/verification/test-spec.md`

1. 파일이 없으면 템플릿에서 만들고, 있으면 **백엔드 섹션만 갱신한다.**
2. **테스트 ID는 `T-1NN` 대역**을 쓴다.
3. `AC-USNN-NN` 하나에 최소 하나의 테스트가 대응해야 한다.
4. 모킹 경계 표의 백엔드 행을 채운다. 외부 시스템 대역은
   `infrastructure.md`의 외부 서비스 표와 대응되어야 한다.
5. 순방향이므로 `상태` 열은 전부 `미구현`, `근거` 열은 비운다.

### 단계 6: 도메인 지도와 추적성 갱신

1. **`domain-map.md`의 `## 백엔드 컨텍스트 맵`** — 이 도메인의 애그리거트
   노드와 다른 도메인으로 향하는 엣지(패턴 약어 + 통합 방식, upstream →
   downstream 방향)를 추가한다. 다른 도메인이 이미 쓴 것은 보존한다.
2. **`planning/traceability.md`** — `스토리 → 흐름`에 `FLOW-` 키를,
   `인수 기준 → 테스트`에 `T-1NN`을 채우고 미연결 항목을 갱신한다.
3. **`architecture.md`의 `## 백엔드 구조`** — 순방향이므로 "실측 레이어
   패턴"을 "채택 레이어 구조"로 바꾸고 결정 사항을 기술한다.
4. `common-rules.md` §3의 결정적 검사를 실행한다.

### 단계 7: 완료 리포트

`common-rules.md` §4에 다음을 더한다: 부여한 `FLOW-` 키 목록.

> 백엔드 설계가 끝났습니다.
>
> - 프론트엔드가 있다면 `/explainable:init-design-frontend`
> - 번역 미러가 필요하면 `/explainable:translate-docs`

## 문서 규칙

`common-rules.md` §5를 따른다. 이 스킬 고유 사항: 순방향이므로
`## 읽은 소스`를 생성하지 않고 `분석 기준 커밋`은 "해당 없음"이다.
