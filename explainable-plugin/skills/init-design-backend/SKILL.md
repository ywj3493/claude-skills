# init-design-backend

기획 문서가 정한 **무엇을**을 받아 **어떻게**로 옮기는 스킬이다. 백엔드만
다룬다. 프론트엔드는 `init-design-frontend`가 별도로 담당한다.

## 사용 시점

- `init-planning`이 끝난 뒤
- "백엔드 설계해줘", "도메인 모델 만들어줘", "ERD 그려줘"
- 기획은 이미 있고 서버 쪽 구조만 필요할 때

## 사용하지 않는 경우

- **기획 문서가 없는 경우** — 무엇을 설계할지 알 수 없다.
  `init-planning`을 먼저 실행한다.
- **이미 코드가 있는 경우** — `reverse-design-backend`가 코드에서 근거를
  달아 뽑아낸다.
- **백엔드가 없는 프로젝트** — 감지 후 "해당 없음"을 보고하고 멈춘다.
  빈 문서를 만들지 않는다.
- **프론트엔드 설계** — `init-design-frontend`의 일이다.

## 실행 규약

1. **템플릿은 필수다.** 각 단계는 생성 전에
   `${CLAUDE_PLUGIN_ROOT}/templates/design/backend/` 아래 템플릿을 읽는다.
   없으면 없는 경로를 보고하고 멈춘다.

2. **입력은 디스크에서 다시 읽는다.** `requirements.md`, `user-stories.md`,
   `api-interface.md`, `architecture.md`, `glossary.md`를 파일에서 읽는다.
   대화에 있던 내용을 그대로 쓰지 않는다.

3. **프레임워크에 의존하는 지시를 만들지 않는다.** 4-Layered DDD의 레이어
   **역할**과 **의존성 방향**만 다루고, 어떤 프레임워크로 구현하는지는
   `architecture.md`의 아키텍처 규약 표에 이미 결정되어 있다. 그 표의 값을
   읽어 쓰되, 설계 판단에 프레임워크 관례를 끌어들이지 않는다.

4. **이름은 용어집에서 가져온다.** 애그리거트, 엔티티, 값 객체, 테이블,
   컬럼 이름은 `glossary.md`의 영문 식별자를 따른다. 새 개념이 필요하면
   먼저 용어집에 추가한 뒤 쓴다.

5. **FLOW 키를 부여한다.** 시퀀스 다이어그램의 흐름마다
   `FLOW-<도메인>-<오퍼레이션 ID>` 키를 제목에 넣는다. 이 키가 추적성
   매트릭스와 향후 구현 단위의 식별자가 된다.

6. **참여자 라벨은 계층 기준이다.** `[파일명]<br/>(계층)` 형식을 쓰고,
   계층 이름은 `architecture.md`의 매핑 표에서 가져온다. 프레임워크 타입명을
   쓰지 않는다.

7. **`## 읽은 소스` 섹션은 생성하지 않는다.** 코드가 없으므로 인용할 대상이
   없다. 템플릿에서 제목까지 삭제한다.

8. **병합 전용 문서는 자기 섹션만 쓴다.** `test-spec.md`의 백엔드 섹션,
   `domain-map.md`의 백엔드 컨텍스트 맵, `architecture.md`의 백엔드 구조
   섹션만 건드리고 나머지는 바이트 단위로 보존한다.

9. **리뷰 게이트를 문자 그대로 지킨다.**

10. **확인한 경로만 보고한다.**

## 산출물

```text
docs/<원본 언어>/specifications/<도메인>/
├── design/backend/
│   ├── layered-architecture.md
│   ├── domain-model.md
│   ├── erd.md                    # 조건부
│   └── sequence-diagram.md
└── verification/test-spec.md     # 백엔드 섹션만 (T-1NN)
```

갱신하는 병합 전용 문서: `domain-map.md`의 백엔드 컨텍스트 맵,
`planning/traceability.md`의 흐름 키, `glossary.md`.

## 단계별 지침

### 단계 0: 입력 확인

1. **문서 환경 감지.** `docs/config.yml`을 읽어 `source_language`를 정한다.
   없으면 디렉터리에서 추론한다. 절차는 `init-planning` 단계 0과 같다.

2. **선행 기획 문서를 확인한다.** 대상 도메인의 `planning/requirements.md`,
   `user-stories.md`, `api-interface.md`가 있어야 한다. 없으면 멈춘다:

   > `<도메인>/planning/`에 기획 문서가 없습니다. 설계는 기획을 입력으로
   > 받습니다. `/explainable:init-planning`을 먼저 실행해 주세요.

3. **백엔드가 있는 프로젝트인지 확인한다.** `architecture.md`의 스택 표에
   백엔드 항목이 비어 있고 사용자도 백엔드를 계획하지 않는다면:

   > 이 프로젝트에는 백엔드가 없습니다. 백엔드 설계 문서를 만들지 않고
   > 종료합니다. 프론트엔드 설계는 `/explainable:init-design-frontend`를
   > 사용하세요.

   빈 문서를 만들지 않는다.

4. **기존 설계 문서를 확인한다.** 이미 있으면 덮어쓰지 않는다. 어느 문서를
   다시 만들지 사용자에게 확인받는다.

5. **리뷰 모드를 확인한다** (`단계별` 기본 / `연속`).

### 단계 1: 레이어 매핑

**산출**: `<도메인>/design/backend/layered-architecture.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/backend/layered-architecture.md`

**일반적인 4계층 설명을 여기 쓰지 않는다.** 계층의 역할과 허용 의존성은
`architecture.md`가 한 번만 소유한다. 이 문서는 **이 도메인에서만 참인 것**만
담는다.

1. `architecture.md`의 레이어 ↔ 디렉터리 매핑 표를 읽는다.
2. 계층별로 이 도메인에 만들 구성 요소와 그 계획 경로를 표로 채운다.
   경로는 `architecture.md`의 매핑과 일치해야 한다.
3. `역할` 열은 동어반복을 피한다. "Order 컨트롤러"가 아니라 "주문 생성
   요청 수신과 입력 검증"처럼 쓴다.
4. 도메인 고유 규칙이 없으면 그 섹션을 삭제한다. 규약 예외가 없으면
   "예외 없음"이라고 적는다.
5. 도메인이 프로젝트 규약을 그대로 따르면 이 문서는 계층별 구성 요소 표
   하나로 끝나는 것이 정상이다. 분량을 채우려고 규약을 복사하지 않는다.

> **단계 1 완료**: 레이어 매핑을 작성했습니다. 검토 후 도메인 모델로
> 진행할까요?

### 단계 2: 도메인 모델

**산출**: `<도메인>/design/backend/domain-model.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/backend/domain-model.md`

1. `requirements.md`의 기능 요구사항에서 **명사**를 추려 애그리거트 후보를
   만들고, **동사**에서 행위를 만든다.
2. 애그리거트 경계를 정한다. 기준은 **함께 일관성을 지켜야 하는 범위**다.
   한 트랜잭션에서 함께 바뀌어야 하는 것들이 한 애그리거트다.
3. `classDiagram`을 그린다. 스테레오타입(`<<AggregateRoot>>`, `<<Entity>>`,
   `<<ValueObject>>`)을 반드시 붙인다.
4. **애그리거트 경계를 넘는 참조는 ID로만** 그린다. 다른 애그리거트의
   객체를 직접 참조하는 선을 그리지 않는다.
5. **불변식을 채운다.** 값 범위 제약(길이, 최소/최대)은 여기가 아니라
   `erd.md`나 `api-interface.md`에 속한다. 여기는 **여러 필드에 걸친 규칙**을
   쓴다. 불변식이 하나도 없는 애그리거트는 애그리거트가 아니라 데이터
   덩어리다 — 그렇다면 그렇게 표시한다.
6. 행위 표에서 getter/setter는 적지 않는다.
7. 상태를 가지는 애그리거트만 `## 상태 전이` 섹션을 만든다. **금지 전이도
   적는다** — 무엇이 안 되는지가 무엇이 되는지만큼 중요하다.
8. 도메인 이벤트가 도메인 경계를 넘으면 `domain-map.md`의 통합 계약과
   일치해야 한다.
9. 새로 등장한 개념을 `glossary.md`에 추가한다. 기존 항목은 고치지 않는다.

> **단계 2 완료**: 도메인 모델을 작성했습니다. 검토 후 ERD로 진행할까요?

### 단계 3: ERD (조건부)

**산출**: `<도메인>/design/backend/erd.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/backend/erd.md`

**영속성 스키마가 도메인 모델과 구분될 때만 만든다.**

1. `architecture.md`의 영속성 항목을 확인한다. 저장소가 없는 도메인(순수
   계산, 외부 API 프록시)이면 이 문서를 만들지 않고 내비게이션 체인에서도
   뺀다. 그 사실을 완료 리포트에 남긴다.
2. `erDiagram`으로 테이블과 관계를 그린다. 카디널리티를 정확히 표기한다.
3. 테이블 정의 표를 채운다. **컬럼 타입·제약·인덱스는 이 문서가 소유한다.**
4. `## 도메인 모델 매핑` — 도메인 모델과 영속성 모델이 다를 때만 채운다.
   ORM 엔티티가 곧 도메인 모델이면 표를 지우고 한 문장으로 대체한 뒤,
   `domain-model.md`에 "도메인 모델 = 영속성 모델" 주석을 남긴다.
   `불일치` 열이 이 표의 존재 이유다 — 값 객체가 여러 컬럼으로 펼쳐지거나,
   애그리거트가 여러 테이블로 나뉘는 지점을 기록한다.
5. 인덱스를 정할 때 그 근거가 되는 `NFR-PERF-NN`이 있으면 연결한다.

### 단계 4: 시퀀스 다이어그램

**산출**: `<도메인>/design/backend/sequence-diagram.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/backend/sequence-diagram.md`

1. **템플릿의 Source-Linked 모드 요소를 전부 생략한다.** 참여자 `link` 줄,
   메시지별 `Note`, 숨김 `CALLGRAPH` 블록은 코드가 있을 때만 쓴다. 순방향에는
   근거로 삼을 코드가 없다.
2. **유저 스토리 하나당 흐름 하나**를 기본으로 만든다. `api-interface.md`의
   오퍼레이션 카탈로그와 대조해 빠진 것이 없는지 확인한다.
3. **흐름 제목은 행위로 짓는다.** `FLOW-<도메인>-<오퍼레이션 ID>: <행위 이름>`
   형식이며, "만료된 세션 토큰 갱신"이지 "POST /auth/refresh"가 아니다.
   진입점이 바뀌어도 행위 이름은 유지된다.
4. 참여자는 4계층을 지나가게 그린다. 라벨은 `[파일명]<br/>(계층)`이고
   계층 이름은 `architecture.md`의 매핑에서 가져온다.
5. **인수 기준의 실패 조건을 `alt` 블록으로 그린다.** 정상 경로만 그린
   다이어그램은 설계가 아니라 그림이다. `AC-USNN-NN`에 있는 실패 조건이
   다이어그램에 나타나야 한다.
6. 단순 통과 오퍼레이션(참여자 3개 미만, 분기 없음)은 다이어그램 대신
   `## 단순 통과 오퍼레이션` 표에 한 줄로 적는다.
7. **추적성 확인** — 모든 `US-NN`에 흐름이 있는지, `api-interface.md`의
   모든 오퍼레이션이 흐름이나 단순 통과 표에 있는지 확인한다. 빠진 것이
   있으면 채우거나 그 이유를 기록한다.

> **단계 4 완료**: 시퀀스 다이어그램을 작성했습니다. 검토 후 테스트 명세로
> 진행할까요?

### 단계 5: 테스트 명세 백엔드 섹션

**산출**: `<도메인>/verification/test-spec.md` (백엔드 섹션)

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/verification/test-spec.md`

1. 파일이 없으면 템플릿에서 만들고, 있으면 **백엔드 섹션만 갱신한다.**
   프론트엔드·E2E 섹션은 바이트 단위로 보존한다.
2. **테스트 ID는 `T-1NN` 대역을 쓴다.** 프론트엔드(`T-2NN`)와
   E2E(`T-3NN`)의 번호를 침범하지 않는다.
3. `AC-USNN-NN`에서 테스트를 도출한다. 인수 기준 하나에 최소 하나의
   테스트가 대응해야 한다.
4. 모킹 경계 표에서 백엔드 관련 행을 채운다. 외부 시스템 대역은
   `infrastructure.md`의 외부 서비스 표와 대응되어야 한다.
5. 순방향이므로 `상태` 열은 전부 `미구현`이고 `근거` 열은 비운다. 아직
   테스트 코드가 없다.

### 단계 6: 도메인 지도와 추적성 갱신

1. **`domain-map.md`의 `## 백엔드 컨텍스트 맵`을 갱신한다.**
   - 도메인이 하나뿐이면 건너뛴다.
   - 이 도메인의 애그리거트 노드와, 다른 도메인으로 향하는 엣지를 추가한다.
   - 엣지 라벨에 컨텍스트 맵 패턴 약어와 통합 방식을 넣는다. 화살표는 항상
     upstream → downstream이다.
   - **다른 도메인이 이미 쓴 노드와 엣지는 보존한다.**

2. **`planning/traceability.md`를 갱신한다.**
   - `스토리 → 흐름` 표에 이번에 부여한 `FLOW-` 키를 채운다.
   - `인수 기준 → 테스트` 표에 `T-1NN` ID를 채운다.
   - 미연결 항목을 정직하게 갱신한다.

3. **`architecture.md`의 `## 백엔드 구조` 섹션을 갱신한다.** 순방향이므로
   "실측 레이어 패턴" 소제목을 "채택 레이어 구조"로 바꾸고 결정 사항을
   기술한다. 다른 섹션은 보존한다.

4. **결정적 검사를 실행한다**:

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-docs.sh" docs/<원본 언어>/specifications
   ```

   보고된 문제를 전부 고친 뒤 다시 실행해 통과시킨다.

### 단계 7: 완료 리포트

- 생성한 파일 경로 (디스크에서 확인한 것만)
- 생성하지 않은 문서와 그 이유 (`erd.md` 생략 등)
- `check-docs.sh` 결과
- 부여한 `FLOW-` 키 목록
- 다음 단계 안내:

  > 백엔드 설계가 끝났습니다.

## 문서 규칙

- 모든 문서는 한국어로 쓴다. 코드 블록, 파일 경로, 식별자, 다이어그램 안의
  타입명은 영어 그대로 둔다.
- 기계용 토큰은 영문 고정이다: `FLOW-`, `FR-`, `US-`, `AC-`, `T-` 접두사.
- `## 문서 정보` 표는 문서 하단에 둔다. `분석 기준 커밋` 필드는 순방향이므로
  "해당 없음"이다.
- 날짜는 `date +%F`로 얻는다.
- 내비게이션 링크는 `${CLAUDE_PLUGIN_ROOT}/references/document-order.md`를
  따른다. 생성하지 않은 문서(`erd.md` 등)는 체인에서 빼고 링크하지 않는다.
- 모든 Mermaid 블록은 문법적으로 완결되어야 한다. 다이어그램 종류 선언
  (`classDiagram`, `erDiagram`, `sequenceDiagram`, `stateDiagram-v2`)을
  빠뜨리지 않는다.
- 증거가 없거나 해당하지 않는 섹션은 비워 두지 말고 제목까지 삭제한다.
