# backend-implementation

설계 문서가 정한 **어떻게**를 코드로 옮긴다. 백엔드만 다룬다. 이 스킬의
산출물은 문서가 아니라 **코드와 테스트**이며, 문서는 구현 결과를 반영하는
범위에서만 고친다.

**시작 전에 로드한다**:

- `${CLAUDE_PLUGIN_ROOT}/references/common-rules.md`
- `${CLAUDE_PLUGIN_ROOT}/references/backend-implementation-rules.md`
  (이하 `구현 규약`)
- 단계 0에서 정한 스택 프로파일
  `${CLAUDE_PLUGIN_ROOT}/references/stacks/<프로파일>.md` (있을 때)

## 사용 시점

- `init-design-backend`가 끝난 뒤
- "백엔드 구현해줘", "설계대로 코드 짜줘", "FLOW-order-cancel-order 구현해줘"
- 테스트 명세에 `미구현` 백엔드 테스트가 남아 있는 도메인에 기능을 더할 때 —
  기존 코드베이스여도 설계 문서가 있으면 쓸 수 있다

## 사용하지 않는 경우

- **백엔드 설계 문서가 없는 경우** — `init-design-backend`를 먼저 실행한다.
- **기존 코드를 문서화하려는 경우** — `reverse-design-backend`
- **프론트엔드 구현** — 이 스킬의 범위가 아니다.
- **백엔드가 없는 프로젝트** — `common-rules.md` §6.1에 따라 "해당 없음"을
  보고하고 멈춘다.
- **설계를 바꾸는 작업** — 애그리거트 경계, 불변식, 오퍼레이션 추가는 설계
  문서를 먼저 고친다. 이 스킬은 설계를 새로 정하지 않는다.

## 실행 규약

`common-rules.md`의 실행 규약 1~9를 따른다. 계약 1(템플릿 필수)은 이 스킬에서
**스택 프로파일**로 대신한다 — 프로파일이 없을 때의 처리는 단계 0.4. 이 스킬
고유 항목:

1. **입력을 디스크에서 읽는다** (계약 2): `architecture.md`,
   `glossary.md`, `<도메인>/planning/api-interface.md`,
   `<도메인>/design/backend/*.md`, `<도메인>/verification/test-spec.md`.
2. **설계에 없는 것을 지어내지 않는다.** 파일 위치는 `layered-architecture.md`,
   클래스·메서드 이름은 `domain-model.md`와 `glossary.md`, 오류 코드와 상태
   코드는 `api-interface.md`에서 가져온다. 설계에 없는 애그리거트·불변식·
   오퍼레이션이 필요해지면 **멈추고 묻는다** — 설계 문서를 먼저 고칠지,
   이번 범위에서 뺄지. DTO, 매퍼, 페이크, 오류 처리기 같은 구현 보조물은
   설계에 없어도 만든다.
3. **결정의 우선순위는 `구현 규약` §1을 따른다.** 관용구는 기존 코드가
   프로파일보다 앞서지만, 원칙(의존 방향, 불변 값 객체, 얇은 유스케이스)은
   기존 코드가 달라도 새 코드에서 지킨다.
4. **테스트가 먼저다.** 계층마다 테스트를 쓰고 실패를 확인한 뒤 구현한다
   (`구현 규약` §8.3). 실패·건너뜀이 남은 테스트의 `T-1NN`을 `구현됨`으로
   표시하지 않는다.
5. **범위를 지킨다.** 단계 0에서 승인된 FLOW와 그에 필요한 공용 부분
   (컴포지션 루트, 오류 처리기, 설정 파일)만 바꾼다. 범위 밖 기존 코드의
   규약 이탈은 고치지 않고 보고한다.
6. **기존 파일을 고치기 전에 계획에 올린다.** 새 파일은 단계 0의 구현 계획에
   있으면 만든다. 기존 파일 수정과 매니페스트(의존성) 변경은 계획에 명시하고
   승인받는다.
7. **문서는 자기 범위만 쓴다** (계약 6). 고치는 문서와 범위:
   - `test-spec.md` — 백엔드 테스트 매트릭스의 **`상태`·`근거` 열**과
     `## 테스트 파일 구조` 표. 다른 열과 섹션은 바이트 단위로 보존한다.
   - `layered-architecture.md` — 계획 경로가 실제 경로와 달라진 행의 `경로`
     열, 그리고 `구현 규약` §9의 `## 규약 예외` 행. 둘 다 사용자 승인 후.
   - 그 밖의 문서는 쓰지 않는다. 고쳐야 할 불일치를 발견하면 보고한다.
8. **git 커밋을 만들지 않는다.** 변경은 작업 트리에 남기고 완료 리포트에
   파일 목록을 적는다. 커밋 단위와 메시지는 호스트 프로젝트 규칙을 따라
   사용자가 정한다.

## 산출물

```text
<architecture.md 매핑이 정한 백엔드 경로>/
├── <컨텍스트>/{domain, application, infrastructure, presentation}/...   # 코드
├── <컨텍스트>/<컴포지션 루트>
└── <테스트 경로>/                                                       # 계층별 테스트 + 페이크
<매니페스트·설정 파일>          # 의존성, 테스트·린트·의존 방향 계약 설정 (승인 시)
```

갱신하는 문서: `<도메인>/verification/test-spec.md`(위 범위),
`<도메인>/design/backend/layered-architecture.md`(위 범위, 승인 시).

## 단계별 지침

### 단계 0: 입력 확인과 구현 계획

1. `common-rules.md` §1의 문서 환경 감지와 리뷰 모드 확인을 수행한다.
   단계별 모드의 게이트는 단계 0, 1, 2와 **FLOW마다**(단계 3), 단계 4에 있다.
2. **대상 도메인을 정한다.** `docs/<원본 언어>/specifications/` 아래에서
   `design/backend/`가 있는 도메인을 나열하고 고르게 한다.
3. **입력 문서를 확인한다.** 하나라도 없으면 멈춘다 (`erd.md`는 조건부라
   없어도 된다):

   > `<도메인>`의 백엔드 설계 문서가 부족합니다: `<없는 파일 목록>`.
   > 구현은 설계를 입력으로 받습니다. `/explainable:init-design-backend`를
   > 먼저 실행해 주세요.

   `architecture.md`의 `## 아키텍처 규약`에서 스택 표의 백엔드 행과
   계층 ↔ 디렉터리 매핑의 백엔드 행이 비어 있어도 같은 방식으로 멈춘다.
   백엔드 행 자체가 없으면 §6.1 "해당 없음"으로 멈춘다.
4. **스택 프로파일을 정한다.** 스택 표의 백엔드 언어와 프레임워크로
   `${CLAUDE_PLUGIN_ROOT}/references/stacks/` 아래 파일을 찾는다(예: Python +
   FastAPI → `python-fastapi.md`). 찾은 프로파일을 사용자에게 알린다.
   맞는 프로파일이 없으면:

   > `<언어> + <프레임워크>`용 스택 프로파일이 없습니다. 구현 규약(프레임워크
   > 중립)만으로 진행하고, 아래 관용구는 지금 정해 주세요.
   >
   > 1. 테스트 도구와 테스트 디렉터리 구조
   > 2. 의존성 주입 방식(컴포지션 루트 위치)
   > 3. 의존 방향 검사 도구 (없으면 "미강제"로 기록)
   > 4. 불변 값 객체를 만드는 문법

   답을 완료 리포트의 "프로파일 없이 정한 관용구"에 남긴다. 기억으로
   프레임워크 관례를 지어내지 않는다 (계약 8).
5. **기존 코드를 확인한다.** 매핑 표의 백엔드 경로가 이미 있으면 같은
   계층의 이웃 파일 몇 개를 읽어 관용구(파일 이름, 폴더, 테스트 형식)를
   파악한다. 없으면 새 프로젝트로 본다.
6. **구현 대상 FLOW를 고른다.** `sequence-diagram.md`의 `FLOW-` 제목과
   `## 단순 통과 오퍼레이션` 표를 나열하고, 각 FLOW에 걸린 `test-spec.md`
   백엔드 행의 `상태`를 붙인다. 기본 선택은 `미구현` 행이 하나라도 있는 FLOW
   전부다. 20개를 넘으면 `common-rules.md` §6.3을 따른다.
7. **구현 계획을 보인다.** 아래 표를 만들고 승인받는다. 파일 경로는
   `layered-architecture.md`의 계층별 구성 요소 표에서 가져온다.

   | FLOW | 계층 | 파일 | 신규/수정 | 대응 테스트 |
   |---|---|---|---|---|
   | `FLOW-<도메인>-<OpID>` | Domain / Application / Infrastructure / Presentation | 경로 | 신규 | `T-1NN` |

   표 아래에 적는다: 공용으로 만들거나 고칠 파일(컴포지션 루트, 오류 처리기,
   설정·매니페스트), 추가할 의존성, 설계에서 찾지 못해 질문이 필요한 항목.

> **단계 0 완료**: 구현 계획을 작성했습니다. 이 범위로 진행할까요?

### 단계 1: 골격과 검사 도구

1. 매핑 표와 프로파일에 따라 **구현 계획에 필요한** 디렉터리만 만든다.
   빈 디렉터리를 미리 만들지 않는다.
2. 컴포지션 루트 파일, 공용 예외 기반 타입(`구현 규약` §3.5), 오류 처리기
   뼈대, 테스트 공용 픽스처와 페이크 디렉터리를 만든다. 이미 있으면 재사용한다.
3. **의존 방향 계약을 설정한다** (`구현 규약` §2.3). 프로파일의 설정을 쓰고,
   `architecture.md`의 허용 의존성 표와 대조한다. 계약에 있어야 할 행이 표에
   없으면(예: Presentation → Domain 예외 타입) 사용자 동의를 받아
   `architecture.md`에 기록할지 묻고, 동의하지 않으면 계약에서 그 허용을 뺀다.
4. 승인된 의존성을 매니페스트에 추가하고 설치한다.
5. **빈 상태에서 검증 명령을 한 번 돌린다** — 테스트 수집, 린트, 의존 방향
   검사가 실행 가능한지 확인한다. 실패하면 단계 2로 가지 않는다.

> **단계 1 완료**: 골격과 검사 도구를 준비했습니다. 도메인 계층으로
> 진행할까요?

### 단계 2: 도메인 계층

구현 대상 FLOW가 쓰는 애그리거트를 `domain-model.md`에서 모아, **애그리거트
단위로** 구현한다. 도메인은 여러 FLOW가 공유하므로 FLOW 슬라이스보다 먼저
한 번에 만든다.

1. **테스트를 먼저 쓴다.** 애그리거트마다:
   - 불변식 표의 행마다 위반 테스트 하나
   - 행위 표의 메서드마다 정상 테스트, `사전 조건` 위반 테스트
   - `## 상태 전이`의 허용 전이마다 하나, **금지 전이 표의 행마다 하나**
   - 값 객체의 생성 검증과 불변성
   `test-spec.md`에 이 테스트에 해당하는 `T-1NN`이 있으면 그 ID를 붙이고,
   없으면 ID 없이 쓴다 (`구현 규약` §8.2.3).
2. 테스트가 실패하는지 확인한다.
3. 값 객체 → 도메인 예외 → 애그리거트(팩토리, 행위, 재구성 경로) → 도메인
   서비스 → 포트 순으로 구현한다 (`구현 규약` §3).
4. 도메인 테스트와 의존 방향 검사를 통과시킨다.

> **단계 2 완료**: 도메인 계층 `<애그리거트 목록>`을 구현했습니다 (테스트
> `<통과 수>`개 통과). FLOW 구현으로 진행할까요?

### 단계 3: FLOW 수직 슬라이스 (FLOW마다 반복)

구현 계획의 FLOW를 하나씩 끝까지 완성한다. 한 FLOW가 녹색이 되기 전에 다음
FLOW로 넘어가지 않는다.

1. **응용 계층** (`구현 규약` §4)
   1. 이 FLOW가 쓰는 포트의 페이크가 없으면 만든다 (`구현 규약` §8.1).
   2. 유스케이스 테스트를 쓴다 — 정상 경로, 그리고 `sequence-diagram.md`
      흐름의 **`alt` 실패 분기마다 하나 이상**. 매트릭스의 `T-1NN`을 붙인다.
   3. Command/Result DTO와 유스케이스를 구현한다. 트랜잭션 경계는
      `layered-architecture.md`의 `트랜잭션 경계` 열을 따른다.
2. **인프라 계층** (`구현 규약` §5) — 이 FLOW가 쓰는 포트 중 아직 어댑터가
   없는 것만. 어댑터 테스트(저장 형식, 재구성, 기술 예외 변환)를 먼저 쓰고
   구현한다. 대상 저장소·외부 시스템은 `layered-architecture.md`
   Infrastructure 표의 `대상` 열과 `erd.md`를 따른다.
3. **표현 계층** (`구현 규약` §6)
   1. `api-interface.md`에서 이 FLOW의 오퍼레이션 계약(요청·응답 스키마,
      상태 코드)과 `## 오류 모델`을 읽는다.
   2. 표현 테스트를 쓴다 — 정상 상태 코드, 실패 분기의 상태 코드와 오류 코드.
   3. 요청·응답 스키마와 진입점을 구현하고, 이 FLOW가 던질 수 있는 예외를
      오류 처리기 표에 추가한다.
4. **배선** — 컴포지션 루트에 어댑터와 유스케이스를 등록한다.
5. **검증** — 전체 테스트, 린트, 의존 방향 검사를 실행한다. 실패를 남긴 채
   다음 FLOW로 가지 않는다.

> **`FLOW-<도메인>-<OpID>` 완료**: 테스트 `<T-1NN 목록>` 통과. 생성 `<n>`개,
> 수정 `<n>`개 파일. 다음 FLOW `<키>`로 진행할까요?

### 단계 4: 전체 검증과 자체 검토

1. 프로파일의 검증 명령을 전부 실행한다 (테스트, 린트, 의존 방향 검사, 있으면
   타입 검사). 결과를 그대로 기록한다.
2. **`구현 규약` §10 체크리스트**로 생성·수정한 파일 전부를 검토한다.
   "아니오" 항목은 고치거나, 타협이 정당하면 `구현 규약` §9에 따라
   `## 규약 예외`에 기록할지 사용자에게 묻는다.
3. **설계 대조** — 구현 결과가 설계와 다른 지점을 모은다: 계획 경로와 다른
   실제 경로, 설계에 없던 실패 분기, 계약과 다른 필드. 경로 차이는
   단계 5에서 반영하고, 나머지는 설계 수정 제안으로 보고한다.

> **단계 4 완료**: 검증 결과 `<요약>`. 자체 검토에서 `<n>`건을 고쳤고
> `<n>`건은 규약 예외로 기록을 제안합니다. 문서 갱신으로 진행할까요?

### 단계 5: 문서 갱신

1. **`test-spec.md` 백엔드 테스트 매트릭스** — 구현한 `T-1NN` 행마다:
   - 그 ID를 단 테스트가 **통과했으면** `상태`를 `구현됨`으로, `근거`에
     테스트 함수 정의 줄을 `[REF: <테스트 파일>:<줄>]`로 쓴다. 경로는 저장소
     루트 기준이다. 테스트가 여러 개면 인용을 하나씩 따로 쓴다
     (`[REF: a:12], [REF: b:30]`) — 한 괄호에 여러 경로를 넣으면 검사가 깨진다.
   - 실패·건너뜀이면 `미구현`으로 두고 이유를 완료 리포트에 쓴다.
   - 다른 열과 다른 섹션은 건드리지 않는다.
2. **`test-spec.md`의 `## 테스트 파일 구조`** — 계획 경로를 실제 테스트
   파일 경로와 실행 명령으로 바꾼다. `근거` 열은 실제 파일의 `[REF:]`.
3. **`layered-architecture.md`** — 단계 4.3의 경로 차이와 단계 4.2에서 승인된
   규약 예외만 반영하고, `## 문서 정보`의 `최종 수정일`과 버전 이력을
   갱신한다 (`common-rules.md` §6.4). 날짜는 `date +%F`.
4. **검증한다.**
   - `common-rules.md` §3의 `check-docs.sh`를 실행한다. `[REF:]`의 파일과
     줄 범위가 검사된다.
   - 이번에 쓴 `[REF:]`가 주장(그 테스트가 그 행의 설명을 검증한다)과
     맞는지 `citation-verifier`로 `test-spec.md`를 검증한다. **검증 범위는
     이번에 `근거`를 채운 행으로 한정해 호출한다** — `미구현` 행은 인용이
     없는 것이 정상이므로 `UNSUPPORTED`로 세지 않는다. `MISMATCHED`·
     `UNSUPPORTED`만 고치고 다시 검증한다 (`common-rules.md` §3, 계약 9).

### 단계 6: 완료 리포트

`common-rules.md` §4에 다음을 더한다.

- 구현한 FLOW 키와 각 FLOW의 `T-1NN` → `구현됨` 목록
- `미구현`으로 남은 `T-1NN`과 이유
- 생성한 파일과 수정한 파일 (디스크에서 확인한 것만, 계약 5)
- 추가한 의존성과 바꾼 설정 파일
- 검증 명령과 결과 (테스트 수, 린트, 의존 방향 계약)
- 사용한 스택 프로파일, 또는 "프로파일 없이 정한 관용구"
- 기록한 규약 예외와 기록을 거절한 항목
- 명세 외 테스트 (`구현 규약` §8.2.2)
- 기존 코드의 규약 이탈 (고치지 않은 것)
- 설계 수정 제안 (단계 4.3)
- `citation-verifier` 최종 집계
