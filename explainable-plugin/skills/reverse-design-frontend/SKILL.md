# reverse-design-frontend

이미 동작하는 프론트엔드 코드에서 **코드 흐름과 렌더링 흐름**을 근거와 함께
문서로 만든다.

**순서가 이 스킬의 핵심이다.** 인프라 → 프레임워크 감지 → FSD 적합도 판정 →
앱 셸 → 라우트. 프레임워크가 무엇인지 모르는 채로 파일을 읽기 시작하면
라우트 정의조차 찾지 못한다.

## 사용 시점

- 인수인계받은 프론트엔드를 파악해야 할 때
- "프론트엔드 분석해줘", "화면 구조 파악해줘", "렌더링 흐름 문서화"
- 어느 상태가 어디서 바뀌는지 추적해야 할 때

## 사용하지 않는 경우

- **코드가 아직 없는 경우** — `init-design-frontend`를 쓴다.
- **프론트엔드가 없는 프로젝트** — 감지 후 "해당 없음"을 보고하고 멈춘다.
- **백엔드 분석** — `reverse-design-backend`의 일이다.
- **요구사항·유저 스토리가 필요한 경우** — 이 스킬을 먼저 돌리고
  `reverse-planning`을 실행한다.

## 프레임워크 중립

**React를 가정하지 않는다.** 단계 2에서 실제로 감지한 값만 쓰고, 그 값을
모든 에이전트 호출에 입력으로 넘긴다. 에이전트가 스스로 프레임워크를
추측하지 않도록 하는 장치다.

문서에 쓰는 어휘는 일반 명칭이다: "UI 단위", "라우트", "렌더링 모드",
"상태 저장소", "데이터 조회 단위", "로딩·오류 경계". 구체 라이브러리 이름은
감지 결과를 인용할 때만 등장한다.

## FSD는 대조 기준일 뿐이다

**역방향은 기존 코드를 기술하는 것이지 FSD로 리팩터링하자고 제안하는 것이
아니다.** FSD는 순방향(`init-design-frontend`)의 기본값이고, 여기서는 실제
구조를 FSD에 대비해 보여주는 기준으로만 쓴다.

코드가 FSD를 따르지 않으면 "따르지 않는다"고 쓰고 실제 구조를 기록한다.
억지로 재분류하지 않는다.

## 근거와 인용 계약

`reverse-design-backend`와 동일한 계약이 적용된다. 요약하면:

1. **코드에서 직접 확인한 사실만 쓴다.** 프레임워크 관례로 빈칸을 채우지
   않는다.
2. **모든 주장에 `[REF: 경로:줄번호]`가 붙는다.** 이번 패스에서 실제로 연
   파일만 인용한다.
3. **확인할 수 없는 내용은 `[ASSUMED: <추론>; basis: <실제로 본 것>]`.**
   추측을 확인된 것처럼 보이게 하려고 `파일:줄`을 지어내지 않는다.
4. **모든 문서는 `## 읽은 소스` 원장으로 끝난다.**
5. **렌더 시퀀스 다이어그램은 Source-Linked 규약을 따른다** — 참여자 `link`
   줄, 메시지별 `Note`, 숨김 `CALLGRAPH` 블록. 상세 규약은
   `${CLAUDE_PLUGIN_ROOT}/templates/design/backend/sequence-diagram.md`의
   해당 절에 있다.

## 실행 규약

1. **템플릿은 필수다.** 없으면 없는 경로를 보고하고 멈춘다.

2. **에이전트 결과를 코드 재확인 없이 렌더링한다.** `render-flow-tracer`가
   반환한 `RENDER_TRACE` 블록에서 다이어그램·`Note`·`CALLGRAPH`를 함께
   만든다.

3. **문서 간 책임 경계를 지킨다.**

   | 무엇 | 어느 문서 |
   |---|---|
   | 구조 (무엇이 무엇을 담는가) | `component-tree.md` |
   | 렌더 시점, 데이터 조회, **지역 상태**, 재렌더 유발 요인 | `render-flow.md` |
   | **공유·전역 상태, 서버 캐시** | `state-flow.md` |
   | 라우트 정의와 접근 제어 | `routing.md` |
   | 사용자 여정 | `user-flows.md` |

   에이전트의 `state` 항목에 있는 `scope` 값이 이 배분을 결정한다:
   `local`은 `render-flow.md`, `shared`와 `server`는 `state-flow.md`.

4. **앱 셸은 한 번만 추적한다.** 라우트마다 다시 추적하면 N개의 동일한
   추적이 생기고 곧 서로 어긋난다.

5. **`PARTIAL` 추적을 조용히 받아들이지 않는다.** 처리 절차는 단계 6에
   명시되어 있다.

6. **유저 플로우에 백엔드 호출을 그리지 않는다.** `FLOW-` 키를 링크만 한다.

7. **리뷰 게이트를 문자 그대로 지킨다.**

8. **미해결 항목이 남아 있으면 완료를 보고하지 않는다.**

## 단계별 지침

### 단계 0: 환경 감지와 재실행 판단

절차는 `reverse-design-backend` 단계 0과 동일하다.

1. **문서 환경 감지** — `docs/config.yml` 또는 디렉터리 추론. 동의 없이
   `docs/config.yml`, 루트 `CLAUDE.md`, `.claude/rules/`를 쓰지 않는다.
2. **분석 기준 커밋 확정** — `git rev-parse HEAD`, 정규화한 저장소 URL,
   체크아웃된 브랜치, 작업 트리 상태.
3. **재실행 판단** — 기존 역방향 문서가 있으면 폐기 대상 목록을 보여주고
   확인받는다. 작업 트리가 clean하지 않으면 경고한다. 폐기 범위는
   `<도메인>/design/frontend/**`이며, 횡단 문서와 `glossary.md`는 폐기하지
   않는다.
4. **리뷰 모드 확인** (`단계별` 기본 / `연속`).

### 단계 1: 인프라 탐색

**산출**: `specifications/infrastructure.md`

1. **`infrastructure.md`가 이미 있고 `분석 기준 커밋`이 현재 HEAD와 같으면
   건너뛴다.** `reverse-design-backend`가 방금 만들었을 수 있다. 그 사실을
   완료 리포트에 남긴다.
2. 그렇지 않으면 **`infra-explorer` 에이전트를 호출한다.**
3. 반환된 `INFRA` 블록에서 **프론트엔드 관련 항목**을 문서에 병합한다:
   빌드 도구, 번들러, 정적 자산 배포 대상, 클라이언트에 노출되는 환경 변수,
   CDN 설정.
4. **환경 변수의 값을 절대 적지 않는다.** 클라이언트 번들에 들어가는 변수는
   특히 주의해서 이름만 적는다.
5. 기존 파일이 있으면 백엔드가 쓴 섹션을 바이트 단위로 보존한다.

### 단계 2: 프레임워크 감지와 코드베이스 구조

**산출**: `specifications/architecture.md`의 `## 프론트엔드 구조` 섹션과
`## 아키텍처 규약` 표의 프론트엔드 행

이 단계의 산출물이 **이후 모든 에이전트 호출의 입력**이 된다.

1. **프론트엔드가 있는지 확인한다.** 없으면 멈춘다:

   > 이 저장소에서 프론트엔드 코드를 찾지 못했습니다.
   > 확인한 경로: `<경로들>`
   > 백엔드 분석은 `/explainable:reverse-design-backend`를 사용하세요.

2. **감지된 프레임워크 환경 표를 채운다.** 각 항목에 인용을 붙인다.

   | 항목 | 어디서 확인하나 |
   |---|---|
   | 프레임워크 | 패키지 매니페스트와 잠금 파일 |
   | **라우트 정의 파일 패턴** | 라우터 설정 또는 파일 기반 라우팅 규칙 |
   | 상태 관리 | 매니페스트의 의존성과 실제 사용처 |
   | 데이터 조회 계층 | 서버 통신 코드의 공통 패턴 |
   | 렌더링 모드 | 프레임워크 설정과 페이지별 지시 |

   **라우트 정의 파일 패턴이 특히 중요하다** — 이것이 없으면 에이전트가
   라우트 경계를 찾지 못한다.

3. **FSD 레이어 ↔ 디렉터리 매핑을 시도한다.** 실제 경로를 FSD 레이어에
   대응시킨다. 대응되지 않는 디렉터리는 `미분류`로 둔다.

4. **`## 아키텍처 규약`의 스택 표와 레이어 매핑 표에 프론트엔드 행을
   채운다.** 백엔드 행은 바이트 단위로 보존한다.

### 단계 3: FSD 적합도 판정

**산출**: `<도메인>/design/frontend/fsd-structure.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/fsd-structure.md`

1. **FSD 준수 여부를 판정한다**: 준수 / 부분 준수 / 따르지 않음.
2. **따르지 않으면 실제 구조를 먼저 기록하고** FSD 대비표를 붙인다.
   개요에 "FSD를 따르지 않는다"는 사실과 실제로 어떤 구조인지를 쓴다.
3. **억지로 재분류하지 않는다.** 대응되지 않는 레이어는 "대응 없음"으로
   두고, 그것이 정보다.
4. 슬라이스 목록과 공개 API를 인용과 함께 기록한다.
5. 세그먼트 구성 표에서 프로젝트가 실제로 쓰는 이름을 `이 프로젝트의 이름`
   열에 적고 표준 세그먼트와 대응시킨다.
6. **의존 규칙 위반을 이 도메인 범위에서 기록한다.** 사실만 쓰고
   리팩터링을 제안하지 않는다.
7. `domain-model.md`가 있으면 `entities` 슬라이스와 애그리거트를 용어집을
   매개로 대응시킨다. 없으면 그 섹션을 삭제한다.

### 단계 4: 라우트·도메인 식별 — 리뷰 게이트 ①·②

1. **라우트를 전부 나열한다.** 단계 2에서 확정한 라우트 정의 파일 패턴으로
   찾고, 각 라우트의 진입점 `경로:줄번호`를 기록한다.

2. **도메인에 매핑한다.** 백엔드가 이미 도메인을 정했으면 그것을 따르고,
   프론트엔드 전용 프로젝트면 라우트 그룹과 슬라이스로 도메인을 제안한다.

3. **사용자에게 제시하고 확인받는다:**

   > 라우트 `<N>`개를 찾았습니다. 도메인 매핑은 다음과 같습니다:
   >
   > | 도메인 | 라우트 | 근거 |
   > |---|---|---|
   >
   > 이대로 진행할까요?

4. **추적 대상 라우트가 도메인당 20개를 넘으면 개수를 알리고 다시
   확인받는다.** 조용히 잘라내지 않는다.

5. **모노레포면 앱 경계도 함께 확인한다.**

### 단계 5: 앱 셸 추적 (1회)

**산출**: `<도메인>/design/frontend/render-flow.md`의 `## 앱 셸` 섹션

1. **`render-flow-tracer`를 `mode: shell`로 한 번만 호출한다.**

2. **에이전트에 넘기는 입력:**

   | 입력 | 출처 |
   |---|---|
   | 저장소 루트 | 단계 0 |
   | `mode: shell` | — |
   | 애플리케이션 진입점 `경로:줄번호` | 단계 2 |
   | 감지된 프레임워크·라우터·상태 라이브러리·데이터 조회 계층 | 단계 2 |
   | 라우트 정의 파일 패턴 | 단계 2 |
   | FSD 레이어 ↔ 디렉터리 매핑 | 단계 2·3 |
   | 용어집 항목 | 현재까지 확정된 것 |

3. 반환된 `RENDER_TRACE`에서 진입점부터 라우터 해석까지의 시퀀스
   다이어그램, 단계 표, 전역 가드 표를 만든다.

4. **셸 추적 요약을 보관한다.** 단계 6의 모든 라우트 호출에 입력으로
   넘긴다.

5. **여러 도메인 문서에 앱 셸을 반복하지 않는다.** 첫 도메인 문서에만 쓰고,
   나머지는 그 문서를 링크한다.

### 단계 6: 라우트별 흐름 추적

**산출**: `<도메인>/design/frontend/render-flow.md`,
`component-tree.md`, `state-flow.md`, `routing.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/` 아래 각 파일

1. **라우트 하나당 `render-flow-tracer`를 `mode: route`로 한 번 호출한다.**
   5~8개씩 묶어 병렬로 실행한다.

2. **입력은 단계 5와 같되 다음을 추가한다:**
   - `mode: route`
   - 대상 라우트 패턴과 진입점 `경로:줄번호`
   - **셸 추적 요약** — 이것이 있어야 에이전트가 셸을 다시 훑지 않는다

3. **`status: PARTIAL` 처리 절차:**
   - **1회 재시도** — 종료 규칙과 FSD 매핑을 보강해 다시 호출한다.
   - 여전히 `PARTIAL`이면 해당 구간을 `[ASSUMED: ...]`로 표시하고
     `unresolved`를 문서의 `## 미해결 항목`에 남긴다.
   - **완료 리포트에 미해결 개수를 명시한다.**
   - 스키마를 벗어난 응답은 그 라우트를 실패로 기록하고 다음으로 넘어간다.
     **묶음 하나가 실패해도 전체를 멈추지 않는다.**

4. **반환 데이터를 네 문서로 배분한다.**

   | 에이전트 필드 | 가는 문서 |
   |---|---|
   | `route`, `guards` | `routing.md` |
   | `ui_tree` | `component-tree.md` |
   | `participants`, `edges`, `branches` | `render-flow.md`의 시퀀스 다이어그램 |
   | `entry`, `render_mode`, `data_sources`, `render_boundaries`, `rerender_triggers` | `render-flow.md` |
   | `state` (`scope: local`) | `render-flow.md` |
   | `state` (`scope: shared` 또는 `server`) | `state-flow.md` |
   | `navigation` | `routing.md`의 라우트 전환 표 |

   **`edges`와 `ui_tree`를 섞지 않는다.** `edges`는 시퀀스 다이어그램의
   원료이고 `ui_tree`는 구조 문서의 원료다.

   **`scope`가 이 배분을 결정한다.** 판단이 애매해 에이전트가 `unresolved`에
   남긴 상태는 임의로 배분하지 말고 미해결 항목에 둔다.

5. **`render-flow.md`의 라우트 섹션**을 만든다. 제목은
   `### FLOW-<도메인>-<라우트 슬러그>: <라우트 이름>`이다. 각 `RENDER_TRACE`의
   데이터 하나에서 시퀀스 다이어그램·`Note`·`CALLGRAPH`를 함께 렌더링한다.
   **앱 셸 부분은 다시 그리지 않는다.**

6. **`state-flow.md`의 서버 상태 표**에서 `캐시 키`는 `render-flow.md`의
   데이터 조회 표와 일치해야 한다. **`무효화 계기`를 코드에서 찾아 채운다** —
   찾지 못하면 `[ASSUMED: ...]`로 표시한다.

7. **`routing.md`의 접근 제어 표**에서 공개 라우트도 "인증 불필요"로
   명시한다. 빈 칸은 미확인과 구분되지 않는다.

### 단계 7: 유저 플로우 역추출

**산출**: `<도메인>/design/frontend/user-flows.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/user-flows.md`

1. `routing.md`의 라우트 전환 표와 각 라우트의 UI 단위에서 사용자 여정을
   조립한다.
2. `flowchart TD`로 그린다. **노드는 사용자가 보는 것**, **간선은 사용자
   행동**이다.
3. **서버 처리는 노드 하나로 뭉뚱그리고 `서버 흐름` 열에 `FLOW-` 키를
   링크만 한다.** 백엔드 시퀀스 다이어그램을 여기 복제하지 않는다.
4. 예외 경로를 반드시 채운다. `render-flow.md`의 오류 경계와 대응시킨다.
5. **의도를 추론한 부분에는 배너를 넣는다** — 사용자 여정의 "왜"는 코드에
   없다.

### 단계 8: 슬라이스 의존 맵

**산출**: `specifications/domain-map.md`의
`## 프론트엔드 슬라이스 의존 맵`

1. **슬라이스 간 import를 전부 수집한다.** 각 간선에 인용을 붙인다.
2. **정상 의존과 규칙 위반을 구분해 그린다.** 정상은 실선, 위반은 점선에
   위반 스타일.
3. **위반은 사실로만 기록하고 리팩터링을 제안하지 않는다.**
4. **다른 스킬이 쓴 섹션(백엔드 컨텍스트 맵, 도메인 간 통합 계약, 도메인
   횡단 흐름)은 바이트 단위로 보존한다.**
5. `## 패턴 범례`는 고정 표다. 편집하지 않는다.

### 단계 9: 검증과 수정 루프

1. **생성한 문서마다 `citation-verifier`를 한 번씩 호출한다.**
   `render-flow.md`는 시퀀스 다이어그램을 담으므로 `Note` ↔ `CALLGRAPH`
   양방향 교차 검증까지 받는다.

2. **수정 루프:**
   - `MISMATCHED`와 `UNSUPPORTED`만 고친다.
   - `MATCHED`와 `EXCLUDED`는 건드리지 않는다.
   - 깨끗해질 때까지 다시 호출한다.

3. **결정적 검사도 실행한다:**

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-docs.sh" docs/<원본 언어>/specifications
   ```

4. **미해결 항목이 남아 있으면 완료를 보고하지 않는다.**

### 단계 10: 완료 리포트 — 리뷰 게이트 ③

- 생성한 파일 경로 (디스크에서 확인한 것만)
- 문서별 `citation-verifier` 최종 집계
- `check-docs.sh` 결과
- **미해결 항목 개수**와 그 목록
- 추적하지 않은 라우트와 그 이유
- FSD 준수 판정 결과와 발견한 규칙 위반 개수
- 건너뛴 단계 (인프라 재사용 등)
- 다음 단계 안내:

  > 프론트엔드 설계 문서화가 끝났습니다.
  >
  > - 요구사항과 유저 스토리를 역산하려면 `/explainable:reverse-planning`
  > - 백엔드가 아직이면 `/explainable:reverse-design-backend`
  > - 번역 미러가 필요하면 `/explainable:translate-docs`

## 문서 규칙

- 모든 문서는 한국어로 쓴다. 코드 블록, 파일 경로, 식별자는 영어 그대로 둔다.
- **프레임워크 고유 API 이름을 서술의 기본 어휘로 쓰지 않는다.** 일반
  명칭으로 기술하고, 구체 이름은 감지 결과를 인용할 때만 등장한다.
- 기계용 토큰은 영문 고정이다: `[REF: ...]`, `[ASSUMED: ...; basis: ...]`,
  `MATCHED`/`MISMATCHED`/`UNSUPPORTED`/`EXCLUDED`, `FLOW-` 접두사.
- `## 문서 정보` 표는 하단에 두고 **`분석 기준 커밋`을 반드시 채운다.**
- 날짜는 `date +%F`로 얻는다.
- 내비게이션 링크는 `${CLAUDE_PLUGIN_ROOT}/references/document-order.md`를
  따른다. 생성하지 않은 문서는 체인에서 뺀다.
- 병합 전용 문서에서 자기 소유가 아닌 섹션은 바이트 단위로 보존한다.
- 증거가 없는 카테고리의 문서를 만들지 않는다.
