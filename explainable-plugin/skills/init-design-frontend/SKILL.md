# init-design-frontend

기획 문서가 정한 **무엇을**을 화면 구조와 흐름으로 옮기는 스킬이다.
프론트엔드만 다룬다.

## 사용 시점

- `init-planning`이 끝난 뒤
- "프론트엔드 설계해줘", "화면 구조 잡아줘", "라우팅 설계"
- 기획은 이미 있고 클라이언트 쪽 구조만 필요할 때

## 사용하지 않는 경우

- **기획 문서가 없는 경우** — `init-planning`을 먼저 실행한다.
- **이미 코드가 있는 경우** — `reverse-design-frontend`가 코드에서 근거를
  달아 뽑아낸다.
- **프론트엔드가 없는 프로젝트** — 감지 후 "해당 없음"을 보고하고 멈춘다.
- **백엔드 설계** — `init-design-backend`의 일이다.

## FSD 기준선

레이어는 여섯 개다.

```text
app → pages → widgets → features → entities → shared
```

| 레이어 | 담는 것 |
|---|---|
| `app` | 진입점, 전역 프로바이더, 라우터 설정 |
| `pages` | 라우트 단위 화면 조립 |
| `widgets` | 재사용 가능한 화면 블록 |
| `features` | 사용자 행동 단위 |
| `entities` | 도메인 개체와 그 표현 |
| `shared` | 도메인 무관 공용 코드 |

레이어 안은 **슬라이스**(도메인 단위)로, 슬라이스 안은 **세그먼트**(`ui`,
`model`, `api`, `lib`, `config`)로 나뉜다.

**의존 규칙**: 상위 레이어만 하위 레이어를 참조한다. 같은 레이어의 다른
슬라이스는 참조하지 않는다. 공유가 필요하면 하위 레이어로 내린다.

## 프레임워크 중립

**React를 가정하지 않는다.** 문서와 사고에 쓰는 어휘는 일반 명칭이다:
"UI 단위", "라우트", "렌더링 모드", "상태 저장소", "데이터 조회 단위",
"로딩·오류 경계". React·Vue·Svelte·Angular 어느 것이든 이 어휘로 기술된다.

구체 프레임워크·라이브러리 이름은 `architecture.md`의 스택 표에서 읽어
쓰되, **설계 판단에 그 프레임워크의 관례를 끌어들이지 않는다.**

## 실행 규약

1. **템플릿은 필수다.** 각 단계는 생성 전에
   `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/` 아래 템플릿을 읽는다.
   없으면 없는 경로를 보고하고 멈춘다.

2. **입력은 디스크에서 다시 읽는다.** `requirements.md`, `user-stories.md`,
   `api-interface.md`, `architecture.md`, `glossary.md`를 파일에서 읽는다.

3. **문서 간 책임 경계를 지킨다.** 이 경계를 어기면 두 문서가 같은 내용을
   서로 참조하며 반복한다.

   | 무엇 | 어느 문서 |
   |---|---|
   | 무엇이 무엇을 담는가 (구조) | `component-tree.md` |
   | 언제 그려지고 무엇을 조회하는가 | `render-flow.md` |
   | **지역 상태와 재렌더 유발 요인** | `render-flow.md` |
   | **공유·전역 상태, 서버 캐시** | `state-flow.md` |
   | 어떤 주소가 어떤 화면으로 가는가 | `routing.md` |
   | 사용자가 화면 사이를 어떻게 지나가는가 | `user-flows.md` |

   지역/공유의 경계는 **"그 라우트를 벗어나도 살아 있는가"**다.

4. **유저 플로우에 백엔드 호출을 그리지 않는다.** 서버 처리가 필요한
   지점은 `FLOW-` 키를 링크만 한다. 이 규칙을 어기면 백엔드 시퀀스
   다이어그램과 같은 내용을 두 번 그리게 된다.

5. **이름은 용어집에서 가져온다.** 슬라이스와 UI 단위 이름은
   `glossary.md`의 영문 식별자를 따른다.

6. **FLOW 키를 부여한다.** 라우트마다
   `FLOW-<도메인>-<라우트 슬러그>` 키를 붙인다.

7. **`## 읽은 소스` 섹션은 생성하지 않는다.** 코드가 없다.

8. **병합 전용 문서는 자기 섹션만 쓴다.** `test-spec.md`의 프론트엔드·E2E
   섹션, `domain-map.md`의 슬라이스 의존 맵, `architecture.md`의 프론트엔드
   구조 섹션만 건드린다.

9. **리뷰 게이트를 문자 그대로 지킨다.**

10. **확인한 경로만 보고한다.**

## 산출물

```text
docs/<원본 언어>/specifications/<도메인>/
├── design/frontend/
│   ├── fsd-structure.md
│   ├── routing.md
│   ├── component-tree.md
│   ├── render-flow.md
│   ├── state-flow.md
│   └── user-flows.md
└── verification/test-spec.md     # 프론트엔드(T-2NN)·E2E(T-3NN) 섹션
```

## 단계별 지침

### 단계 0: 입력 확인

1. **문서 환경 감지.** `docs/config.yml`을 읽어 `source_language`를 정한다.
   절차는 `init-planning` 단계 0과 같다.

2. **선행 기획 문서를 확인한다.** 없으면 멈춘다:

   > `<도메인>/planning/`에 기획 문서가 없습니다.
   > `/explainable:init-planning`을 먼저 실행해 주세요.

3. **프론트엔드가 있는 프로젝트인지 확인한다.** `architecture.md`의 스택
   표에 프론트엔드 항목이 없고 사용자도 계획하지 않는다면:

   > 이 프로젝트에는 프론트엔드가 없습니다. 프론트엔드 설계 문서를 만들지
   > 않고 종료합니다.

   빈 문서를 만들지 않는다.

4. **FSD 채택 여부를 확인한다.** `architecture.md`의 아키텍처 규약에 이미
   기록되어 있으면 그것을 따른다. 없으면 묻는다:

   > 프론트엔드 구조로 FSD(app / pages / widgets / features / entities /
   > shared)를 제안합니다. 이대로 갈까요, 아니면 다른 구조를 쓸까요?

   FSD를 쓰지 않기로 하면 `fsd-structure.md` 대신 사용자가 정한 구조를
   같은 자리에 기록하고, 이후 단계의 레이어 관련 표를 그 구조에 맞춘다.

5. **기존 설계 문서를 확인한다.** 있으면 덮어쓰지 않고 어느 문서를 다시
   만들지 확인받는다.

6. **리뷰 모드를 확인한다** (`단계별` 기본 / `연속`).

### 단계 1: FSD 구조

**산출**: `<도메인>/design/frontend/fsd-structure.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/fsd-structure.md`

1. `architecture.md`의 레이어 ↔ 디렉터리 매핑 표에서 프론트엔드 행을 읽는다.
2. 레이어 구성 표를 채운다. 이 도메인이 쓰지 않는 레이어는 경로를 `—`로
   두고 비고에 "이 도메인에서는 사용하지 않음"이라고 적는다. **행을 지우지
   않는다** — 왜 안 쓰는지가 정보다.
3. 슬라이스를 정한다. 슬라이스 이름은 `glossary.md`의 영문 식별자를 따른다.
4. 세그먼트 구성 표에서 프로젝트가 실제로 쓸 세그먼트만 남긴다.
5. **`## 백엔드 도메인 모델과의 대응`** — `domain-model.md`가 있으면
   `entities` 슬라이스와 애그리거트를 용어집을 매개로 연결한다. 둘이 1:1일
   필요는 없다. 다른 부분이 있으면 그것이 이 표의 정보다. 백엔드가 없는
   프로젝트면 섹션과 목차 항목을 삭제한다.

> **단계 1 완료**: FSD 구조를 작성했습니다. 검토 후 라우팅으로 진행할까요?

### 단계 2: 라우팅

**산출**: `<도메인>/design/frontend/routing.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/routing.md`

1. `user-stories.md`의 각 스토리가 어떤 화면을 필요로 하는지 도출한다.
2. 라우트 트리를 그린다. 동적 구간 표기는 `architecture.md`에 기록된
   라우터의 표기를 따른다.
3. 라우트 목록 표에서 **`관련 스토리` 열을 반드시 채운다.** 어느 스토리와도
   연결되지 않는 라우트가 있으면 `traceability.md`의 미연결 항목으로
   내린다.
4. **접근 제어 표에서 공개 라우트도 "인증 불필요"로 명시한다.** 빈 칸은
   미확인과 구분되지 않는다. 권한 이름은 `api-interface.md`의 인가 표와
   일치해야 한다.
5. `FLOW-<도메인>-<라우트 슬러그>` 키를 각 라우트에 부여한다.
6. **라우트 전환 표에는 간선만 적는다.** 전체 여정 서술은 `user-flows.md`의
   일이다.

### 단계 3: UI 구성

**산출**: `<도메인>/design/frontend/component-tree.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/component-tree.md`

1. 라우트마다 화면을 조립하는 UI 단위 트리를 그린다. 각 노드에 FSD
   레이어·슬라이스를 괄호로 표시해 슬라이스 경계가 보이게 한다.
2. 조건부로 나타나는 단위는 `(조건부)`, 반복되는 단위는 `(반복)`을 붙인다.
   **조건의 내용은 여기 쓰지 않는다** — `render-flow.md`의 일이다.
3. 공용 UI 단위는 두 개 이상의 화면에서 쓰이는 것만 적는다. `사용처` 열이
   비면 그 단위는 공용이 아니다.
4. **입출력 계약은 공용 단위와 슬라이스 공개 API만 적는다.** 내부 구현
   단위까지 적으면 코드가 바뀔 때마다 문서가 틀린다.
5. 렌더 시점이나 상태 변화를 여기 쓰고 싶어지면 멈춘다 — 그건 다른 문서의
   내용이다.

> **단계 3 완료**: UI 구성을 작성했습니다. 검토 후 렌더링 흐름으로
> 진행할까요?

### 단계 4: 렌더링 흐름

**산출**: `<도메인>/design/frontend/render-flow.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/render-flow.md`

1. **`## 앱 셸`을 한 번만 기술한다.** 진입점 → 전역 프로바이더 → 전역 상태
   → 라우트 가드. 다른 도메인 문서에 이미 앱 셸이 있으면 여기서는 링크만
   하고 반복하지 않는다.
2. **Source-Linked 모드 요소를 전부 생략한다.** 참여자 `link` 줄, 메시지별
   `Note`, 숨김 `CALLGRAPH` 블록은 코드가 있을 때만 쓴다.
3. 라우트마다 한 섹션을 만든다. 제목은
   `### FLOW-<도메인>-<라우트 슬러그>: <라우트 이름>`이다. **앱 셸 부분은
   다시 그리지 않고 라우트 경계 안쪽부터 시작한다.**
4. **데이터 조회 표** — `조회 시점`을 "라우트 진입 전 / 렌더 중 / 렌더 후 /
   사용자 행동 시" 중에서 정한다. `대상 오퍼레이션`은 `api-interface.md`의
   오퍼레이션 ID와 일치해야 한다.
5. **지역 상태 표** — 이 라우트를 벗어나면 사라지는 상태만. 다른 라우트와
   공유되면 `state-flow.md`의 일이다.
6. **재렌더 유발 요인 표** — 무엇이 바뀌면 어떤 UI 단위가 다시 그려지는지.
   성능 문제의 근원이 여기서 보인다.
7. `## 로딩·오류 경계` — 재시도 정책은 `api-interface.md`의 오류 모델에 있는
   `재시도 가능` 열과 일치해야 한다. 어긋나면 어느 쪽이 맞는지 확인한다.

### 단계 5: 상태 흐름

**산출**: `<도메인>/design/frontend/state-flow.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/state-flow.md`

1. **`## 상태 분류` 표를 먼저 채운다.** 이 표가 있어야 새 상태가 생겼을 때
   어디에 둘지 판단할 수 있다.
2. **서버 상태** — `캐시 키`는 `render-flow.md`의 데이터 조회 표와 일치해야
   한다. **`무효화 계기`를 반드시 채운다** — 이것이 없으면 "왜 화면이
   갱신되지 않는가"를 설명할 수 없다.
3. **클라이언트 공유 상태** — 저장소 단위로 나눠 적는다. FSD를 따르면
   대부분 `entities`나 `shared`의 `model` 세그먼트에 있다.
4. **낙관적 갱신을 쓴다면 실패 시 복구 방법이 반드시 있어야 한다.** 없으면
   낙관적 갱신을 설계하지 않는다.
5. **`## 상태 간 의존`에서 순환이 있으면 반드시 기록한다** — 무한 갱신의
   원인이 된다.
6. 지역 상태를 여기 쓰지 않는다. `render-flow.md`의 일이다.

> **단계 5 완료**: 상태 흐름을 작성했습니다. 검토 후 유저 플로우로
> 진행할까요?

### 단계 6: 유저 플로우

**산출**: `<도메인>/design/frontend/user-flows.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/design/frontend/user-flows.md`

1. 유저 스토리 하나에 플로우 하나가 기본이다.
2. `flowchart TD`로 그린다. **노드는 사용자가 보는 화면이나 결정**이고,
   **간선은 사용자 행동**이다.
3. **서버 처리는 노드 하나로 뭉뚱그리고 그 안을 그리지 않는다.**
   `서버 흐름` 열에 해당 `FLOW-` 키를 링크만 한다.
4. 정상 경로만 그리지 않는다. 예외 경로 표를 반드시 채운다. 오류 코드는
   `api-interface.md`의 오류 모델을 링크하고 여기서 정의하지 않는다.
5. `## 진입점` — 다른 도메인에서 넘어오는 경로가 있으면 `domain-map.md`의
   횡단 흐름과 일치해야 한다.

### 단계 7: 테스트 명세 프론트엔드·E2E 섹션

**산출**: `<도메인>/verification/test-spec.md`

템플릿: `${CLAUDE_PLUGIN_ROOT}/templates/verification/test-spec.md`

1. 파일이 없으면 템플릿에서 만들고, 있으면 **프론트엔드·E2E 섹션만
   갱신한다.** 백엔드 섹션은 바이트 단위로 보존한다.
2. **테스트 ID 대역**: 프론트엔드 `T-2NN`, E2E `T-3NN`. 백엔드(`T-1NN`)를
   침범하지 않는다.
3. E2E는 유저 플로우 하나에 하나가 기본이다. **모든 인수 기준을 E2E로
   덮으려 하지 않는다** — 느리고 깨지기 쉽다. 정상 경로와 치명적 실패
   경로만 E2E로 두고 나머지는 아래 계층에 맡긴다.
4. 순방향이므로 `상태` 열은 전부 `미구현`이고 `근거` 열은 비운다.

### 단계 8: 도메인 지도와 추적성 갱신

1. **`domain-map.md`의 `## 프론트엔드 슬라이스 의존 맵`을 갱신한다.**
   - 슬라이스 간 참조 그래프를 그린다. 정상 의존은 실선, **규칙 위반은
     점선에 위반 스타일**로 구분한다.
   - 순방향 설계에서 규칙 위반이 나오면 그건 설계 결함이다. 기록만 하지 말고
     설계를 고친다.
   - **백엔드 컨텍스트 맵 섹션은 건드리지 않는다.**

2. **`planning/traceability.md`를 갱신한다.**
   - `스토리 → 흐름` 표에 프론트엔드 `FLOW-` 키를 `계층: 프론트엔드`로
     추가한다. 백엔드 행은 보존한다.
   - `인수 기준 → 테스트` 표에 `T-2NN`, `T-3NN` ID를 채운다.

3. **`architecture.md`의 `## 프론트엔드 구조` 섹션을 갱신한다.** 순방향이므로
   "감지된 프레임워크 환경" 표는 사용자 결정값으로 채우고, FSD 적합도 표는
   채택한 구조를 기록한다. 다른 섹션은 보존한다.

4. **결정적 검사를 실행한다**:

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-docs.sh" docs/<원본 언어>/specifications
   ```

   보고된 문제를 전부 고친 뒤 다시 실행해 통과시킨다.

## 문서 규칙

- 모든 문서는 한국어로 쓴다. 코드 블록, 파일 경로, 식별자는 영어 그대로 둔다.
- **프레임워크 고유 API 이름을 설계 지시로 쓰지 않는다.** 일반 명칭으로
  기술하고, 구체 라이브러리 이름은 `architecture.md`에서 읽은 값을 인용할
  때만 등장한다.
- 기계용 토큰은 영문 고정이다: `FLOW-`, `US-`, `AC-`, `T-` 접두사.
- `## 문서 정보` 표는 문서 하단에 둔다. `분석 기준 커밋`은 "해당 없음"이다.
- 날짜는 `date +%F`로 얻는다.
- 내비게이션 링크는 `${CLAUDE_PLUGIN_ROOT}/references/document-order.md`를
  따른다. 생성하지 않은 문서는 체인에서 빼고 링크하지 않는다.
- 모든 Mermaid 블록은 문법적으로 완결되어야 하고 다이어그램 종류 선언을
  포함해야 한다.
- 증거가 없거나 해당하지 않는 섹션은 비워 두지 말고 제목까지 삭제한다.
