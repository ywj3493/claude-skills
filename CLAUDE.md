# Project Instructions

This project follows a structured documentation system. All work is driven by
and recorded in the `docs/` directory. Claude must treat `docs/` as the source
of truth and keep it up to date.

## Documentation Structure

Languages are configured in `docs/config.yml`; this project uses `en` as the
source language with a `ko` translation mirror.

```text
docs/
├── config.yml            # Language configuration (source + translation languages)
├── en/
│   ├── specifications/   # Domain-based: <domain>/planning/, <domain>/design/, <domain>/verification/
│   │   ├── architecture.md, config.md, infrastructure.md  # Cross-cutting top-level docs
│   │   └── <domain>/     # Created by the dev-docs plugin's dev-planning/dev-reverse-docs skills
│   ├── issue/            # One file per work item: issue001.md, issue002.md, ...
│   └── policy/           # Scaffolding only — this repo's own core policy lives in .claude/rules/;
│                         # this directory is for future ad-hoc, downstream-style docs (via new-policy)
├── ko/
│   ├── specifications/   # Korean translations of en/specifications/
│   ├── issue/            # Korean translations of en/issue/
│   └── policy/           # Korean translations of any docs added under en/policy/
└── reference/            # Reference materials — user-provided only, never generated by Claude
```

This repo's own operative policy — commit message format, naming
conventions, the `@`-reference convention, and skill/plugin versioning —
lives in `.claude/rules/` (English-only, auto-loaded every session), not
under `docs/en/policy/`. See Core Rule 5.

## Core Rules

1. **Start with an issue.** Every piece of work — feature, bug fix, refactor,
   investigation — begins by creating or referencing an issue — either a
   GitHub Issue (preferred when a remote exists) or a local document in
   `docs/en/issue/`. Do not start implementation without one.

2. **Language directories.** English documents live in `docs/en/`. Korean
   translations live in `docs/ko/`. Both use the same filename (no `.ko.md`
   suffix).
   Example: `docs/en/issue/issue003.md` → `docs/ko/issue/issue003.md`

3. **Korean mirror.** Every doc created in `docs/en/specifications/`,
   `docs/en/issue/`, and `docs/en/policy/` gets a matching Korean translation
   in the corresponding `docs/ko/` subdirectory with the same filename.

4. **Reference is read-only.** Never create or modify files in `docs/reference/`.
   That directory is managed exclusively by the user. It sits at the `docs/`
   root because reference materials are language-neutral.

5. **Policy is law.** Operative policy lives in `.claude/rules/` — it loads
   automatically every session, so there is no manual load step. Policy
   rules take precedence over general conventions.

6. **Keep docs current.** When implementation changes, update the relevant docs
   in the same commit or PR.

## Required Context

Policy (commit message format, naming conventions, the `@`-reference
convention, skill/plugin versioning) is in `.claude/rules/` and already
loaded — no action needed to bring it into context.

For active work, also load the relevant issue from `docs/en/issue/`.
For GitHub Issues, load the issue content via `gh issue view <number>`.

## Issue Document Format

This format applies to local docs-mode issues (`docs/en/issue/`).
GitHub Issues use the same sections in the issue body (without Status/Created fields).

Each issue document must contain:

- **Title** and brief description
- **Status** — Open / In Progress / Done
- **Background** — why this work is needed
- **Acceptance Criteria** — what "done" looks like (checkboxes)
- **Tasks** — numbered checklist of steps
- **Notes** — decisions and discoveries made during implementation

## Language Notes

- Code, variable names, file paths, technical identifiers: English
- All documentation in `docs/en/`: English
- All documentation in `docs/ko/`: Korean
- Code blocks inside Korean docs remain in English
